Picture this

It is Saturday evening and ten million phones are awake at once, each one quietly whispering "here I am" to the backend every 30 seconds. Somewhere downtown, you open the app and, within seconds, dots appear: your college roommate is 1.2 miles away, a colleague is 3 miles out, and the dot for your cousin just slid a little closer. Unlike a restaurant finder, where the addresses sit still for years, every dot here is moving, and every move must be relayed to the handful of friends who care. That is roughly 334,000 location updates arriving each second, each fanning out to about 40 online friends. The hard part is not finding friends; it is being a tireless, real-time switchboard at that volume.

1 Macro Structure & Dependency Map

From 10,000 feet this is a fan-out machine: updates come in over persistent connections, get stored briefly, and are broadcast to friends. Read each hub as a load-bearing wall; everything nested under it collapses if the hub is misunderstood.

  • WebSocket servers (stateful, persistent connections) — the only path by which updates reach phones in real time; every other component is fed by or feeds these
    • Periodic location update routine (client sends location every 30s)
      • Other routines: client init, receive update, subscribe / unsubscribe a friend
    • Distance filter: forward only if friend is within the 5-mile threshold
      • Server keeps each connected user's latest location in memory for this math
    • Scaling by "draining" a server in the load balancer before removal
      • REST API servers handle auxiliary work (friends, profiles) and scale trivially
  • Redis Pub/Sub (one channel per user) — the switchboard that routes one user's update to all servers holding that user's friends
    • WebSocket servers subscribe to channels of each connected user's friends
      • Channels are pre-allocated; idle channels consume no memory
    • Distributed cluster sized for CPU: ~14M pushes/s ÷ ~100k per server = 140+ servers
      • Memory need is only ~200GB (2 servers of 100GB would do)
    • Consistent hash ring stored in ZooKeeper / etcd
      • Ring cached in memory on each WebSocket server
  • Redis location cache (latest location + TTL) — the "who is active and where" snapshot that seeds new clients and defines activity itself
    • Maps user_id to lat, long, timestamp
      • TTL expiry = user is inactive (friends disappear after ~10 min)
    • Sharded across several Redis nodes to absorb the write load
  • Durable stores (User DB + Location history DB) — the slow, permanent side: who your friends are, and where everyone has been
    • User DB: users + friendships, sharded by user_id
      • Could be its own service owned by a dedicated team
    • Location history in Cassandra (write-heavy), used for analytics / ML
      • Not on the hot path of the nearby feature

WebSocket servers are the hub because they own the live connection and the distance calculation. Redis Pub/Sub is the second hub because it replaces a brute-force "look up all 400 friends" query with a push-based broadcast. The location cache and durable stores are supporting actors: the cache answers "where is everyone right now" at startup, and the databases hold the slow-changing friend graph and the history nobody reads in real time.

2 Black-Box Cause & Effect Flow

Treat each component as a sealed box: know what goes in and what comes out, and the whole update pipeline becomes a chain of cause and effect.

Mobile client

Input: GPS reading, a 30-second timer.

Output: A location update (lat, long, timestamp) over its persistent WebSocket.

A lighthouse that flashes its position every half minute. Walking speed is slow, so more frequent flashes would waste battery for little gain.

→ feeds into: Load balancer → the client's WebSocket server

WebSocket server (sender side)

Input: The user's location update.

Output: A row in location history, a fresh entry in the location cache, an in-memory copy, and a publish to the user's own Pub/Sub channel.

A post office clerk who files a copy, updates the "last seen" board, and then drops the letter into the user's personal outgoing chute.

→ feeds into: Location history DB, Location cache, Redis Pub/Sub

Redis Pub/Sub channel

Input: One published message on channel user_X.

Output: A copy delivered to every subscriber, i.e. each WebSocket server holding one of X's online friends.

A megaphone with a subscriber list. It does not know who is near whom; it just repeats the message to everyone who signed up.

→ feeds into: Subscribed WebSocket servers

WebSocket server (receiver side)

Input: Friend X's new location, plus its own connected user's last known location held in memory.

Output: Either a pushed update (distance + timestamp) to the phone, or silence if beyond 5 miles.

The bouncer at the door: it calculates the distance and only lets the update through if the friend is close enough to matter.

→ feeds into: Friend's mobile client

Client initialization

Input: A newly opened connection with the user's location.

Output: Friend list fetched, subscriptions to every friend's channel, friends' current locations pulled from cache and sent down.

Walking into a party: you get the guest list, tune into everyone's conversation, and glance at where each person is standing right now.

→ feeds into: Steady-state periodic update loop

Location cache TTL

Input: Silence from a user (no updates).

Output: The cache entry expires; the user is treated as inactive.

A candle that burns out unless someone keeps relighting it. No explicit "logout" is needed.

→ feeds into: Future client initializations (friend no longer shown)

Follow one location update

  1. Maya's phone, 30 seconds after its last ping, sends (37.77, -122.41, t=20:00:30) over its open WebSocket.
  2. The load balancer routes it along the persistent connection to WebSocket server WS-7, which owns Maya's connection.
  3. WS-7 appends the point to the Cassandra location history table (for later analytics).
  4. WS-7 overwrites Maya's entry in the Redis location cache and resets its TTL; it also stores the point in its own memory.
  5. WS-7 hashes the channel name "maya" on the cached consistent-hash ring, finds Pub/Sub server p_3, and publishes.
  6. Maya has 400 friends; about 10% (40) are online. Their WebSocket servers all subscribed to "maya" during init, so p_3 pushes 40 copies out.
  7. On WS-2, friend Leo's last location is in memory: 1.8 miles from Maya. Within 5 miles, so WS-2 pushes "Maya, 1.8 mi, 20:00:30" to Leo's phone.
  8. On WS-9, friend Priya is 11 miles away. WS-9 drops the update silently.
  9. Multiply by 334k updates per second and you get ~14 million pushes per second through the Pub/Sub layer.

3 Purpose & Concept Beacons

Build a real-time fan-out backend that relays each active user's constantly changing location to nearby friends within seconds, tolerating occasional lost points but never falling over.

Mental picture

Imagine a vast radio network. Every user owns a personal radio frequency: that is their Redis Pub/Sub channel. The WebSocket servers are receiving stations that tune in to the frequencies of every friend of the listeners they serve. When you speak your location into your frequency, every tuned-in station hears it, but each station has a filter: it only relays your voice to its listener if you are within 5 miles. The big bulletin board by the door that shows "last heard from, and where" is the Redis location cache, and chalk marks on it fade after a few minutes (TTL). The archive room recording every broadcast forever is the Cassandra location history database.

4 Opportunistic Drilling

Interviews on this problem live or die on three things: the fan-out path, scaling the Pub/Sub cluster, and what state the WebSocket layer holds. Drill those; skim the rest.

The periodic update and fan-out path

The core insight is to flip the question. Instead of each user asking "where are my 400 friends?", each user announces "here I am" once, and the system pushes that announcement to the ~40 friends who are online. Redis Pub/Sub is the lightweight message bus that makes this cheap: one publish, many deliveries.

Notice where the distance check happens: on the receiving WebSocket server, not in Redis. Pub/Sub delivers blindly to every subscriber; the receiving server compares the friend's new point against its own user's in-memory location and decides whether to push. This keeps Redis dumb and fast.

  1. Client sends location to its WebSocket server.
  2. Server writes to location history DB and to the location cache (plus its own memory).
  3. Server publishes to the user's channel.
  4. Pub/Sub broadcasts to every subscribed WebSocket server.
  5. Each receiver computes distance and pushes only if within the threshold.
Common trap: proposing peer-to-peer between phones. The notes reject it: mobile connections are flaky and battery-constrained, so a shared backend acting as a fan-out hub is the practical choice.

Scaling Redis Pub/Sub: a CPU problem in disguise

The memory math is surprisingly small: around 200GB for all channels, which two 100GB servers could hold. But the push rate tells a different story. Roughly 14 million location pushes per second, at about 100k pushes per server, demands at least 140 Redis servers. The bottleneck is CPU, so the cluster must be distributed.

To know which server owns which channel, the channel names are placed on a consistent hash ring stored in a service discovery system (ZooKeeper or etcd). Each WebSocket server caches that ring in memory and hashes a channel name to find its home. When a server is added or removed, consistent hashing ensures only the channels in the affected arc move.

Gains

Horizontal scaling of push throughput; minimal channel movement on resize; lookups are local (cached ring).

Costs

The cluster is effectively stateful: resizing triggers a storm of resubscriptions and may drop some updates, so do it at the daily traffic low, driven by a scheduled job, and overprovision for spikes.

Common trap: sizing the cluster by memory alone and concluding "two servers is enough." Always compute both memory and operations per second; here CPU wins by a factor of 70.

What each store holds, and why Redis twice

Redis appears in two roles and it is easy to blur them. The location cache stores just the latest point per user with a TTL: it answers "where is my friend right now?" during initialization and naturally forgets inactive users. Redis Pub/Sub stores no location at all; it is purely a routing fabric.

Adding or removing a friend is handled by a client callback: the app tells the WebSocket server, which subscribes to or unsubscribes from that friend's channel. "Whale" users with many friends are capped (Facebook's cap is 5000), and their extra load is absorbed by having enough WebSocket servers.

Extension: nearby random people via geohash channels

If the interviewer asks to show strangers nearby, swap "one channel per user" for "one channel per geohash cell." Everyone inside a cell publishes to and subscribes to that cell's channel, so you hear about anyone in your square of the map.

An alternative to Redis Pub/Sub entirely is Erlang: millions of lightweight processes can handle both WebSocket connections and channels in one distributed application. The catch is people, not technology: Erlang is niche and strong developers are hard to hire.

Test yourself

Write your answer in the margin with your stylus before tapping to reveal.

Why is the location refresh interval 30 seconds rather than 1 second?

Human walking speed is slow, so position barely changes in a second. With 10M concurrent users, 30s gives ~334k QPS; 1s would be 10M QPS inbound and 30x the fan-out, with little user-visible benefit and much worse battery drain.

Where does the 5-mile distance check happen, and why there?

On the receiving WebSocket server, which holds its connected user's latest location in memory. Pub/Sub just broadcasts to all subscribers; doing the math at the edge keeps Redis simple and avoids extra lookups.

Memory says 2 Redis servers; why do we need 140+?

The channels fit in ~200GB, but pushing ~14M updates per second at ~100k pushes per server needs at least 140 servers. The workload is CPU-bound, so the cluster size is set by throughput, not storage.

What happens when a Redis Pub/Sub server is added to the cluster?

Some channels move to the new server per the consistent hash ring. WebSocket servers see the updated ring and must resubscribe those channels, causing a burst of resubscription requests and possibly a few missed updates. Consistent hashing limits how many move; doing it at the daily traffic low limits the damage.

How does the system know a friend has gone inactive?

Each location cache entry has a TTL. If a user stops sending updates, the entry expires and they are treated as inactive, so they no longer appear when friends initialize. The TTL also caps the cache's maximum memory.

Compare the Redis location cache with the Cassandra location history table.

Both hold user_id, lat, long, timestamp. The cache keeps only the latest point with a TTL for real-time lookups; Cassandra keeps every point permanently for analytics and machine learning, chosen because it handles heavy write loads well.

Why can Pub/Sub channels be pre-allocated for every user?

Channels that exist but have no activity consume no memory in Redis Pub/Sub. Pre-allocating avoids the complexity of creating a channel when a user comes online and notifying all interested WebSocket servers.
