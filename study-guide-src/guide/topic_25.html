Picture this

It is the last evening of the monthly tournament. Five million daily players are grinding out matches, and every win nudges someone up the ladder. Mary, currently sitting in position 361, finishes a game, taps "Leaderboard", and expects to see herself climb right now, not after a nightly batch job. Behind that single tap sits a hard question: how do you keep tens of millions of scores permanently sorted, let thousands of them change every second, and still answer "what is my exact rank?" in milliseconds?

1 Macro Structure & Dependency Map

From 10,000 feet, this system is a pipe that carries trusted wins into one always-sorted data structure, plus a few side tables that give names to the numbers. Read the map top-down: each hub is a decision the others lean on.

  • Trusted score ingestion — if scores can be forged, every rank downstream is meaningless
    • Game service validates the win, then calls the leaderboard service
      • POST /v1/scores takes user_id and points; only game servers may call it
    • Rejected alternative: client writes its own score
      • Open to man-in-the-middle; a player with a proxy edits their score
    • Optional message queue between game and leaderboard services
      • Only worth it if other services consume game results; not required here
  • Redis sorted set — the always-sorted core that makes rank queries cheap
    • Hash map (user_id → score) + skip list (scores in order)
      • Skip list = sorted linked list with multi-level express indexes
    • Four commands: ZADD, ZINCRBY, ZREVRANGE, ZREVRANK
      • O(log N) updates and rank; O(log N + M) range fetch
    • One key per monthly tournament, e.g. leaderboard_feb_2021
      • Old months move to historical storage
  • Supporting relational storage — turns user IDs into names and provides the rebuild source
    • MySQL user profile table (username, display name)
      • Cache the top 10 players' details; they are read constantly
    • MySQL game-result table (who won, when)
      • Used to reconstruct the leaderboard after an infrastructure failure
    • Redis replica + Redis persistence for crash safety
  • Scaling strategy — what happens when one Redis node is no longer enough
    • Range (fixed) partitioning by score — author's preference
      • user_id → shard mapping kept in application code (MySQL or a cache)
    • Hash partitioning via Redis Cluster
      • Top 10 needs scatter-gather; rank has no easy answer
    • NoSQL alternative (DynamoDB) with write sharding
      • Exact rank is hard; fall back to percentiles computed by a cron job
  • Hosting model — who runs the boxes
    • Self-managed: Redis + MySQL (+ optional profile cache)
    • Serverless: AWS API Gateway routing to AWS Lambda
      • Recommended by the author for a game built from the ground up

The sorted set is the gravitational center: the API shape, the storage estimate, the scaling debate and even the NoSQL comparison all orbit around "how do we keep scores sorted and rankable?" Trusted ingestion sits upstream because a fast leaderboard of fake scores is worthless. Relational storage and hosting are supporting cast: they name the players and keep the lights on, but they never answer a rank query themselves.

2 Black-Box Cause & Effect Flow

Treat each component as a sealed box: something goes in, something comes out. Two flows share the same core — the write path (a win becomes a score) and the read path (a tap becomes a ranked list).

Game client

Input: A finished match on the player's device.

Output: A "match finished" signal to the game service (or nothing at all, if the server runs the game logic itself).

The client is the witness, not the judge. It reports that something happened but never gets to write the verdict.

→ feeds into: Game service

Game service

Input: Match result from the client or from its own game logic.

Output: A validated POST /v1/scores call with user_id and points.

This is the referee who checks the scoreboard before announcing a winner. Because only game servers may hit the score API, a player with a proxy cannot inflate their own number.

→ feeds into: Leaderboard service

Leaderboard service

Input: Score updates from game servers; read requests (GET /v1/scores, GET /v1/scores/{user_id}) from players.

Output: ZINCRBY writes to Redis; JSON responses with user_id, user_name, rank and score.

A thin translator: it turns HTTP calls into sorted-set commands and stitches the returned IDs together with human-readable names.

→ feeds into: Redis sorted set (scores) and MySQL / cache (names)

Redis sorted set (leaderboard_<month>)

Input: ZINCRBY for wins; ZREVRANGE and ZREVRANK for reads.

Output: Updated score, ordered slices of (user, score), or a user's position.

A self-sorting shelf. Every time a book (player) gets thicker (more points), it slides into its correct slot automatically in O(log N) steps, so reading the top shelf is always instant.

→ feeds into: Leaderboard service response

MySQL tables + top-10 cache

Input: User IDs to resolve; win records to persist.

Output: Usernames and display names; a durable history of wins.

The filing cabinet next to the scoreboard: it knows who "mary1934" really is, and it keeps receipts so the board can be rebuilt if Redis burns down.

→ feeds into: Leaderboard response; recovery script after outages

Recovery path (MySQL WAL / game-result table)

Input: A large-scale Redis outage.

Output: A rebuilt sorted set, replayed by an ad-hoc script.

If the scoreboard is wiped, you replay every stored win in order and the board redraws itself.

→ feeds into: Redis sorted set

Follow one score update

  1. Mary (user_id mary1934) wins a match in February 2021. Her client tells the game service the match ended.
  2. The game service checks the win is legitimate, then calls POST /v1/scores with user_id=mary1934 and points=1.
  3. The leaderboard service runs ZINCRBY leaderboard_feb_2021 1 'mary1934'. If she had no entry, her score starts from zero and becomes 1; otherwise it grows by one. Cost: O(log N).
  4. The win is also recorded in MySQL, giving a durable trail the leaderboard can be reconstructed from later.
  5. Mary taps "Leaderboard". The service runs ZREVRANGE leaderboard_feb_2021 0 9 WITHSCORES and gets back the top 10 (user, score) pairs in descending order.
  6. The service resolves those 10 IDs to names — ideally from a cache, since the top 10 are the hottest profiles in the game.
  7. For Mary's own row, ZREVRANK returns her position, say 361.
  8. For the bonus "four above, four below" view, the service runs ZREVRANGE leaderboard_feb_2021 357 365 and returns her neighbourhood.
  9. At month's end a new key (leaderboard_mar_2021) starts fresh, and February's board moves to historical storage.

3 Purpose & Concept Beacons

A real-time leaderboard is fundamentally a "keep it sorted on every write" problem: pay a small O(log N) cost per update so that top-K and rank queries never have to scan or re-sort millions of rows.

Mental picture

Imagine a giant stadium scoreboard with an army of ushers. The referees on the field (game service) are the only people allowed to radio in a point; a fan shouting from the stands (the client) is ignored. The scoreboard itself (the Redis sorted set) is a magical ladder where every player's plaque slides to its correct rung the instant a point arrives, guided by express elevators that skip whole floors (the skip-list indexes). A clerk's office under the stands (MySQL) holds everyone's real name and the paper receipts for every point, so if lightning fries the board, the clerks can replay the receipts and rebuild it. When the stadium outgrows one board, you split it into sections by score range (range partitioning), so the VIP section with the top scores can still be read in one glance.

4 Opportunistic Drilling

Three ideas carry most of the interview weight: why the sorted set beats SQL, how to shard it when it outgrows one box, and what the NoSQL alternative gives up. Master those and the rest is detail.

Why a sorted set beats a relational table

In MySQL, a leaderboard is a table of (user_id, score). A win is an easy UPDATE ... SET score = score + 1, and the top 10 can be made tolerable with an index on score plus LIMIT 10. The trouble starts when Mary, deep in the middle of the pack, asks "what is my rank?" The relational answer is a nested query that counts every row with a score greater than or equal to hers — effectively a scan that grows with the player base.

The Redis sorted set sidesteps this by paying the sorting cost up front. It keeps two structures in lockstep: a hash map for "what is mary1934's score?" and a skip list that keeps everyone in score order. A skip list is a sorted linked list with extra "express lane" levels on top; searching starts on the fastest lane and drops down level by level, like taking an express train to the right neighbourhood and then walking the last block.

Common trap: Treating Redis as the only copy of truth. The notes pair it with a MySQL table of wins precisely so the board can be rebuilt (via the MySQL WAL and an ad-hoc script) after a large outage.

Sizing: why one Redis node is enough — until it is not

Start with the arithmetic. 5 million daily users spread over 24 hours is about 50 users per second on average; uneven traffic pushes peak online users to about 250 per second. Each player averages 10 matches a day, so score updates run at about 500 QPS, peaking at 2,500. Top-10 reads, assuming one look per user per day, are only about 50 QPS.

Storage is equally modest. Worst case, all 25 million monthly users play: a 24-character ID plus a 16-bit score is 26 bytes, so about 650 MB. Double it for skip-list overhead and it still fits comfortably. 2,500 writes per second is well within a single Redis server's capability.

The picture changes if the game explodes. At 500 million DAU the notes estimate 65 GB of storage and 250,000 QPS — now sharding is mandatory, and the interesting design debate begins.

Common trap: Jumping to sharding before doing the math. The strongest answer states that the baseline fits on one node, then explains exactly which growth figures force a change.

Sharding the leaderboard: range vs hash partitioning

With range (fixed) partitioning, each shard owns a band of scores — for example [900–1000] on one node, lower bands on others. The application keeps a user_id → shard mapping (in MySQL or a cache). The top 10 is simply the top of the highest band. A user's rank is their rank within their own shard plus the number of users in every higher shard, and that count is an O(1) lookup via the info keyspace command.

With hash partitioning via Redis Cluster, users are spread across nodes by a hash of their key (similar to, but not exactly, consistent hashing). Writes spread nicely, but every leaderboard read becomes a scatter-gather: ask every shard for its top 10, then merge in the application.

The author therefore leans toward fixed range partitions. Two operational tips round it out: give write-heavy Redis nodes twice the memory they need so snapshots have room, and use Redis-benchmark to make data-driven sizing decisions.

The NoSQL alternative and the percentile escape hatch

A NoSQL store optimized for heavy writes and for sorting within a partition — DynamoDB, Cassandra or MongoDB — is a valid alternative. The notes walk through DynamoDB. A first chess-leaderboard table works but cannot query by score, so score becomes the sort key. That creates a new problem: partitioning by month makes the current month a hotspot, hammered while older months sit idle.

The fix is write sharding: append a partition number, computed as user_id % num_partitions, to the key. Writes now spread out, but reads must scatter-gather across every sub-partition. That is the core tradeoff.

Gains

More partitions means higher write scalability, and a fully managed database with global secondary indexes for fields outside the primary key.

Costs

More partitions means reads must hit more of them to aggregate results, and exact rank becomes hard to compute. The right partition count needs benchmarking.

When exact rank is impractical at that scale, reframe the product: tell users their percentile. A cron job periodically analyses the score distribution (e.g. 10th percentile = score < 100, 90th percentile = score < 6500) and each user is placed in a bucket.

Common trap: Forgetting that write sharding and hash partitioning share the same weakness — scatter-gather reads that slow down as you add partitions.

Security, hosting and the finishing touches

The design rejects letting clients post their own scores because a player can put a proxy in the middle and rewrite the number. Only game servers call POST /v1/scores, and for server-run games the server records wins automatically. A message queue between game and leaderboard services is a reasonable extension only if other consumers need game results.

For hosting, you can run Redis and MySQL yourself, or put AWS API Gateway in front of AWS Lambda functions that run only when called and scale automatically. The author recommends the serverless route for a game built from scratch.

  1. Faster retrieval: cache user objects in a Redis hash (user_id → user object).
  2. Breaking ties: equal scores share a rank by default; to break ties, order by the last played game.
  3. Failure recovery: replay MySQL WAL entries with an ad-hoc script to rebuild the board.

Test yourself

Write your answer in the margin with your stylus first, then tap to reveal.

Why must the score update go through the game service instead of the client?

A client-side update is vulnerable to man-in-the-middle tampering: a player can proxy the request and set any score they like. Making POST /v1/scores callable only by game servers, which validate the win first, keeps the leaderboard trustworthy.

What two internal structures make up a Redis sorted set, and what does each contribute?

A hash map from user_id to score gives direct score lookups, and a skip list keeps members ordered by score. Together they allow O(log N) updates and rank lookups and O(log N + M) range fetches.

What happens to rank queries if you stay on MySQL as the player base grows?

Top 10 stays manageable with an index and LIMIT, but finding a mid-table user's rank requires a nested COUNT over all higher scores, which effectively scans the table. It does not scale to millions of players, which is why the design moves to Redis.

Compare range partitioning and hash partitioning for computing the top 10 and a user's rank.

Range partitioning puts the top 10 in the highest-score shard, and a rank is the local rank plus O(1) counts from higher shards. Hash partitioning requires scatter-gather across every shard for the top 10 and has no straightforward way to compute rank, and its latency grows with more partitions.

Why does partitioning a DynamoDB leaderboard by month cause trouble, and how is it fixed?

The current month receives almost all traffic, creating a hot partition. Write sharding appends user_id % num_partitions to the key to spread writes, at the cost of scatter-gather reads across those partitions.

If Redis suffers a large-scale outage, how do you get the leaderboard back?

Redis replicas and persistence reduce the risk, but the durable source is MySQL, which records each win. An ad-hoc script can replay the MySQL WAL entries to recreate the sorted set.

Why is a single Redis node enough at 5M DAU?

Peak writes are about 2,500 QPS and storage is about 650 MB (26 bytes × 25M users), still small even doubled for skip-list overhead. Both are well within one Redis server; sharding only becomes necessary at figures like 65 GB and 250k QPS.
