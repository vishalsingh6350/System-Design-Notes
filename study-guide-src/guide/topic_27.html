Picture this

A million times a second, someone taps "Send" to move money from their in-app wallet to a friend's. Account A lives on one database shard, account C on another, and no single machine can see both. For a split second, one dollar has left A but not yet arrived at C — and during that split second a server might crash. Months later an auditor asks, "What was A's balance at 3:14 pm on the 9th, and can you prove it?" The digital wallet has to be fast enough for 1 million TPS, atomic across machines, and able to replay its entire history on demand.

1 Macro Structure & Dependency Map

This chapter is an evolution story: each hub fixes the weakness of the one before it. Read the map top to bottom as a sequence of "yes, but..." moments.

  • Scale target & sharded balances — 1M TPS forces data across many nodes
    • Each transfer has two legs, so the real load is 2M TPS
      • ~1,000 TPS per cloud relational node; 10,000 TPS per node needs only 200 nodes
    • map<user_id, balance> partitioned by accountID.hashCode() % partitionNumber
      • Zookeeper stores partition count and Redis node addresses
    • Stateless wallet service scales horizontally
      • Weakness: in-memory Redis is not durable and cannot transfer atomically
  • Distributed transactions — making a two-shard transfer all-or-nothing
    • 2PC: prepare, then commit or abort
      • Lock contention; coordinator is a single point of failure
    • TC/C: Try reserves, then Confirm or Cancel via compensation
      • Phase status table, deduct-before-add, out-of-order flag
    • Saga: linear steps, roll back with compensating operations
      • Orchestration preferred over choreography
  • Event sourcing — reproducibility: replay history to prove every balance
    • Command → state machine validates → events → state
      • State machine must be deterministic: no external IO, no randomness
    • CQRS: one write state machine, many read-only state machines
  • High-performance, reliable event sourcing — making the event log fast and durable
    • Local disk appends + in-memory cache via mmap
      • State in RocksDB (LSM tree, write-optimized); snapshots to HDFS
    • Raft replicates the events list only
      • Runs while more than half of nodes are up
  • Distributed event sourcing — beyond one Raft group, and real-time responses
    • Reverse proxy sends commands and waits on the user's behalf
      • Read state machines push results instead of being polled
    • Shard into multiple Raft groups, coordinated by TC/C or Saga

Scale forces sharding; sharding breaks atomicity, which forces distributed transactions. Audit requirements force event sourcing, whose external storage is too slow, which forces local mmap/RocksDB, which makes nodes stateful, which forces Raft. Finally, one Raft group is not enough, so the design shards Raft groups and reuses the distributed-transaction hub on top — the story loops back on itself.

2 Black-Box Cause & Effect Flow

Here is the final architecture as sealed boxes, in the order a transfer touches them. Each box has one job; the coordinator and the event log carry the hard guarantees.

Reverse proxy

Input: POST /v1/wallet/balance_transfer with from_account, to_account, amount (as a string), currency, transaction_id.

Output: Commands forwarded into the system; a final response to the user when results are pushed back.

A concierge who takes your request, goes into the back office for you, and returns only when there is an answer — so you do not stand at the counter asking "is it done yet?"

→ feeds into: Saga / TC/C coordinator

Coordinator (Saga or TC/C) + phase status table

Input: A distributed transaction such as A-1 and C+1.

Output: Per-partition commands and a durable record of each phase's status.

The project manager with a checklist. It records every step before and after doing it, so if it crashes mid-flight it can read the checklist and resume.

→ feeds into: The Raft group owning each account

Raft leader's write state machine

Input: A command (e.g. A-1) from the command list, plus current balance state.

Output: Validated, immutable events appended to the event list; updated state.

The notary: it checks the request is legal (enough balance?), then writes an irreversible fact into the register.

→ feeds into: Raft followers, read state machines

Event list, replicated by Raft

Input: New events from the leader.

Output: The same ordered event list on a majority of nodes; state rebuilt on each node from it.

Carbon copies of the register kept in several vaults. As long as more than half the vaults survive, the history survives in the right order.

→ feeds into: State (RocksDB), snapshots, read state machines

Local storage: mmap + RocksDB + snapshots

Input: Commands and events (appends); state updates.

Output: Fast local persistence, cached recent data, and periodic snapshots in HDFS.

A notebook on the clerk's own desk instead of a filing room down the hall — with a bookmark (snapshot) so you never reread from page one.

→ feeds into: Fast replay and recovery

Read-only state machines (CQRS)

Input: The replicated event list.

Output: Query views of balances and history; pushed completion results to the coordinator/proxy.

Reporters who watch the register and answer questions about it, so the notary never has to stop writing to answer them.

→ feeds into: Coordinator, reverse proxy, user

Follow one transfer

  1. User A sends $1 to user C with transaction_id 01589980-2664-11ec-9621-0242ac130002 as the idempotency key. The reverse proxy forwards it as a distributed transaction with two operations: A-1 and C+1.
  2. The Saga coordinator writes a row in the phase status table so the transaction can be traced and resumed after a crash.
  3. It hashes each account to find its partition: A lives in Raft group 1, C in Raft group 2.
  4. Partition 1's Raft leader receives A-1, validates it against A's balance, converts it to an event and replicates the event to its followers.
  5. The event is applied to state and synchronized to the read state machine, which pushes a "done" response back to the coordinator.
  6. The coordinator records operation 1 as successful. For a moment A is $1 lighter and C has not yet gained it — the safe direction, since nobody can spend money that has not arrived.
  7. The coordinator sends C+1 to partition 2, which validates, logs, replicates and pushes back a response in the same way.
  8. The coordinator records operation 2 as successful and informs the client: "status": "success".
  9. Months later, an auditor replays the event lists from a snapshot and recomputes A's balance at any moment — getting the identical answer every time.

3 Purpose & Concept Beacons

The digital wallet moves balances between accounts at 1 million TPS with transactional guarantees and full reproducibility: shard for scale, compensate for atomicity, and treat an immutable, replicated event log as the single source of truth.

Mental picture

Picture a network of notary offices across a city, each responsible for a slice of residents (shards / Raft groups). Every office keeps a bound register in permanent ink — not a balance sheet, but a list of every change ever made (the event list), with carbon copies in neighbouring vaults (Raft replication). A transfer between two offices is handled by a courier with a clipboard (the Saga/TC/C coordinator and phase status table): first debit the sender's office, then credit the receiver's, and if the second fails, go back and refund the first (compensation). The office clerk must follow the rulebook exactly, with no guessing or phoning out (deterministic state machine), so anyone who rereads the register reaches the same balances. Reporters in the lobby (read-only state machines) answer customers' balance questions, and a concierge (reverse proxy) waits in line on your behalf.

4 Opportunistic Drilling

The payoff sections are the ones interviewers love to push on: how a cross-shard transfer stays correct (TC/C and Saga), why event sourcing proves correctness, and how that event log is made both fast and durable.

TC/C: the two-phase dance by compensation

2PC keeps one transaction open across databases, holding locks until every participant says yes — slow, and fragile if the coordinator dies. TC/C instead runs two independent local transactions. In the Try phase, the coordinator reserves resources; in phase two it either Confirms or Cancels. Because each phase commits on its own, undoing work means running a new, opposite transaction (compensation).

PhaseAccount AAccount C
1. TryBalance -$1NOP (do nothing)
2a. Confirm (all said yes)NOPBalance +$1
2b. Cancel (any Try failed)Balance +$1 (refund)NOP

Between phases the books are briefly unbalanced: $1 has left A but not reached C. That is acceptable only because the Try phase always does the deduction first. Crediting C first (choice 2) would let C spend money that might be cancelled, and doing both at once (choice 3) is impossible to make atomic across databases without 2PC.

  1. Coordinator crash: a phase status table, updated atomically in the shard databases, records transaction ID and content, Try status (not sent / sent / response received), second-phase name (confirm or cancel), its status, and an out-of-order flag.
  2. Out-of-order delivery: a database might receive Cancel before Try. It sets the out-of-order flag; when Try finally arrives it checks the flag and returns failure.
Common trap: Calling TC/C "just 2PC". In 2PC the first phase leaves transactions unfinished; in TC/C they are already committed or cancelled, and failure means reversing a committed transaction in business logic.

TC/C vs Saga: choosing the coordinator style

A Saga orders every operation in a line; each runs in its own database. If one fails, the process rolls back to the start with compensating operations. It can be coordinated by choreography (services react to each other's events) or orchestration (one coordinator directs everyone). Orchestration is preferred for wallets because choreography scatters business logic across services that talk asynchronously.

Event sourcing: history as the source of truth

Reconciliation can flag a discrepancy, but it cannot explain it. Auditors ask sharper questions: what was the balance at any given time, are historical and current balances correct, and does new code still produce the right answers? Event sourcing answers all three by storing every change instead of just the latest balance.

Four pieces work together. A command is an intention ("transfer $1 from A to C"), placed in a FIFO queue such as Kafka so there is a global order; it can fail and may involve randomness. The state machine validates the command against current state and, if valid, emits events — immutable facts, one per affected account — which are then applied to update balances.

Because the event list is immutable and the state machine is deterministic, replaying events always reproduces the same intermediate states. That gives balance-at-any-time (replay up to that point), correctness checks (recompute from scratch), and code verification (run old and new versions over the same events and compare). Client queries are served through CQRS: multiple read-only state machines build their own views from the event list.

Common trap: Letting the state machine call an external service or use randomness. The moment it does, replay stops being guaranteed to match, and the whole audit argument collapses.

Making the event log fast and durable

External Kafka and databases add network hops the 1M TPS target cannot afford. The deep dive moves commands and events to local disk (append-only writes are fast even on HDDs), caches recent ones in memory, and uses mmap to get both at once. State moves into RocksDB, whose LSM tree is optimized for writes, with caching for reads. Periodic snapshots written to HDFS mean replay starts from a recent checkpoint instead of from the beginning.

That speed makes each node stateful, so it must be replicated. The key insight is what to replicate: state and snapshots can be regenerated from events, and events cannot be regenerated from commands because commands are non-deterministic. So only the event list needs high reliability, with no data loss and identical ordering across replicas — exactly what Raft provides. One leader is active, followers are passive, a follower takes over if the leader dies, and the group keeps running while more than half its nodes are up.

Two limits remain. One Raft group has finite capacity, so data is sharded across groups and cross-group transfers use TC/C or Saga again. And CQRS clients would have to poll for results, which is slow and can overload query services — so a reverse proxy sends commands and waits on the user's behalf, and read-only state machines push responses to it, making updates feel real-time.

Common trap: Replicating commands or state instead of events. Commands cannot deterministically reproduce events, and state is derivable — the event list is the one thing you cannot lose.

Test yourself

Jot your answer in the margin with your stylus, then tap to check.

Why does the in-memory Redis sharding solution fall short even though it scales?

It spreads balances across nodes for throughput, but it cannot execute a transfer atomically across two nodes, and in-memory Redis is not durable storage. That pushes the design toward databases with distributed transactions.

In TC/C, why must the Try phase debit A rather than credit C?

During the in-flight window the accounts are unbalanced. If C were credited first, C could spend money that might later be cancelled. Deducting first means the inconsistency is only "missing" money that nobody can use, and a Cancel simply refunds A.

What happens if a shard receives Cancel before Try?

It records the out-of-order flag in the phase status table. When the delayed Try arrives, the shard checks the flag and returns a failure rather than executing it.

Compare TC/C and Saga. When would you pick each?

Both use compensation, central coordination (Saga in orchestration mode) and application-level logic, and both can expose partial inconsistency. TC/C can execute in any order and in parallel, so choose it for low latency; Saga executes linearly, which is simpler but slower.

Why must the event-sourcing state machine be deterministic?

Replaying the immutable event list must always produce the same states, otherwise historical balances and code-change verification cannot be trusted. External IO or randomness would break that guarantee.

Why does Raft replicate only the event list, not commands or state?

State and snapshots can always be rebuilt by replaying events. Commands are non-deterministic, so replaying them would not reliably regenerate the same events. The event list is therefore the only data that needs high reliability.

What problem does the reverse proxy with push-based read state machines solve?

In CQRS, clients would otherwise poll to learn when their transfer completed, which is not real-time and can overload query services. The proxy sends commands and waits on the user's behalf, and read state machines push results to it, so users see updates promptly.
