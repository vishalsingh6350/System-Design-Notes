Picture this

It is 9 p.m. on a Friday and a billion people are scrolling. Every few microseconds, somewhere on the planet, a thumb taps an ad, and each of those taps is a tiny invoice: an advertiser now owes money. Your job is to count those taps, per ad and per minute, while they pour in at up to 50,000 per second, arrive late, arrive twice, and hit machines that occasionally die mid-count. Miscount by even a fraction of a percent and someone is billed millions of dollars wrong. This is ad click event aggregation: a cash register for an unbounded river of events, where accuracy matters more than speed but a few minutes is the most you can be late.

1 Macro Structure & Dependency Map

From 10,000 feet this is a streaming pipeline: raw clicks in, per-minute counts out, with a safety net underneath. Read the map top to bottom: each hub is a problem that must be solved before the details beneath it make sense.

  • Decoupled streaming pipeline (Kafka → aggregation → Kafka → DB) — the skeleton; every other decision plugs into one of its stages
    • Message queue 1: raw click events (ad_id, click_timestamp, user_id, ip, country)
      • Enough partitions created up front; consumer rebalancing done off-peak
    • Message queue 2: per-minute counts and top-N lists
      • Exists so results and offsets can be committed atomically (exactly-once)
    • Storage: Cassandra for both raw and aggregated data
      • Raw data can move to cold storage; S3 + Parquet/ORC/AVRO was an alternative
  • Aggregation service as a MapReduce DAG — where counting actually happens, in memory, every minute
    • Map node: filter, sanitize, route by ad_id
    • Aggregate node: count per ad_id per minute; heap for top N
    • Reduce node: merge partial results into the final answer
      • Star schema: pre-aggregate by dimensions like country (filter_id)
  • Time & windows — you cannot count "per minute" until you decide whose clock defines the minute
    • Event time (chosen) vs processing time
    • Watermark: extend the window to catch stragglers
    • Tumbling window for counts, sliding window for top N in M minutes
      • Hopping and session windows exist but are not used
  • Correctness guarantees — the bill must be right, so duplicates and losses are not tolerated
    • Exactly-once delivery via atomic commit of offset + downstream write
    • Fault tolerance: Kafka offsets + periodic snapshots of in-memory state
    • End-of-day reconciliation batch job against raw data
      • Monitoring: latency, Kafka records-lag, CPU/disk/JVM
  • Scaling — 30% year-over-year growth and viral ads that attract a flood
    • Queue, aggregation service and DB scale independently
    • Hotspot handling: borrow extra nodes from the resource manager
      • Global-local aggregation, split distinct aggregation

The pipeline is the trunk: without the two queues there is nowhere to hang exactly-once, recovery or independent scaling. The aggregation DAG is the engine sitting on that trunk, and it cannot produce a number until the time hub defines what "this minute" means. The correctness hub then wraps the whole thing, because the output is money.

2 Black-Box Cause & Effect Flow

Treat each stage as a sealed box: know what goes in, what comes out, and why the next box depends on it. The internals come later.

Message queue 1 (raw clicks)

Input: An unbounded stream of click events, ~10,000/sec average, 50,000/sec peak, ~0.1 KB each.

Output: A durable, replayable log with offsets that consumers read at their own pace.

A giant conveyor belt with numbered slots. If a worker downstream faints, the belt keeps moving and nothing falls off; the worker picks up at its last slot number.

→ feeds into: raw data writer (Cassandra) and the aggregation service

Map node

Input: Raw events from the queue.

Output: Cleaned events, routed so every event for the same ad_id reaches the same aggregate node (e.g. ad_id % 3).

A mail sorter. It throws out junk and drops each letter in the pigeonhole for its ad, so no ad's clicks are split across counters.

→ feeds into: aggregate nodes

Aggregate node

Input: Events for its slice of ads, bucketed by event time into one-minute windows (plus a watermark).

Output: Per-minute counts per ad_id and a local top-N heap.

A tally clerk with a clicker for each ad, resetting every minute and keeping a short "leaderboard" of the busiest ads on the side.

→ feeds into: reduce node

Reduce node

Input: Partial counts and partial top-N lists from all aggregate nodes.

Output: Final per-minute counts and the global top N most clicked ads.

The head accountant who adds up every clerk's sheet. Each clerk's top 3 is merged into one true top 3.

→ feeds into: message queue 2

Message queue 2 + atomic commit

Input: Aggregated results plus the upstream consumer offset they came from.

Output: Results published and the offset committed together, or neither.

A sealed envelope: "these counts" and "I am done up to slot 100" are mailed as one package, so a crash can never send one without the other.

→ feeds into: aggregation database writer

Aggregation DB (Cassandra) + query API

Input: Rows like (ad001, 202101010000, filter 0012, count 2) and most_clicked_ads lists.

Output: Fast answers to GET /v1/ads/{ad_id}/aggregated_count and GET /v1/ads/popular_ads.

The scoreboard in the lobby. Nobody recounts clicks when they look at it; they read a number that was pre-computed a minute ago.

→ feeds into: dashboards, billing, RTB decisions, and the nightly reconciliation check

Follow one click

  1. At 2021-01-01 00:00:01, user1 in the USA (IP 207.148.22.22) taps ad001. An event with that event time is produced into message queue 1.
  2. Two consumers read it: the raw data writer stores the untouched row in Cassandra (for debugging and backfill), and the aggregation service picks it up at, say, offset 100.
  3. The map node checks the event is well-formed and routes it by ad_id, so it lands on the one aggregate node responsible for ad001.
  4. The aggregate node places it in the tumbling window for minute 202101010000 based on its event time, not the time it arrived. The window is held open a little longer (the watermark) in case stragglers from 00:00:59 show up late.
  5. When the window closes, the node emits "ad001, 202101010000, count 2" (user1 clicked twice) and updates its top-N heap.
  6. The reduce node merges this with other nodes' partial results and produces the final count and the global top 100 for that minute.
  7. The result is written to message queue 2 and offset 100 is committed in the same atomic step, so a crash cannot double-count or lose it.
  8. The database writer stores the row in the aggregation DB, including pre-aggregated filter rows such as filter_id 0012 (US clicks).
  9. An advertiser's dashboard calls GET /v1/ads/ad001/aggregated_count?from=...&to=...&filter=0012 and sees the number a few minutes after the tap. That night, reconciliation recounts from raw data and confirms it matches.

3 Purpose & Concept Beacons

Turn an infinite, messy stream of billable clicks into correct per-minute counts and top-N rankings within a few minutes, surviving late events, duplicates and crashes.

Mental picture

Imagine a vast vote-counting hall on election night. Ballots stream in through a mail chute that never closes (Kafka queue 1), and every ballot is also photocopied into an archive in the basement (raw data store). Sorters at the door route each ballot to the table for its candidate (map nodes), clerks tally each table minute by minute (aggregate nodes), and a head counter combines the tables and posts the leaderboard (reduce node) onto a public board (aggregation DB). The official results are only posted in sealed envelopes that also record which ballots were counted (atomic commit via queue 2). And at dawn an auditor recounts from the basement photocopies to prove the board was right (reconciliation).

4 Opportunistic Drilling

Interviewers probe where money can leak: duplicates, late clicks, crashes and hot ads. These four drills cover the questions most likely to decide the round.

Exactly-once: why the second queue exists

A duplicate can come from the client resending, or from a server outage: an aggregation node processes offset 100, sends its result downstream, then dies before acknowledging. The upstream thinks offset 100 was never handled and it is processed again. Now ad001 has been billed twice for one click.

The naive fix is to save "last seen offset" to HDFS/S3 before sending the result. But if the node dies after saving and before sending, the result never reaches downstream: you traded a duplicate for a loss. The only safe option is to make "send result" and "commit offset" a single atomic step, which is a distributed transaction. That is the job of the atomic commit around message queue 2.

ApproachFailure modeVerdict
Ack after sending resultCrash before ack → reprocess → duplicateAt-least-once; fine elsewhere, not for billing
Save offset first, then sendCrash between the two → result lostAt-most-once; unacceptable
Atomic offset + send (distributed transaction)None of the aboveExactly-once; chosen
Common trap: Saying "Kafka gives us exactly-once" and stopping. The guarantee must cover the whole path to the downstream sink. As the notes point out, if the downstream writes are idempotent you can skip the distributed transaction entirely.

Time, watermarks and windows

Because of queues and network delays, the moment a click happened (event time) can be far from the moment a server sees it (processing time). Processing time is reliable but mis-buckets late clicks; event time is accurate but can be wrong or malicious on the client. Since billing needs accuracy, the design uses event time and then fights the lateness problem.

The weapon is the watermark. Picture a train that officially departs at 00:01 but holds its doors open for a few extra seconds so running passengers can jump on. Those extra seconds are the watermark. A short one lets the train leave on time but strands more passengers; a long one catches almost everyone but delays the whole schedule.

No watermark catches everything, and chasing the last rare straggler is not worth the latency. Those leftovers are fixed by end-of-day reconciliation. For the windows themselves: a tumbling (fixed, non-overlapping) window drives the per-minute counts, and a sliding window drives "top N in the last M minutes".

Gains

Event time + watermark puts clicks in the minute they really happened, which is what advertisers pay for.

Costs

Every window closes later than real time, and a small tail of very late events still needs a batch correction.

The MapReduce DAG, scaling and hotspots

Inside the aggregation service each node does one job and passes results downstream over TCP or shared memory, with intermediate data kept in memory. Map routes by ad_id, aggregate counts per minute, reduce merges. For top N, every aggregate node keeps a heap of its local leaders and the reduce node merges those heaps, which is why "top 3" extends easily to "top 100".

Why have a map node at all, instead of letting Kafka partition by ad_id? Because you may not control how producers partition data, so clicks for one ad can land on different partitions, and the map step also lets you sanitize data first.

The three big pieces (queue, aggregation service, DB) are decoupled, so each scales on its own: more partitions and consumers for Kafka (possibly topics by region like topic_na, topic_eu), more nodes or multi-processing via Apache YARN for aggregation, and Cassandra's consistent hashing for the DB, which rebalances automatically when nodes join.

Common trap: Forgetting that consumer rebalancing across thousands of consumers is slow. Pre-create enough partitions and scale consumers off-peak.

Surviving crashes and proving the numbers

Aggregate nodes count in memory, so a crash wipes the tally. Kafka offsets tell a replacement node where to resume reading, but they do not restore the half-finished "top N in M minutes" state. So nodes periodically snapshot that state; recovery reads the latest snapshot plus the latest committed offset and replays only the events after it.

  1. Node takes snapshots of its ongoing aggregation at a given minute.
  2. Node dies; a new node is assigned its partitions.
  3. New node loads the last snapshot and last committed offset.
  4. It replays events from that offset forward and continues as if nothing happened.

Two more safety nets sit on top. If the aggregation logic itself had a bug, a recalculation service reads raw data in batch and feeds it to a dedicated aggregation service (so live traffic is untouched), then writes through queue 2. That reuse of the same stream engine is what makes this Kappa rather than Lambda. And every night, reconciliation recomputes from raw data and compares against the aggregation DB.

Test yourself

Write your answer in the margin with your stylus, then tap to reveal.

Why keep raw click data if queries only ever read aggregated data?

Aggregated data is derived and loses information. Raw data lets you debug, recalculate after a logic bug (backfill), and run end-of-day reconciliation. It can sit in cold storage to keep costs down.

What happens if an aggregation node saves its offset before sending results, then crashes in between?

On restart the offset says the events were handled, so they are skipped, but the results never reached downstream. The clicks are lost. That is why offset commit and output must be atomic.

Compare event time and processing time for this system.

Event time is more accurate but client clocks can be wrong or malicious, and late events must be handled. Processing time is reliable but places late events in the wrong minute. Accuracy drives billing, so event time plus watermarks is chosen.

What happens if you make the watermark very long?

Fewer events are missed, but every window closes later, raising end-to-end latency. Since some events will always be late, it is better to keep the watermark moderate and rely on reconciliation.

Why is at-least-once delivery not good enough here, when it is fine for most systems?

The counts are used for billing and RTB. A small percentage of duplicates can mean millions of dollars of discrepancy, so exactly-once is required.

Lambda vs Kappa: which does this design use and why?

Kappa. Historical recalculation goes through the same stream aggregation engine rather than a separate batch codebase, avoiding Lambda's two processing paths to maintain.

How does a replacement node recover the top-N state of a crashed node?

It loads the latest snapshot of the in-memory aggregation and the latest committed Kafka offset, then replays events from that offset forward.
