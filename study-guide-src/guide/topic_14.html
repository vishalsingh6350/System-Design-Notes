Picture this

A creator finishes editing a 300 MB clip on a train and taps "Upload" on a patchy mobile connection. Minutes later someone on a smart TV across the world presses play and it starts instantly, crisp in HD, then quietly drops to a lower resolution when their Wi-Fi stutters, without buffering. Between those two moments the raw file was chopped up, inspected, re-encoded into many resolutions and formats, thumbnailed, watermarked and pushed to edge servers near every viewer. Do that for millions of daily users, adding 150 TB of new video a day, while CDN bills alone run around $150,000 a day, and you see why the hard problems here are heavy processing and heavy bandwidth.

1 Macro Structure & Dependency Map

YouTube is two pipelines joined by storage: an upload pipeline that turns one raw file into many streamable versions, and a streaming pipeline that serves those versions from the CDN. Read the map top-down: flows first, the transcoding engine second, the optimisations last.

  • Video Upload Flow — everything starts with getting the raw file and its metadata in safely
    • Two parallel paths: file → original storage, metadata → API servers → metadata DB
    • Completion queue + completion handler update metadata and inform the user
    • Upload hardening
      • Pre-signed URLs for authorised uploads
      • Chunked, resumable parallel uploads; CDNs as upload centres
  • Video Transcoding (DAG engine) — the expensive heart that makes one upload playable everywhere
    • Why: smaller storage, device compatibility, quality that adapts to network
      • Container (MP4, AVI) vs codec (H.264, VP9)
    • Preprocessor → DAG scheduler → resource manager → task workers
    • Temporary storage for retries
      • GOP (Group of Pictures) splitting
  • Video Streaming Flow — the part viewers actually feel; must be fast and cheap
    • CDN edge servers stream directly to clients
    • Streaming protocols
      • MPEG-DASH, Apple HLS, Adobe HDS
  • Optimisations & Error Handling — the levers for speed, safety and the huge CDN bill
    • Speed: parallel uploads, message queues between modules
    • Safety: pre-signed URLs, DRM, AES encryption, watermarking
    • Cost: CDN only for popular videos, on-demand encoding, regional distribution
      • Custom CDNs and ISP partnerships
    • Recoverable errors retry; non-recoverable errors stop with an error code

Upload feeds transcoding; transcoding feeds transcoded storage and the CDN; the CDN feeds streaming. The optimisations are not a separate system but dials on each of those three hubs. The transcoding engine is the deepest hub because it decides how fast a video becomes watchable and how much compute it burns.

2 Black-Box Cause & Effect Flow

Follow the file as it moves from the creator's phone to the viewer's screen. Each box transforms it in one specific way.

API Servers (upload gatekeeper)

Input: A POST /upload request plus video metadata (file name, size, format).

Output: A pre-signed URL for the client, and a metadata record saved in the metadata DB.

A front desk that checks your ID and hands you a one-time key to the storage room, instead of carrying your luggage itself.

→ feeds into: client uploads directly to Original Storage

Original Storage (blob)

Input: The raw video, often in parallel chunks.

Output: A durable raw copy ready for processing.

The loading dock where unprocessed crates are stacked before the factory opens them.

→ feeds into: Transcoding servers

Preprocessor + DAG Scheduler

Input: Raw video and configuration files written by client programmers.

Output: GOP-aligned chunks cached in temporary storage, and a DAG split into stages of tasks.

The planner who cuts the job into pieces and writes the recipe: split into video, audio, metadata first, then encode and thumbnail.

→ feeds into: Resource Manager's task queue

Resource Manager + Task Workers

Input: Prioritised tasks and worker-utilisation info.

Output: Each task executed on the best available worker; encoded video assembled.

A dispatcher matching jobs to free, capable hands, then tracking who is doing what.

→ feeds into: Transcoded Storage and the Completion Queue (in parallel)

Transcoded Storage → CDN

Input: Encoded versions of the video in multiple resolutions and formats.

Output: Copies distributed to CDN edge servers close to viewers.

The finished goods warehouse ships stock to corner shops in every neighbourhood.

→ feeds into: streaming to clients

Completion Queue + Completion Handler

Input: Transcoding-complete events.

Output: Updated metadata (video is ready) and a notification to the creator.

The bell that rings when the order is done, so the front desk can update the ticket and call the customer.

→ feeds into: Metadata DB / cache; user sees "ready"

CDN Edge Streaming

Input: A viewer's play request.

Output: A stream in a protocol such as MPEG-DASH or Apple HLS, at a quality suited to their device and network.

The corner shop hands you the video immediately; nobody drives to the central warehouse.

→ feeds into: the viewer's player

Follow one upload

  1. The creator's app sends POST /upload to the API servers. In parallel it sends metadata: file name, size (300 MB), format.
  2. API servers authorise the user, store the metadata, and return a pre-signed URL granting temporary permission to write to original storage.
  3. The client splits the 300 MB file into smaller chunks and uploads them in parallel to the nearest upload centre (a CDN edge acting as an upload hub). If the train enters a tunnel, only the missing chunks are resent.
  4. Once the raw video lands in original storage, the preprocessor splits it by GOP alignment, builds the DAG from configuration files, and caches the GOPs and metadata in temporary storage.
  5. The DAG scheduler emits stage 1 (split into video, audio, metadata) and then stage 2 (video encoding and thumbnail, alongside audio encoding) into the task queue.
  6. The resource manager's task scheduler pops the highest-priority task, picks the best worker from the worker queue, records the pair in the running queue, and dispatches. An encoding worker fails halfway? The task is retried from the data in temporary storage.
  7. Encoded outputs are assembled. In parallel, they go to transcoded storage (then out to the CDN) and a completion event goes to the completion queue.
  8. The completion handler marks the video ready in the metadata DB and notifies the creator.
  9. A viewer on a smart TV presses play; the nearest CDN edge streams it, switching resolution if the network weakens.

3 Purpose & Concept Beacons

The design turns one raw upload into many device-ready versions through a parallel, retryable DAG pipeline, then serves them from the edge while aggressively controlling bandwidth cost.

Mental picture

Think of a film-processing factory with a network of corner kiosks. The front desk (API servers) issues you a stamped pass (pre-signed URL) so you can drop your reels straight at the loading dock (original storage). Inside, a planner (preprocessor and DAG scheduler) cuts the reel into short segments (GOPs) and writes a recipe of steps that can run side by side. A dispatcher (resource manager) assigns each step to the best free technician (task workers), keeping spare copies in a back room (temporary storage) in case someone spills chemicals. Finished prints go to a warehouse (transcoded storage) and then out to kiosks on every street (CDN edges), while a bell (completion queue) tells the front desk the order is ready.

4 Opportunistic Drilling

Interviewers probe three things: the upload flow's parallel paths, the DAG transcoding architecture, and how you tame the CDN bill. Master those and the rest is vocabulary.

The upload flow: two parallel paths and a completion bell

Uploading is really two things happening at once. The heavy path pushes the video bytes into original storage. The light path sends metadata (file name, size, format) to the API servers, which write it to the metadata database. Separating them means the metadata record exists even while hundreds of megabytes are still in flight.

After the file lands, transcoding servers produce the encoded versions. Then two things happen in parallel again: the encoded files go to transcoded storage and on to the CDN (3a, 3a.1), and a completion event is placed on the completion queue so completion handlers can update metadata and tell the user (3b, 3b.1). The queue means a slow metadata update never holds up distribution, and vice versa.

Common trap: routing video bytes through the API servers. The API servers only hand out pre-signed URLs and handle metadata; bytes go straight to blob storage.

Transcoding as a DAG: split, parallelise, assemble

Transcoding is computationally expensive and slow if done as one long job. The DAG model breaks it into tasks with explicit dependencies. First the original video is split into video, audio and metadata. The video branch fans out into tasks such as inspection, video transcoding (resolutions, codecs, bitrates), thumbnail generation (user-supplied or automatic) and watermarking (an identifying overlay). The audio branch goes through audio encoding. Finally everything is assembled.

Because the graph is acyclic and the branches are independent, many tasks run simultaneously. Different creators can also get different DAGs, because the preprocessor builds the graph from configuration files that client programmers write.

Gains

High parallelism, flexible per-video pipelines, and each task can fail and retry independently.

Costs

Needs orchestration: a scheduler to stage tasks, a resource manager to place them, and temporary storage to hold intermediate results.

Inside the transcoding architecture

Five components turn the DAG into running work. Think of them as planner, foreman, dispatcher, crew and safety locker.

  1. Preprocessor: splits video into GOP-aligned chunks (also for old clients), generates the DAG from config files, and caches GOPs and metadata in temporary storage for retries.
  2. DAG scheduler: splits the graph into stages (stage 1: video, audio, metadata; stage 2: video encoding and thumbnail) and pushes tasks into the resource manager's task queue.
  3. Resource manager: holds a task queue (priority queue of tasks), a worker queue (priority queue of worker utilisation), and a running queue (current task/worker pairs). Its task scheduler picks the optimal task and worker and instructs the worker.
  4. Task workers: execute the work; different workers may specialise in different tasks.
  5. Temporary storage: holds intermediate data; the store type depends on data type, size, access frequency and lifespan.
Common trap: describing the resource manager as "a queue". It is three queues plus a scheduler; the worker queue is what lets it pick the least-loaded capable worker.

Speed, safety and the $150,000-a-day bill

Speed comes from parallelism everywhere. Uploads are split into chunks by GOP so they are faster and resumable; CDNs serve as distributed upload centres near users; and message queues sit between modules so, for example, encoding does not wait for downloading to finish before it can take the next job.

Safety uses pre-signed URLs so only authorised users can upload, and protects content with DRM (Apple FairPlay, Google Widevine), AES encryption and visual watermarking.

Test yourself

Sketch or jot your answer in the margin first, then tap to check.

Why is transcoding necessary at all?

Raw video is huge, so encoding reduces storage. Different devices and browsers support different formats, so multiple encodings ensure compatibility. And multiple resolutions and bitrates let playback adapt to the viewer's network.

What does a pre-signed URL solve, and who issues it?

The API servers issue it after a POST /upload. It gives the client time-limited permission to upload straight to original storage, so only authorised users can write, and the video bytes never pass through the API servers.

What happens if a task worker crashes midway through encoding?

It is a recoverable error, so the task is retried. The preprocessor and workers persisted GOPs and intermediate data in temporary storage, so the retry resumes from that data instead of reprocessing the whole upload.

Compare the task queue, worker queue and running queue.

The task queue is a priority queue of work waiting to run. The worker queue is a priority queue of worker utilisation, used to pick the best worker. The running queue records which tasks are currently executing on which workers.

Why put a completion queue between transcoding and metadata updates?

It decouples the two: transcoded files can flow to storage and the CDN in parallel while completion handlers update metadata and notify users at their own pace. A slow or failed handler does not block distribution.

The CDN bill is too high. Name three changes from the notes.

Serve only popular videos via the CDN and the rest from high-capacity servers; encode rarely watched videos on demand; distribute regionally by popularity. Longer term, build a custom CDN and partner with ISPs.

How does chunked upload help the creator on a patchy connection?

The video is split (by GOP) into smaller chunks uploaded in parallel, which is faster, and if the connection drops only the unfinished chunks need resending, making the upload resumable.
