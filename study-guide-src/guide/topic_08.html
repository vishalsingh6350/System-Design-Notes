Picture this

Someone pastes a monstrous Amazon product link — a tangle of /dp/, tracking parameters and referral codes — and gets back tinyurl.com/qtj5opu. Minutes later that tiny link is in a million tweets, and every tap has to bounce instantly to the right page. Now multiply: 100 million new short links every day, kept alive for 10 years, with ten clicks for every link created. The job looks like a toy, but it is really a high-volume dictionary that must mint unique seven-character keys forever and answer lookups at lightning speed.

1 Macro Structure & Dependency Map

Two verbs drive the whole system: shorten (write) and redirect (read). Everything else either creates the short key, stores the mapping, or serves it fast. Read the hubs as layers from the outside in.

  • Requirements & scale — the numbers that size every other decision
    • 100 million URLs generated per day, supported for 10 years
      • 365 billion records, about 365 TB
    • 10:1 read-to-write ratio: reads dominate
    • Short URLs unique and as short as possible
  • API & redirect semantics — the contract with the outside world
    • POST api/v1/data/shorten with {longUrl} → shortURL
    • GET api/v1/shortUrl → longURL for redirection
    • 301 (permanent, browser caches) vs 302 (temporary, good for analytics)
  • Short-key generation — the heart of the design: turning a long URL into 7 characters
    • Base 62 conversion of a unique ID
      • Characters [0-9, a-z, A-Z]; 7 chars ≈ 3.5 trillion URLs
    • Hash (CRC32, MD5, SHA-1) + collision resolution
      • Take first 7 characters; append a predefined string on collision; Bloom filter to check existence
  • Storage & serving — keeping 365 billion mappings and returning them quickly
    • Relational table: id, shortURL, longURL
    • Cache in front of the database on the redirect path
    • Scaling: stateless web tier; DB replication and sharding
      • Rate limiter per IP; analytics on clicks, source, timestamps

The requirements tell you the key must be about seven characters and the read path must be heavily optimised. Key generation is the central decision because it determines whether you need a unique ID generator (from the previous chapter) and whether collisions exist at all. Storage and caching then follow directly from the 10:1 read ratio.

2 Black-Box Cause & Effect Flow

Two pipelines share one table. The shortening pipeline writes a mapping once; the redirecting pipeline reads it many times. Trace the boxes in order.

Shorten API (POST)

Input: {longUrl: longURLString}.

Output: a request to find or create a short key.

The front counter where you hand over your unwieldy address and wait for a claim ticket.

→ feeds into: duplicate check

Duplicate check

Input: the longURL.

Output: the existing shortURL if found; otherwise a signal to create a new one.

Before printing a new ticket, the clerk checks whether this exact address already has one, so the same long URL is not stored twice.

→ feeds into: ID generator (if new)

Distributed unique ID generator

Input: a request for a fresh ID.

Output: a globally unique number, e.g. 2009215674938.

The ticket roll. Because every number is unique, everything derived from it is unique too — no collisions to resolve.

→ feeds into: Base 62 encoder

Base 62 encoder

Input: the numeric ID.

Output: a compact string such as zn9edcu.

Rewrites a long decimal number using 62 symbols instead of 10, so it shrinks to a handful of characters — like writing a big number in a denser alphabet.

→ feeds into: database write

Relational database

Input: the row <id, shortURL, longURL>.

Output: a durable mapping, replicated and sharded for scale.

The master ledger of every claim ticket ever issued: 365 billion lines over 10 years.

→ feeds into: the cache and the redirect path

Redirect path (cache → DB → 301/302)

Input: GET on a shortURL.

Output: an HTTP redirect whose location header is the longURL.

The valet: hand over the ticket, the valet checks the nearby rack (cache) first, walks to the back lot (database) only if needed, then points you to your car.

→ feeds into: the user's browser landing on the long URL

Follow one click

  1. Earlier, someone POSTed https://en.wikipedia.org/wiki/Systems_design to api/v1/data/shorten. It was not in the database, so the ID generator issued 2009215674938.
  2. Base 62 turned that ID into zn9edcu, and the row <2009215674938, zn9edcu, https://en.wikipedia.org/wiki/Systems_design> was saved.
  3. Now a reader taps https://tinyurl.com/zn9edcu. The browser sends a GET to the load balancer.
  4. The load balancer forwards it to one of many stateless web servers.
  5. The web server looks up zn9edcu in the cache. On a hit, it has the long URL immediately.
  6. On a miss, it queries the database for the <shortURL, longURL> mapping (and can populate the cache for next time).
  7. The server responds with a redirect whose location is the Wikipedia URL — 301 if you want browsers to cache it, 302 if you want every click to come back for analytics.
  8. The browser follows the redirect and the reader lands on the article.

3 Purpose & Concept Beacons

Map each long URL to a unique, as-short-as-possible key and serve a flood of redirects quickly, sized for 100 million new URLs a day over 10 years with reads outnumbering writes ten to one.

Mental picture

Picture a giant coat check at a stadium. When you hand over a bulky coat (the long URL), the attendant takes the next number off a never-repeating ticket roll (the unique ID generator) and writes it in a compact code (Base 62), then records coat and code in the master ledger (the relational database). When you return with your ticket (the short URL click), the attendant first glances at the rack right behind the counter where popular coats hang (the cache) before trekking to the back rooms (the database). Hand over a "permanent" slip (301) and you will never need to visit the counter again for that coat; hand over a "temporary" slip (302) and you come back every time, which lets the manager count visits (analytics).

4 Opportunistic Drilling

The key-generation decision, the 301-vs-302 choice, and the two flows are where almost every interview question on this topic lands. The rest (rate limiting, analytics) is worth a sentence each.

Base 62 vs hash + collision resolution

Both approaches aim for a seven-character key. Base 62 starts from a unique numeric ID and simply rewrites it with 62 symbols. Because the input ID is unique, the output string is unique — collisions are impossible by construction. The price is that you need a distributed unique ID generator, and the length is not fixed: it grows as IDs grow.

Hashing starts from the long URL itself. Run it through CRC32, MD5 or SHA-1 and keep the first seven characters. That gives a fixed length and no dependency on an ID generator, but truncating a hash invites collisions: two different URLs can share the same first seven characters.

AspectHash + collision resolutionBase 62 conversion
Short URL lengthFixedNot fixed; grows with the ID
Needs unique ID generatorNoYes
CollisionsPossible; must be resolvedNot possible
Next short URL guessableNo; not based on an IDYes if IDs increment by 1 (security concern)
Common trap: forgetting that Base 62's sequential IDs make short URLs enumerable. If the ID goes up by 1, anyone can guess the next link — mention this as a security concern.

301 vs 302: load versus insight

A 301 says the short URL has permanently moved to the long URL. The browser caches that answer, so the next time the same user clicks, the browser goes straight to the destination without asking your service. Great for reducing load.

A 302 says the move is temporary, so the browser checks back every time. More traffic hits your servers, but you see every click — exactly what you want for analytics like click rates, sources and timestamps.

301 gains

Browser caching cuts repeat requests to your service, lowering load.

301 costs

Repeat clicks bypass you, so you cannot track them; choose 302 when analytics matter.

The shortening flow, step by step

The write path is a short decision tree. The first branch prevents duplicates; the second creates a new, collision-free key using the previous chapter's ID generator.

  1. Receive the longURL.
  2. Check whether it already exists in the database.
  3. If it does, return the existing shortURL.
  4. If not, generate a new unique ID with the distributed ID generator.
  5. Convert the ID to a shortURL with Base 62.
  6. Save <id, shortURL, longURL> in the database.

The redirect flow and scaling it

Because reads outnumber writes ten to one, the redirect path is where performance is won. The request passes through a load balancer to a stateless web server, which checks the cache first and falls back to the database only on a miss, then returns the long URL.

Scaling follows the usual pattern. Web servers hold no state, so you add or remove them freely. The database tier uses replication for availability and sharding to split 365 TB across machines. A rate limiter caps requests per IP to stop abuse, and click analytics (rates, sources, timestamps) feed business insight.

Test yourself

Scribble your answer beside each question before tapping to reveal.

Why are seven Base 62 characters enough for this system?

62^7 is about 3.5 trillion possible keys, while the system needs about 365 billion URLs over 10 years (100 million a day). Seven characters leave plenty of headroom.

When would you choose a 302 redirect instead of a 301?

When you need analytics such as click tracking. A 302 is temporary, so every click comes back to your service; a 301 is cached by the browser, so repeat clicks bypass you.

Compare Base 62 conversion with hash + collision resolution on collisions and dependencies.

Base 62 cannot collide because it encodes a unique ID, but it requires a unique ID generator and its length grows with the ID. Hashing needs no ID generator and has a fixed length, but truncating to seven characters causes collisions that must be resolved.

What happens if the same long URL is submitted twice?

The shortening flow first checks whether the longURL exists in the database. If it does, the existing shortURL is returned and no new ID is generated.

Why is resolving hash collisions by appending a predefined string expensive, and what helps?

Each retry requires checking whether the new short URL already exists, potentially a database query per attempt, and it may loop several times. A Bloom filter makes these existence checks fast.

What security concern does Base 62 introduce, and why?

If IDs increment by 1, the next short URL is easy to predict, so links can be enumerated. Hash-based keys do not have this property because they do not depend on a sequential ID.

Why does the redirect path check the cache before the database?

Reads outnumber writes 10:1, so most traffic is redirects. Serving popular mappings from the cache is faster and shields the database from the bulk of the load.
