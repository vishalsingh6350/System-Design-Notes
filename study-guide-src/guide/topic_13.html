Picture this

You type two letters, t and w, and before your finger has even left the glass a neat list slides down: twitter, twitch, twilight, twin peak, twitch prime. It feels like the search box read your mind. Behind that list is a promise to answer in under 100 ms, for 10 million people a day, at peaks of 48,000 requests every second, where every single keystroke is a fresh request. The hard part is not finding matching words; it is finding the five most popular ones, instantly, while the world keeps searching and the popularity scores keep shifting underneath you.

1 Macro Structure & Dependency Map

At 10,000 feet the system is two rivers that never cross in real time: a slow river that learns what people search (data gathering) and a fast river that answers keystrokes (query service). A trie sits in the middle as the shared artifact they both depend on.

  • The Trie (prefix tree) — the single data structure the whole design is built to create, store, shard and read
    • Nodes = prefixes, each storing query popularity
      • Compact storage: shared prefixes stored once
    • Top-k cached at every node
      • Cap prefix length (e.g. 50 chars)
  • Query Service — the hot path; every keystroke lands here and must return 5 results in <100 ms
    • Prefix lookup → read cached top-k → respond
    • Client-side speedups
      • AJAX (lightweight async requests)
      • Browser caching of results
    • Filter layer
      • Strips hate speech etc.; physical delete happens later, asynchronously
  • Data Gathering Pipeline — the offline factory that turns raw searches into a fresh trie
    • Analytics logs (append-only, unindexed)
    • Aggregators → frequency table
      • Weekly for most apps; shorter windows for Twitter-like real-time needs
    • Workers rebuild the trie asynchronously
  • Trie Storage & Scaling — where the built trie lives and how it is split when one machine is not enough
    • Trie Cache (distributed, in memory) in front of Trie DB
    • Trie DB options
      • Document store (MongoDB snapshot of serialized trie)
      • Key-value store: prefix → node data
    • Sharding by prefix range + shard map manager
      • Unicode and country-specific tries; trending-query weighting

The trie is the hub because every other box either produces it (gathering pipeline), stores it (cache, DB, shards) or reads it (query service). The key architectural insight is the split: writes are batched and slow, reads are cached and instant. If you remember only one thing, remember that the trie is rebuilt offline, not edited live.

2 Black-Box Cause & Effect Flow

Treat each component as a sealed box: what goes in, what comes out. Read the first four boxes as the weekly factory line, and the last three as the per-keystroke fast lane.

Analytics Logs

Input: Every raw query users submit, with a timestamp.

Output: An append-only, unindexed stream of query records.

A giant receipt roll: it only ever gets longer, nobody sorts it, and it is cheap to write because nothing is looked up.

→ feeds into: Aggregators

Aggregators

Input: A window of raw log records (usually a week; shorter for real-time products like Twitter).

Output: A frequency table: query → how many times it was searched.

The tally clerk who reads the receipt roll and writes "best: 35, bet: 29, bee: 20" on a clean ledger.

→ feeds into: Workers

Workers

Input: The aggregated frequency table.

Output: A freshly built trie, with top-k lists cached at every node, written to Trie DB.

Asynchronous builders who construct next week's trie in the back room while the old one keeps serving customers.

→ feeds into: Trie DB and Trie Cache

Trie DB + Trie Cache

Input: The built trie (as a MongoDB snapshot, or as prefix → node key-value pairs).

Output: Fast in-memory reads from the distributed cache, backed by durable storage.

The DB is the warehouse; the cache is the shop shelf holding everything customers reach for.

→ feeds into: Query Service

Shard Map Manager

Input: A prefix, e.g. "tw".

Output: The identity of the server that owns that prefix range.

A receptionist with a floor plan: "Words starting with t? Third floor, room n-z."

→ feeds into: the correct Query Service shard

Query Service

Input: The prefix the user has typed so far.

Output: Up to 5 suggestions sorted by popularity, after the filter layer removes unwanted ones.

Walks to the prefix node and simply reads the pre-written top-5 list pinned to it; no searching, no sorting.

→ feeds into: the browser dropdown (and browser cache)

Follow one keystroke

  1. You have already typed "b" and now add "e". The browser fires a lightweight AJAX request for prefix "be" without reloading anything.
  2. The browser first checks its own cache. If you searched "be" earlier today, the answer is already on your device and no network trip happens at all.
  3. Cache miss: the request reaches the backend, where the shard map manager sees the prefix begins with "b" and routes it to the server owning the a-m range.
  4. That server looks up prefix "be" in the Trie Cache (in memory). In a key-value layout this is a single hash lookup: key "be" → node data.
  5. The node for "be" already carries its cached top-k list: best: 35, bet: 29, bee: 20, be: 15, beer: 10. No subtree walk, no sort.
  6. The filter layer scans the five results against its rules and drops anything harmful before it leaves the building.
  7. The list returns to your browser, is rendered in the dropdown, and is saved in the browser cache for next time. Total budget: under 100 ms.
  8. Meanwhile your finished search is appended to the analytics log. It will not change any suggestion until the next aggregation and trie rebuild.

3 Purpose & Concept Beacons

Autocomplete trades freshness for speed: it precomputes the answer for every possible prefix once a week so that each keystroke becomes a lookup rather than a search.

Mental picture

Imagine a library of signposts arranged as a branching road. Each fork in the road is a letter, so walking t → w puts you at the "tw" fork: that is a trie node. Nailed to every fork is a small board listing the five most-visited destinations beyond it: that board is the cached top-k list. Once a week a survey crew counts foot traffic from the visitor logbook (analytics logs and aggregators) and repaints every board overnight (workers rebuilding the trie). Travellers never wait for a survey; they just read the board where they stand (query service reading the cache).

4 Opportunistic Drilling

Three ideas carry most of the marks: how the trie answers in constant-ish time, why data gathering is batched instead of live, and how storage and sharding keep it all in memory. Drill these; skim the rest.

The trie and the cached top-k trick

A plain trie answers "what are the top 5 for prefix be?" in three steps: find the prefix node, traverse its entire subtree collecting every complete query, then sort those by frequency and keep the top k. The first step is fast. The second and third are the problem: a popular prefix like "b" may have millions of descendants, and you would be walking and sorting them on every keystroke.

The fix is to do that work once, at build time, and pin the answer to the node. Every node stores its own top-k list. Now a query is: find the node, read its list, done. Combined with a cap on prefix length (around 50 characters), finding the node is bounded too, so the whole query is effectively constant time.

Gains

Query time no longer depends on how many queries share the prefix. No sorting on the hot path. Easily meets the 100 ms budget.

Costs

Extra memory at every node (the same popular query is copied into many ancestors' lists). Updating one frequency means touching every ancestor, which is why updates are batched.

Common trap: saying "we sort the children at query time". That is the naive version. The interview answer is "we precompute and cache top-k at each node, so the query is a lookup".

Why data gathering is batched, not real time

The first high-level sketch updates frequencies the moment someone searches. It looks tidy but collapses at scale: users can enter billions of queries a day, and each update would ripple through every ancestor's cached top-k list. Worse, the payoff is tiny, because top suggestions barely move once the trie is built.

So the design turns a firehose into a weekly delivery. Raw queries go to append-only analytics logs. Aggregators condense a window of logs into a frequency table. Workers rebuild a brand new trie asynchronously and write it to storage. The old trie keeps serving until the new one is ready.

Common trap: forgetting that the aggregation window is a dial. For trending, real-time products you shorten it or weight recent queries more heavily; for most products, once a week is enough.

Storing, deleting and sharding the trie

Where does the finished trie live? Reads go to the Trie Cache, a distributed in-memory cache. Behind it sits the Trie DB, with two options. A document store such as MongoDB can hold a serialized snapshot of the whole weekly trie. A key-value store flattens the tree: every prefix becomes a key and that node's data (including its top-k list) becomes the value, so any prefix is a single hash lookup.

Deletion is handled in two speeds. A filter layer sits in front of the cache and removes unwanted results (such as hate speech) on the way out, immediately and by flexible rules. The physical removal from the database happens later, asynchronously.

When the trie outgrows one machine, shard by prefix range: a-m on one server, n-z on another. Letters are not evenly popular, so split further inside busy ranges (aa-ag, ah-an). A shard map manager holds the routing table and tells the web tier which server owns which range.

  1. Coarse split by first letter range (a-m, n-z).
  2. Measure load; split hot ranges more finely (aa-ag, ah-an).
  3. Record the mapping in the shard map manager.
  4. Route every request through the map to the owning shard.
Common trap: sharding naively by 26 letters. Far more words start with "s" or "c" than with "x", so fixed letter shards end up badly unbalanced.

Squeezing the last milliseconds and going global

Two client-side tricks shave latency before the server is even involved. AJAX requests send just the prefix and receive just the list, with no page refresh. Browser caching keeps recent results locally, so retyping a common prefix costs zero network time.

Scaling beyond English means storing Unicode characters in the trie and building separate tries per country or region, since what is popular in one market is noise in another. Trending events are handled by dynamically updating trie nodes or weighting recent queries more heavily.

Test yourself

Write your answer in the margin with your stylus first, then tap to reveal.

Why is the top-k list cached at every trie node instead of computed on demand?

Computing on demand means traversing the whole subtree below the prefix and sorting all matches, which is huge for short prefixes like "b". Caching turns the query into "find node, read list", keeping it within the 100 ms budget at 48,000 peak QPS. The cost is extra memory and harder updates.

What would happen if the trie were updated on every search query?

With billions of queries a day, each update would ripple through the cached top-k lists of every ancestor node, creating constant write contention on the hottest nodes. The benefit would be negligible because top suggestions rarely change. That is why queries go to logs and the trie is rebuilt in batches.

Compare storing the trie in a document store versus a key-value store.

A document store like MongoDB holds a serialized snapshot of the weekly trie, which is simple to write and restore. A key-value store maps every prefix to its node data, so any prefix is a single hash lookup, which suits fast serving and fine-grained access.

A harmful suggestion is discovered on Tuesday; the next rebuild is Sunday. What happens?

The filter layer in front of the trie cache blocks it immediately at read time using its filter rules. The physical removal from the database happens asynchronously, and the next rebuild will not include it.

Why shard by prefix range with a shard map manager rather than one shard per letter?

Letter popularity is very uneven, so fixed letter shards would be imbalanced. Prefix ranges can be split further where traffic is heavy (aa-ag, ah-an), and the shard map manager records the mapping so requests are routed correctly as ranges change.

How would you adapt this design for a Twitter-like product where trends matter within hours?

Shorten the aggregation window so the trie is rebuilt more often, and weight recent queries more heavily or update trending nodes dynamically. The weekly cadence is a default for products where popularity is stable.
