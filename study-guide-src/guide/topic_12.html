Picture this

You type "running 5 min late" and hit send on your phone. Before you have locked the screen, your friend's phone buzzes across the city, the little green dot next to your name tells them you are online, and when you open your laptop that evening the same message is waiting there too. It feels effortless, but behind it 50 million daily users are holding open live connections, messages must arrive in the right order, and history must be kept forever. The chat system is a switchboard that never hangs up: it has to know where everyone is plugged in, route each message to the right socket in milliseconds, and remember everything that was ever said.

1 Macro Structure & Dependency Map

The system hangs on four hubs: the live connection, the servers split by whether they hold state, the message store with its ID scheme, and the presence machinery. Read the tree top-down; peripheral items are nice-to-know.

  • Real-time connection (WebSocket) — without a live, two-way pipe, the server cannot push messages to the receiver
    • Receiver-side options compared: polling, long polling, WebSocket
      • polling wastes requests; long polling wastes held connections for inactive users
    • WebSocket chosen for both sending and receiving
    • Service discovery (Apache Zookeeper) picks the chat server
      • based on geography and server capacity
  • Stateless vs stateful services — the architectural split that decides how each part scales
    • Stateless: API servers for signup, login, profile, behind a load balancer
    • Stateful: chat servers holding persistent WebSocket connections
    • Presence servers (online/offline) and notification servers (push)
      • notifications reuse the Notification System design
  • Message storage & ordering — chat history is permanent and must stay in sequence
    • Key-value store for chat history
      • easy horizontal scaling, low latency, used by Facebook Messenger and Discord
    • Message ID decides order; group key is (channel_id, message_id)
      • Snowflake global IDs vs local per-channel sequence numbers
    • Multi-device sync with cur_max_message_id
  • Message flows & presence — how messages and green dots actually move
    • One-on-one: store, then forward or push-notify
    • Group chat: copy to each member's inbox (message sync queue)
      • max 100 members keeps copying affordable
    • Heartbeats for online status; pub-sub channels per friend pair

The WebSocket is the precondition for everything real-time, and it is what makes chat servers stateful. That stateful/stateless split then shapes scaling and discovery. The KV store and its ID scheme guarantee order and history, and the message and presence flows are the traffic running over this foundation.

2 Black-Box Cause & Effect Flow

Here is the chain of boxes a message passes through, from login to delivery. For each, notice what goes in and what comes out.

API servers (stateless, over HTTP)

Input: Login, signup, profile requests via the load balancer.

Output: An authenticated user, and a recommended chat server to connect to.

The reception desk. Interchangeable clerks check you in and hand you a room number.

→ feeds into: Service discovery

Service discovery (Zookeeper)

Input: The user's location plus the load on each chat server.

Output: The best chat server for this client.

The seating host at a busy restaurant, sending you to a nearby table that is not already overcrowded.

→ feeds into: WebSocket connection to that chat server

Chat server (stateful)

Input: Messages arriving over the sender's WebSocket.

Output: A message with a unique ID, stored in the KV store and routed toward the recipient.

A switchboard operator with your line plugged in. It stamps each message with a sequence number and patches it through.

→ feeds into: KV store, then the recipient's chat server or the notification servers

Key-value store

Input: Messages keyed by message ID, or by (channel_id, message_id) for groups.

Output: Permanent, ordered history that any device can query.

The ever-growing ledger. Every message is written once, in order, and kept forever.

→ feeds into: Message sync on each device

Presence servers

Input: Periodic heartbeats from clients.

Output: Online/offline status, published to friends' channels.

The lobby attendant who marks you "in the building" while you keep waving, and "gone" once you have not waved for a while.

→ feeds into: Friends' presence indicators

Notification servers

Input: Messages for users who are offline.

Output: A push notification to the user's device.

The note slipped under the door when nobody answers the phone.

→ feeds into: The offline user's device

Follow one message

  1. Asha logs in on her phone over HTTP. The API servers authenticate her, and service discovery (Zookeeper) recommends Chat Server 1, which is nearby and lightly loaded.
  2. Her phone opens a persistent WebSocket to Chat Server 1 and starts sending heartbeats to the presence servers. Her friends see her go online.
  3. She sends "running 5 min late" to Ben. The message travels over her open WebSocket to Chat Server 1.
  4. Chat Server 1 assigns it the next message ID for their one-on-one channel and stores it in the key-value store.
  5. Ben is online, connected to Chat Server 2. The message is forwarded there, and Chat Server 2 pushes it down Ben's WebSocket instantly.
  6. Ben's phone updates its cur_max_message_id to the new message's ID.
  7. That evening Ben opens his laptop, whose cur_max_message_id is older. It asks for messages where the recipient is Ben and the message ID is larger than its value, and "running 5 min late" appears there too.
  8. Had Ben been offline, step 5 would instead send a push notification via the notification servers.

3 Purpose & Concept Beacons

A chat system keeps a persistent WebSocket between each client and a stateful chat server, stores every message permanently in a key-value store ordered by per-channel IDs, and layers presence and push notifications on top.

Mental picture

Imagine an old-fashioned telephone exchange for a whole city. The front office where you register and update your details is the stateless API tier: any clerk can help you. When you are ready to talk, a dispatcher (Zookeeper service discovery) assigns you to an operator near you, and that operator keeps your line physically plugged in (the WebSocket on a stateful chat server). Every call is transcribed into a permanent ledger with numbered lines (the KV store and message IDs), so any of your extensions at home or at work can catch up by asking "give me everything after line 653" (cur_max_message_id). A light on the switchboard stays lit while you keep tapping the line (heartbeats), and if you are not home, a note goes in your letterbox (push notification).

4 Opportunistic Drilling

The connection protocol, the storage and ID scheme, multi-device sync and presence are where the real reasoning lives. Master these four and the rest of the chapter follows.

Choosing the connection: polling, long polling, WebSocket

Sending is easy: the client just makes a request to the server. Receiving is the hard part, because the server has something to say and the client did not ask for it. HTTP is client-initiated, so the question becomes: how does the server reach the receiver?

Polling has the client ask at intervals, "any new messages?" Most answers are "no," so it burns requests. Long polling improves on this: the client asks, and the server holds the connection open until a message arrives. But for inactive users, those held connections sit idle and still cost resources.

WebSocket opens a single, persistent, two-way connection. Either side can send whenever it likes. The design uses it for both sending and receiving, which is why the chat servers become stateful.

Common trap: Putting chat servers behind the same load balancer as API servers and treating them as interchangeable. They hold live connections, so a client must stay with its assigned chat server; that is why service discovery exists.

Storage and message IDs

Chat history is permanent, so the data only ever grows, and most reads hit recent messages while a vast "long tail" of old messages sits mostly untouched. The notes choose a key-value store because it scales horizontally, gives very low latency, and avoids a weakness of relational databases: when indexes grow large, random access becomes expensive. Facebook Messenger and Discord both use KV stores.

Order matters: messages must show up in the sequence they were sent. The message ID is the primary key and decides that sequence. For group chat the key is the composite (channel_id, message_id).

Where do IDs come from? One option is a global 64-bit generator like Snowflake. The better option in the notes is a local sequence number generator: IDs are unique only within one channel. That is enough, because you only ever need order within a one-on-one conversation or a single group, never across the whole system.

Gains

Local IDs are simpler to generate than a global sequence; the KV store scales out cheaply and serves recent messages fast.

Costs

IDs are not comparable across channels; a KV store gives up the rich querying of a relational database.

Common trap: Insisting on globally unique, globally ordered IDs. Ordering only needs to hold within a channel, so local sequences are sufficient.

Group chat and multi-device sync

In group chat, when User A sends a message, the chat server copies it into a separate inbox (message sync queue) for each recipient. Each recipient's inbox collects messages from every sender they talk to, so a client only has to check one place.

Multi-device sync solves a different problem: the same user on a phone and a laptop. Each device keeps a bookmark, cur_max_message_id, the latest message ID it has seen. A message is new for that device when both conditions hold:

  1. The recipient ID equals the logged-in user's ID.
  2. The message ID in the KV store is larger than that device's cur_max_message_id.
Common trap: Thinking inbox copying scales to huge groups. The notes flag it as expensive for larger groups; it works here because of the 100-member cap.

Online presence: heartbeats and fanout

How do you know someone is online? You could mark them offline the instant their connection drops, but mobile connections flicker constantly, and the green dot would blink on and off. Instead, clients send a heartbeat to the presence servers at regular intervals. As long as heartbeats keep arriving, the user is online. If none arrives within a threshold (x = 30 seconds in the diagram), they are marked offline.

Once status changes, friends must hear about it. The notes use publish-subscribe with one channel per friend pair. When User A's status changes, it is published to channels A-B, A-C and A-D, which Users B, C and D subscribe to. This works well for small groups; the cost grows with the number of friends.

Answer each one in the margin with your stylus before you tap to check.

Why was WebSocket chosen over polling and long polling?

Polling floods the server with redundant requests, and long polling wastes held connections on inactive users. WebSocket is a persistent, bi-directional connection, so the server can push messages the instant they arrive, and it is used for both sending and receiving.

Compare stateless and stateful services in this design.

Stateless API servers handle signup, login and profiles; any server can serve any request behind a load balancer. Stateful chat servers hold persistent WebSocket connections, so each client is tied to one server, chosen by service discovery.

Why use a key-value store for chat history instead of a relational database?

KV stores scale horizontally easily and provide very low latency. Relational databases do not handle the long tail of data well: when indexes grow large, random access becomes expensive. Facebook Messenger and Discord both use KV stores.

Why are local, per-channel message IDs good enough?

Message order only needs to be maintained within a one-on-one channel or a group channel. IDs unique within the channel, combined with channel_id as a composite key, give that ordering without a global sequence generator.

A user's phone has cur_max_message_id = 653. Which messages does it fetch when it reconnects?

Every message in the KV store whose recipient ID is the logged-in user and whose message ID is greater than 653. After fetching, the phone updates its bookmark to the newest ID.

What happens if a client stops sending heartbeats?

If no heartbeat arrives within the threshold (30 seconds in the example), the presence server marks the user offline and publishes the change to each friend-pair channel, so subscribed friends see the update.

What happens when User A messages User B, who is offline?

Chat Server 1 still assigns a message ID and stores the message in the KV store. Because B is offline, a push notification is sent instead of forwarding over a WebSocket. When B reconnects, sync fetches the message using cur_max_message_id.
