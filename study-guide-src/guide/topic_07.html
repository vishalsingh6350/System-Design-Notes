Picture this

On a single database, giving every new row an ID is trivial: auto_increment hands out 1, 2, 3 like a deli-counter ticket roll. Now picture that deli with dozens of counters in several cities, all serving customers at once, and a rule that no two tickets may ever share a number — and that the numbers must roughly tell you who arrived first. Passing one ticket roll around is far too slow; letting each counter print its own risks duplicates. This chapter designs a generator that produces over 10,000 unique, time-sortable, 64-bit numeric IDs per second, with no central ticket roll to become a bottleneck.

1 Macro Structure & Dependency Map

The chapter is a requirements checklist followed by four candidate designs, each tested against that checklist. Snowflake is the winner, so it is the biggest hub; the other three are useful mainly as foils that show why each requirement matters.

  • Requirements — the scorecard every design is judged against
    • Unique and numeric, fits in 64 bits
    • Ordered by date (increasing with time, but not strictly +1)
    • Over 10,000 IDs per second
      • Why plain auto_increment fails: scalability and synchronisation in distributed setups
  • Rejected designs — each fails at least one requirement, which teaches you the requirement
    • Multi-master replication: auto_increment by +k for k servers
      • Hard across data centres; not time-ordered; painful when servers change
    • UUID: 128-bit, generated independently
      • No coordination, scales easily — but too long, not time-sortable, may be non-numeric
    • Ticket server: one central DB hands out numbers
      • Simple, numeric — but a single point of failure
  • Twitter Snowflake bit layout — the chosen design: split 64 bits into meaningful sections
    • 1 sign bit + 41 timestamp + 5 datacenter + 5 machine + 12 sequence
    • Timestamp: milliseconds since a custom epoch (Twitter default 1288834974657)
      • Epoch = Nov 04, 2010, 01:42:54 UTC
    • Sequence: up to 4096 IDs per millisecond per machine, reset every millisecond
  • Operational concerns — what can still go wrong after the design is chosen
    • Clock synchronisation via NTP
    • Section-length tuning for the use case
    • High availability: redundancy and failover

Requirements are the root: without them you cannot say why UUID or a ticket server loses. The rejected designs each expose one tension (coordination vs uniqueness, size vs independence, simplicity vs single point of failure). Snowflake resolves all three by baking time, location and a per-millisecond counter into the bits, and the operational concerns are the fine print on that bargain.

2 Black-Box Cause & Effect Flow

Inside a Snowflake generator, an ID is assembled field by field. Treat each field as a box that contributes a slice of the final 64-bit number.

Requirement filter

Input: candidate designs (multi-master, UUID, ticket server, Snowflake).

Output: Snowflake, the only one that is 64-bit, numeric, time-ordered, decentralised and fast.

A sieve: each requirement shakes out one contender until only one is left in the pan.

→ feeds into: the bit layout

Timestamp section (41 bits)

Input: the machine clock in milliseconds, minus the custom epoch.

Output: the high-order bits of the ID.

Because time sits in the most significant bits, a later ID is numerically bigger — sorting by ID is sorting by time.

→ feeds into: the assembled ID

Datacenter ID + machine ID (5 + 5 bits)

Input: fixed identifiers chosen when the machine starts.

Output: the middle bits, unique per generator (up to 32 × 32 generators).

A return address stamped on every ticket. Two machines printing in the same millisecond still cannot collide, because their addresses differ.

→ feeds into: the assembled ID

Sequence number (12 bits)

Input: how many IDs this machine already issued in the current millisecond.

Output: the low-order bits, 0 to 4095, reset to 0 each new millisecond.

A tally counter clicked for every ticket within the same tick of the clock, wiped clean when the clock ticks over.

→ feeds into: the assembled ID

Clock sync (NTP) and HA

Input: drift between machine clocks; generator failures.

Output: clocks kept close together; generators backed by redundancy and failover.

The whole scheme trusts the clocks, so NTP is the metronome keeping every counter in rhythm.

→ feeds into: IDs that stay correctly ordered across machines

Follow one ID

  1. A web server needs a new ID for a freshly created record. It asks its local Snowflake generator — no network round-trip to a central server.
  2. The generator reads the current time and subtracts Twitter's epoch 1288834974657. In the notes' example the result is 297616116568 milliseconds.
  3. That number fills the 41 timestamp bits, right after the sign bit, which is always 0.
  4. Next come the datacenter bits 01010 (datacenter 10) and the machine bits 01100 (machine 12), configured when the generator started.
  5. This is the first ID this machine has issued in that millisecond, so the 12 sequence bits are all zeros.
  6. The fields are concatenated into one 64-bit number and returned.
  7. Reading it back: take the timestamp bits, convert to decimal (297616116568), add the epoch to get 1586451091225, and convert milliseconds to UTC — Apr 09 2020 16:51:31 UTC. The ID literally carries its birth time.

3 Purpose & Concept Beacons

Generate unique, date-sortable, 64-bit numeric IDs at over 10,000 per second across many machines without any central coordinator, by encoding time, location and a per-millisecond counter directly into the bits.

Mental picture

Imagine every ID as a postmarked envelope. The big date-and-time stamp across the front is the 41-bit timestamp, so stacking envelopes by postmark sorts them by when they were sent. Below it is the post office's region code and branch number — the 5-bit datacenter ID and 5-bit machine ID — so two branches stamping at the same instant still produce different envelopes. In the corner is a little counter the clerk clicks for each envelope within the same millisecond — the 12-bit sequence — reset at every tick. No branch ever phones head office for permission, which is why there is no single point of failure; the only shared thing is the clock on the wall, kept in step by NTP.

4 Opportunistic Drilling

Interviewers almost always ask you to draw the Snowflake layout and defend it against the alternatives. Nail the bit budget, the comparison table, and the clock caveat, and you have covered most of the chapter's yield.

The Snowflake bit budget, field by field

Sixty-four bits, five sections. The leading sign bit is always 0, keeping the number positive. The next 41 bits are milliseconds since the custom epoch — placing time in the most significant bits is what makes larger IDs later IDs. For scale, 2^41 milliseconds works out to roughly 69 years of headroom from the epoch.

Then 5 bits of datacenter ID and 5 bits of machine ID: 32 datacenters, each with up to 32 machines. Finally 12 bits of sequence: up to 4096 IDs per machine within one millisecond. That is far beyond the 10,000 per second requirement even on a single machine.

Decoding an ID back into a timestamp

Because the timestamp is embedded, any Snowflake ID can be read back into its creation time. Slice out the 41 timestamp bits, convert them to decimal, add the epoch, and convert the resulting milliseconds to UTC.

  1. Take the 41 bits after the sign bit.
  2. Convert binary to decimal: 297616116568.
  3. Add Twitter's epoch 1288834974657: 1586451091225.
  4. Interpret as milliseconds since the Unix epoch and convert to UTC: Apr 09 2020 16:51:31.

Why the other three designs lose

Multi-master replication uses each database's auto_increment but steps by k, where k is the number of servers — with two MySQL servers, one yields 1, 3, 5 and the other 2, 4, 6. Unique, yes, but IDs from different servers do not increase with time, it is hard to stretch across data centres, and changing k when servers join or leave is painful.

UUIDs are the opposite extreme: every server mints 128-bit IDs with no coordination at all. Superb for scaling, but they blow the 64-bit budget and do not sort by time. A ticket server centralises one auto_increment counter: simple and numeric, but every ID depends on one box, which is a single point of failure.

The fine print: clocks, tuning, availability

Snowflake quietly assumes every machine agrees on the time. If one clock drifts, its IDs can sort out of order relative to other machines. The notes' remedy is Network Time Protocol (NTP) to minimise drift.

The 41/5/5/12 split is a default, not a law. A workload with low concurrency but a need for a longer lifespan could shrink the sequence and grow the timestamp. And because every insert in the system needs an ID, the generator is mission-critical: build in redundancy and failover.

Gains

Decentralised, 64-bit, time-ordered, 4096 IDs per ms per machine, no coordination per ID.

Costs

Relies on clock sync; datacenter and machine IDs must be assigned uniquely; bit sizes lock in capacity limits.

Common trap: claiming IDs increase by exactly 1. The requirement is only that IDs increase with time; Snowflake IDs jump in large, uneven steps.

Test yourself

Draw the bit layout in the margin from memory, then answer each question before revealing.

Why is UUID rejected even though it needs no coordination?

UUIDs are 128 bits, exceeding the 64-bit requirement, and they are not sortable by time and may be non-numeric. Easy scaling does not compensate for failing the size and ordering requirements.

What are the five Snowflake sections and their bit sizes?

Sign bit (1, always 0), timestamp (41), datacenter ID (5), machine ID (5), sequence number (12). Total 64 bits.

What happens to the sequence number when the millisecond changes?

It resets to 0. Within a single millisecond it counts up to 4095, allowing 4096 IDs per machine per millisecond.

Why does putting the timestamp in the high-order bits make IDs sortable by time?

The most significant bits dominate numeric comparison. An ID created later has a larger timestamp, so it is numerically larger regardless of the lower datacenter, machine and sequence bits.

What goes wrong if machine clocks drift apart, and what is the fix?

IDs from different machines may no longer reflect true creation order, since ordering depends on synchronised clocks. Use Network Time Protocol (NTP) to minimise drift.

Compare a ticket server and multi-master replication.

A ticket server is one central auto_increment: simple and numeric but a single point of failure. Multi-master spreads the load with +k steps, avoiding one SPOF, but IDs are not time-ordered and resizing is hard.

How many distinct generators can the default Snowflake layout support?

32 datacenters times 32 machines per datacenter, from 5 bits each (2^5 = 32).
