Picture this

You are handed a short list of famous websites and told: "Starting from these, find the rest of the internet. Every page. Every month." Each page you open is a doorway to dozens more, many of them copies of pages you have already seen, some of them endless mazes built by accident or on purpose. Meanwhile, every website owner is watching their server logs, and if your robot hammers their small blog with hundreds of requests a second, you are the villain. The web crawler has to be greedy enough to swallow 1 billion pages a month, yet polite, careful and tireless enough never to trip, loop, or knock anyone over.

1 Macro Structure & Dependency Map

From 10,000 feet, a crawler is a loop: take a URL, download it, pull out new URLs, feed them back in. Read the map below as four hubs; everything else is a guard rail or tuning knob attached to one of them.

  • The crawl loop (BFS over the web graph) — the engine; every other component is a station on this circular conveyor belt
    • Seed URLs start the loop
      • chosen by locality or topic (sports, healthcare)
    • HTML Downloader + DNS Resolver fetch pages
      • DNS cache, short timeouts, geo-distributed servers, robots.txt
    • Content Parser validates pages
      • malformed pages are discarded
    • URL Extractor harvests new links
  • URL Frontier — the "to-do list" that decides what is fetched next, in what order, and how gently
    • Front queues = priority
      • Prioritizer scores by PageRank or update frequency
    • Back queues = politeness
      • one host per queue, one worker per queue, delay between downloads
    • Freshness
      • recrawl based on update history or importance
  • Deduplication ("Seen?" checks) — without it the loop drowns in repeats and never finishes
    • Content Seen? compares page hashes
    • URL Filter drops blacklisted or erroneous links
    • URL Seen? + URL Storage remember visited URLs
      • spider traps handled with URL length limits
  • Scale & robustness envelope — what lets the loop survive 1 billion pages a month and 30 PB of data
    • Distributed crawl servers + consistent hashing
    • Error handling and data validation
    • Extensibility via plug-in modules
      • PNG downloader, web monitor for copyright
    • Content Storage: disk, with popular content in memory

The crawl loop is the heartbeat; nothing exists without it. The URL Frontier sits at the top of the loop and controls its rhythm (priority and politeness). Deduplication sits at the bottom of the loop, deciding what is allowed back in. The scale envelope wraps the whole thing so it can run on many machines without falling over.

2 Black-Box Cause & Effect Flow

Treat each station as a sealed box: something goes in, something comes out. Follow the arrows and you have walked the whole architecture.

Seed URLs

Input: A hand-picked list of starting pages, grouped by locality or topic.

Output: The first entries in the URL Frontier.

The kindling for the fire. Good seeds are well-connected pages, so following their links reaches as much of the web as possible.

→ feeds into: URL Frontier

URL Frontier

Input: New, unseen URLs (from seeds and from the extractor).

Output: The next URL to download, chosen by priority and paced by politeness.

An air-traffic controller. It holds every URL waiting for takeoff and releases them in an order that favours important pages and never crowds one host's runway.

→ feeds into: HTML Downloader

HTML Downloader + DNS Resolver

Input: A URL.

Output: Raw HTML of the page (after resolving the hostname to an IP and checking robots.txt).

The courier. It looks up the street address (DNS), checks the "no entry" signs (robots.txt), then fetches the parcel, giving up quickly on slow servers.

→ feeds into: Content Parser

Content Parser + Content Seen?

Input: Raw HTML.

Output: A valid, never-before-seen page, stored in Content Storage; malformed or duplicate pages are dropped.

The quality inspector and the "haven't we seen this already?" clerk. The page is hashed and the hash compared with stored hashes, so duplicates are caught without comparing text character by character.

→ feeds into: Content Storage and URL Extractor

URL Extractor + URL Filter

Input: A parsed, new page.

Output: A clean list of candidate links, minus blacklisted or erroneous ones.

A prospector panning the page for links, then tossing out the fool's gold.

→ feeds into: URL Seen?

URL Seen? + URL Storage

Input: Candidate URLs.

Output: Only URLs never visited or queued before, which are added to the Frontier and recorded.

The bouncer with a guest list. If your name is on the "already been here" list, you do not get back in, which is what stops the loop from circling forever.

→ feeds into: URL Frontier (loop closes)

Follow one URL

  1. A sports-news homepage is placed in the Frontier as a seed URL (topic strategy: sports).
  2. The Prioritizer scores it highly (high PageRank, frequently updated), so it lands in a high-priority front queue.
  3. The biased queue selector picks that front queue; the queue router drops the URL into the back queue mapped to that host.
  4. The worker thread owning that back queue takes it. The DNS Resolver finds the IP (cached, since the host was hit before), robots.txt allows the path, and the page downloads within the short timeout.
  5. The Content Parser confirms the HTML is well-formed. Its hash does not match any stored hash, so the page is written to Content Storage.
  6. The URL Extractor finds, say, 120 links. The URL Filter removes blacklisted ad-tracker URLs and broken links.
  7. URL Seen? discovers most of the remaining links were already visited; only the handful of brand-new article URLs pass.
  8. Those new URLs enter the Frontier and are recorded in URL Storage. The loop begins again, roughly 400 times a second on average, up to 800 at peak.

3 Purpose & Concept Beacons

A web crawler is a breadth-first traversal of the web graph, disciplined by a Frontier that enforces priority and politeness, and by "Seen?" filters that stop it from repeating itself.

Mental picture

Imagine a vast library expedition. The seed URLs are the first few shelves you are told to start from. The URL Frontier is the expedition's master to-do board, sorted so rare manuscripts (high-priority pages) are fetched first, and split into one lane per library building (host) so no single librarian is overwhelmed. The downloader couriers carry the books back; the Content Parser is the conservator who rejects crumbling volumes; Content Seen? is the archivist who stamps each book's fingerprint (hash) and refuses a second copy. The URL Extractor reads each book's bibliography for new titles, and URL Seen? is the catalogue that says "we already have that one."

4 Opportunistic Drilling

If you only have time for a few deep dives, spend them here: the Frontier's two queue layers are the signature idea of this chapter, and deduplication plus robustness are what interviewers probe next.

Politeness: the back queues

A naive crawler pulls URLs off one big FIFO queue. Because pages link heavily to their own site, that queue fills with long runs of URLs from the same host, and a fleet of workers would fire them all at once. To the website, that looks like a denial-of-service attack.

The fix is to guarantee one request per host at a time, with a delay between downloads. The trick is structural: give each host its own FIFO queue, and give each queue exactly one worker thread. A single worker is naturally sequential, so the host can never receive two parallel requests from you.

  1. Queue router looks at the URL's hostname.
  2. Mapping table answers "which queue owns this host?"
  3. The URL is appended to that host's back queue, so each queue holds one host only.
  4. Queue selector hands each queue to its assigned worker thread.
  5. The worker downloads sequentially, pausing between tasks.
Common trap: Saying "add a rate limiter" without structure. The point is that politeness comes for free from the host-to-queue-to-single-worker mapping; you do not need global coordination to stop two workers hitting the same host.

Priority: the front queues

Not every page is equal. A forum post with no inbound links is far less valuable than a major news homepage. Plain BFS treats them the same, so the crawler would waste its 400 pages a second on junk.

The Prioritizer takes each URL and computes a priority (for example from PageRank or how often the page changes). URLs are then dropped into front queues f1..fn, each with an assigned priority. A queue selector randomly chooses a front queue, but with a bias towards high-priority ones, so important pages move faster while low-priority pages still trickle through.

Layered together, URLs flow front (what matters most) then back (who can safely be asked). A third concern, freshness, feeds URLs back in for recrawl based on update history or importance, which covers the "track new and updated pages" requirement.

Common trap: Mixing up the two layers. Front = priority, back = politeness. A memorable hook: you decide what first (front), then where it can be sent (back).

Deduplication and problematic content

The web repeats itself constantly: mirrored pages, the same article under several URLs, and links pointing back to pages you already have. There are two separate guards, and they catch different things.

GuardQuestion it answersHow
Content Seen?Have I already stored this exact content, maybe under a different URL?Hash the page and compare with stored hashes
URL Seen?Have I already visited or queued this URL?Look it up in URL Storage

A hash turns a whole page into a short fingerprint. Comparing fingerprints is fast, whereas comparing two full HTML documents character by character across billions of pages would be hopeless.

Beyond duplicates, watch for spider traps (infinitely deep URL structures, defended with URL length limits) and data noise such as ads or spam, which is filtered out as irrelevant.

Common trap: Assuming URL Seen? makes Content Seen? redundant. Two different URLs can serve identical content; only the content hash catches that.

Downloader performance, robustness and extensibility

At 800 QPS peak, small inefficiencies multiply. The downloader relies on four optimizations: distribute crawling across many servers; keep a DNS cache so every URL on a known host does not trigger a fresh lookup; place crawl servers close to the sites they crawl; and use a short timeout so one slow server cannot stall a worker.

Robustness comes from consistent hashing to spread load across downloaders, careful error handling so one bad page cannot crash the system, and data validation to protect content integrity.

Gains

DNS caching and short timeouts keep workers busy; geo-distribution cuts download latency; plug-in modules add new content types cheaply.

Costs

A short timeout may abandon slow but legitimate pages; many distributed servers mean more coordination and more places for failures to hide.

Cover the answer, write your own in the margin with your stylus, then tap to check.

Why does the crawler use BFS rather than DFS, and what is BFS still missing?

The web graph can be extremely deep, so DFS could disappear down one site for a very long time. BFS explores level by level. But plain BFS treats every URL as equally important, which is why the Frontier adds a prioritizer.

How does the back-queue design guarantee only one request per host at a time?

The mapping table assigns each host to a single back queue, and each queue is served by exactly one worker thread. Because one worker downloads sequentially, and can pause between tasks, a host never receives parallel requests from the crawler.

Compare front queues and back queues.

Front queues handle priority: URLs are sorted by importance and a biased random selector favours higher-priority lanes. Back queues handle politeness: URLs are sorted by host and each lane is bound to one worker.

What happens if you remove the Content Seen? check but keep URL Seen?

The crawler would still avoid revisiting the same URL, but it would store identical pages reached through different URLs. That wastes storage in a system already budgeting about 30 PB over five years, and pollutes the index with duplicates.

What is a spider trap and how do you defend against it?

A spider trap is a URL structure that generates effectively infinite new links, keeping the crawler looping forever. One defence from the notes is a maximum URL length, cutting off absurdly long, auto-generated paths.

Name the four downloader performance optimizations and what each protects.

Distributed crawling (throughput), a DNS cache (avoids repeated slow lookups), geographically distributed crawl servers (lower latency to target sites), and short timeouts (stops unresponsive servers from tying up workers).
