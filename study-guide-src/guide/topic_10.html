Picture this

It is 9 a.m. and a dozen services all want to talk to your users at once: billing wants to send payment reminders, shipping wants to say "your parcel is out for delivery," marketing wants to announce a sale. Some messages must reach an iPhone, some an Android phone, some an inbox, some a plain old SMS. Every day that adds up to 10 million push notifications, 1 million texts and 5 million emails. If one server hiccups, a reminder vanishes; if a retry fires twice, a customer gets the same text two times and rolls their eyes. The notification system is the post office that sits between all those eager senders and the user's pocket, and it has to be fast, reliable, and never annoying.

1 Macro Structure & Dependency Map

At the highest level there are senders on the left, delivery providers on the right, and a pipeline in the middle. Read the map as four hubs: the channels you deliver through, the pipeline that carries events, the reliability guarantees, and the user-facing controls.

  • Delivery channels & third-party providers — you never talk to a phone directly; everything is handed to a provider
    • iOS push via APNS; Android push via FCM
    • SMS via Twilio or Nexmo; email via SendGrid or Mailchimp
    • Contact info gathering
      • device tokens table for push; user table for email and phone
  • Decoupled sending pipeline — the backbone that turns "please notify" into delivered messages at scale
    • Trigger services (micro-service, cron job, distributed system)
    • Notification servers (APIs, validation, fetch render data)
      • horizontally scaled; DB and cache moved out
    • Message queues as buffers
      • monitor queue depth to scale workers
    • Workers pull events and call providers
  • Reliability — a notification must not be lost, and must not be sent twice
    • Notification log database for persistence
    • Retry mechanism when providers fail
    • Deduplication by event ID
  • User-facing controls & polish — what keeps the system respectful and measurable
    • Notification settings (opt-in / opt-out per channel)
    • Rate limiting per user
    • Templates for consistent formatting
    • event tracking: open rate, click rate, engagement
    • security: AppKey and AppSecret on push APIs

The channels define the destination and the pipeline defines the route. Reliability is layered onto the pipeline, since queues and workers are exactly where messages can be lost or duplicated. The user controls sit at the front of the pipeline, deciding whether a message should be sent at all.

2 Black-Box Cause & Effect Flow

Each box below receives something and hands something on. Chain them together and you have the final design from the notes.

Trigger service

Input: A business event (a bill is due, a parcel shipped) or a scheduled job.

Output: An API call to the notification servers saying "notify user X about Y."

The customer walking into the post office with a letter. It knows what to say, but not how to deliver it.

→ feeds into: Notification servers

Notification server

Input: The API request.

Output: A validated, fully rendered notification event, placed on the right queue.

The counter clerk. It authenticates the sender, applies rate limits, checks the email or phone number is valid, and looks up the device token, settings and user info from cache or database.

→ feeds into: Message queue for that channel

Message queue

Input: Notification events.

Output: The same events, released at the pace workers can handle.

A holding bay. During a flood of notifications it absorbs the surge, so a busy SMS provider cannot slow down iOS pushes.

→ feeds into: Workers

Worker

Input: One event from the queue.

Output: A request to the third-party provider, a record in the notification log, and a retry if the provider fails.

The courier who actually takes the parcel to the delivery company, writes it in the logbook, and tries again if the depot is closed.

→ feeds into: APNS / FCM / SMS / email provider

Third-party provider

Input: A formatted notification plus the device token, phone number or address.

Output: The message on the user's device or inbox.

The national postal network. You do not own it, so you must plan for it being slow or unavailable.

→ feeds into: User device, and back to analytics via click tracking

Follow one notification

  1. The shipping service (a trigger service) sees an order leave the warehouse and calls the notification API: "tell this user their parcel is on its way."
  2. A notification server authenticates the caller and checks the rate limit for that user.
  3. It reads the user's notification settings from cache: push is opted in. It fetches the user's iOS device token (gathered when the app was installed).
  4. The server builds the event, with a unique event ID, and puts it on the iOS push queue. Analytics records "send pending."
  5. A worker pulls the event, checks the event ID has not been seen before, fills in the "Your order has shipped" template, and writes it to the notification log.
  6. The worker calls APNS. APNS returns an error; the worker puts the event back for retry.
  7. On the second attempt APNS accepts it and delivers the push to the phone. Analytics records "sent."
  8. The user taps the notification. Click tracking reports back to analytics, feeding the open and click-rate metrics.

3 Purpose & Concept Beacons

A notification system is a decoupled, queue-buffered pipeline that turns internal events into messages delivered by third-party providers, without losing them, duplicating them, or spamming the user.

Mental picture

Think of a busy regional post office. Customers at the front counter are the trigger services; the counter clerks are the notification servers, checking the address book (cache and database) and refusing anyone who sends too much (rate limiting). Behind them are four sorting bins, one per channel: these are the message queues. Couriers (workers) take letters from their bin, log each one in a ledger (the notification log), and hand them to outside carriers like APNS or an SMS company. If a carrier's depot is shut, the courier puts the letter back in the bin and tries later, and a stamp with a unique serial number (the event ID) makes sure nobody delivers the same letter twice.

4 Opportunistic Drilling

The heart of this chapter is the evolution from a fragile single server to a queue-based design, plus the reliability tricks that make it trustworthy. Drill those first.

From the naive design to the decoupled design

The first sketch is simple: trigger services call one notification server, which reads the database and calls the providers directly. It works on a whiteboard, but it has three cracks. It is a single point of failure: if that server crashes, nothing is sent. It is hard to scale, because database, cache and sending logic are bundled together. And it is a performance bottleneck, because rendering and sending notifications is resource-hungry.

The improved design attacks each crack. Databases and caches move out of the notification server. Several notification servers run side by side (horizontal scaling). Message queues sit between the servers and the sending logic, and workers pull from those queues and call the providers.

Problem in first designFix in improved design
Single point of failureMultiple notification servers
Hard to scale parts independentlyDB and cache moved out; servers, queues and workers scale separately
Performance bottleneckQueues buffer load; workers do the heavy sending
Common trap: Putting one shared queue for all channels. The diagram gives each channel its own queue, so an outage at one provider only backs up its own queue and leaves the others flowing.

Reliability: no loss, no duplicates

Two opposite failures haunt a notification system. The first is loss: a worker crashes or a provider errors, and the notification simply disappears. The second is duplication: a retry succeeds but the original also went through, and the user gets the same message twice.

To prevent loss, workers persist notification data in a notification log database and use a retry mechanism. If a provider fails, the event is retried rather than dropped.

To prevent duplicates, every event carries an event ID. When an event arrives, the system checks whether that ID has been seen before. Seen: discard. New: send.

  1. Event arrives at worker.
  2. Look up event ID. Already seen? Drop it.
  3. Otherwise, record it in the notification log and send to the provider.
  4. Provider error? Put it back for retry.
Common trap: Treating retries and dedup as separate features. They are a pair: retries make duplicates more likely, and event-ID dedup is what makes retrying safe.

The final flow and the supporting cast

The updated design adds the components that make the system respectful and measurable. Notification servers now perform authentication and rate limiting at the door. Workers use notification templates so messages are consistent and quick to build. An analytics service records "send pending", "sent" and click tracking, producing open rate, click rate and engagement metrics.

Notification settings live in a dedicated table, and are checked before anything is sent: a user who opted out of SMS should never receive one. Queue monitoring watches how many notifications are waiting; a growing backlog is the signal to add workers.

Gains

Queues let each tier scale on its own and absorb bursts; the log and retries give durability; settings and rate limits protect the user experience.

Costs

More moving parts to operate; delivery is soft real-time rather than instant; you still depend on third parties you cannot control.

Contact info gathering

You cannot notify someone without an address. Contact details are collected when the user installs the app or signs up. Device tokens, needed for push, go into a device tokens table; email addresses and phone numbers live in the user table.

A single user can have several device tokens, one per device, which is why push tokens get their own table rather than a single column on the user record.

Common trap: Forgetting that iOS and Android need different providers. The device token is only useful when sent to the right one: APNS for iOS, FCM for Android.

What were the three problems with the initial single-server design?

It was a single point of failure, it was hard to scale the database, cache and processing independently, and it was a performance bottleneck because sending notifications is resource-intensive.

Why put message queues between notification servers and workers?

Queues decouple the parts of the system and act as buffers when a large volume of notifications must go out. Servers can accept requests quickly while workers drain the queues at their own pace, and each tier can scale separately.

What happens if APNS is down for a few minutes?

Workers get errors and use the retry mechanism, returning events to the queue to try again. The notification log keeps the data safe. Because each channel has its own queue, Android, SMS and email keep flowing.

How does the system avoid sending the same notification twice?

Each notification event has an event ID. When an event arrives, the system checks whether that ID has been seen before; if so it is discarded, otherwise the notification is sent.

Compare notification settings and rate limiting.

Settings are the user's choice: opt in or out of each channel, stored in a notification settings table. Rate limiting is the system's choice: a cap on how often any user is notified, to avoid overwhelming them.

What signal tells you to add more workers?

The number of queued notifications. Monitoring queues shows when the backlog is growing, meaning workers cannot keep up.
