Picture this

Somewhere a company is pouring 100 petabytes a year into your service: nightly database backups, millions of tiny thumbnails, and 200 MB video masters. They never edit any of it; they write it once and read it back, sometimes years later, and they expect every byte to still be there even if a whole rack catches fire. Meanwhile each spinning hard disk manages only 100 to 150 random seeks per second and fails at a steady, predictable rate. Designing an S3-like object store means building a warehouse of nearly unlimited size on top of unreliable shelves, cheaply, while promising six nines of durability.

1 Macro Structure & Dependency Map

The whole design follows from one split: metadata (what and where) is stored separately from data (the bytes). Read the map as "the split", then "how each half works", then "how we keep bytes alive".

  • Separate metadata from data — the UNIX inode idea; lets each side scale independently
    • Object = immutable key-value pair: URI is the key, bytes are the value
    • Write once, read many (~95% of operations are reads)
      • Block vs file vs object storage comparison
      • Flat namespace; "folders" simulated by name prefixes
  • Data store — where bytes physically live, addressed by object UUID
    • Data routing service (stateless), placement service (virtual cluster map, Paxos/Raft), data nodes
    • Small objects packed into large WAL-style files; object_mapping table in SQLite on each node
      • Files pinned to CPU cores to avoid write-lock contention
    • Primary replicates to two secondaries before replying (strong consistency)
  • Durability — the promise the whole product is sold on
    • Replicate across failure domains (rack, DC, network)
    • 3-copy replication vs 8+4 erasure coding
    • Checksums per file and per object to catch silent corruption
      • HDD annual failure rate 0.81% → 3 copies give 6 nines
  • Metadata store — maps names to UUIDs and answers listing and versioning queries
    • Bucket table (small, one server) and object table (sharded by hash(bucket_name, object_name))
    • Listing by prefix via a denormalized table sharded by bucket ID
    • Versioning via TIMEUUID object_version; delete markers
      • Per-user bucket limits keep the bucket table small
  • Lifecycle operations — getting big files in and dead bytes out
    • Multipart upload with upload ID and per-part ETags
    • Garbage collection via compaction
      • Lazy deletion, orphan parts, corrupted data

Everything hangs off the metadata/data split: the data store only ever deals with opaque UUIDs and bytes, while the metadata store only deals with names, buckets and versions. Durability is a property of the data store, and listing, versioning and sharding are properties of the metadata store. Lifecycle operations touch both, which is why they come last.

2 Black-Box Cause & Effect Flow

An upload passes through a gatekeeper, a bytes path and a names path. Keep the two paths distinct in your head and the rest falls into place.

Load balancer + API service

Input: RESTful HTTP requests such as PUT /bucket-to-share/script.txt.

Output: Orchestrated calls to IAM, the data store and the metadata store; an HTTP response.

The warehouse front office. It never touches boxes itself; it checks your paperwork and tells the loading crew and the records clerk what to do.

→ feeds into: IAM

IAM

Input: The caller's identity and the requested action on a bucket.

Output: Allow or deny (authentication, authorization, access control).

The security desk that checks your badge before you enter any aisle.

→ feeds into: data store (on writes) or metadata store (on reads)

Data routing + placement service

Input: Object bytes to store, or a UUID to fetch.

Output: The right primary data node, chosen from the virtual cluster map via consistent hashing.

A dispatcher with a live map of every shelf, which it keeps current by listening to heartbeats; it points each box to a replication group.

→ feeds into: data nodes

Data nodes

Input: Object bytes.

Output: Bytes appended to a large file, a row in the local object_mapping table (object_id, filename, file_offset, object_size), copies on two secondaries, and a UUID.

The shelves. Small parcels are packed tightly into big crates, a small ledger records which crate and position each parcel sits at, and two other shelves get identical copies.

→ feeds into: API service (returns the UUID)

Metadata store

Input: bucket_id, object_name, object_id (UUID), version and other metadata.

Output: Name-to-UUID lookups, prefix listings, version history.

The card catalogue. It does not hold the parcels; it tells you which UUID a name refers to, which the shelves then locate.

→ feeds into: every download (name → UUID → bytes)

Garbage collector

Input: Deleted, orphaned or corrupted objects inside data files.

Output: Compacted files with only live objects and an updated object_mapping table.

The night crew that repacks half-empty crates into full ones and throws out the empties.

→ feeds into: reclaimed disk space on primaries, replicas or all 12 erasure-coded nodes

Follow one upload

  1. A user sends HTTP PUT to create a bucket named "bucket-to-share". The API service asks IAM whether the user may write, then creates a bucket entry in the metadata store and returns success.
  2. Next, PUT /bucket-to-share/script.txt arrives with Content-Length: 4567 and a custom header x-amz-meta-author: Alex. The load balancer routes it to a stateless API service replica.
  3. IAM confirms the user's identity and write permission on the bucket.
  4. The API service streams the 4,567 bytes to the data store. The data routing service consults the placement service, and consistent hashing deterministically picks this object's replication group.
  5. The primary data node appends the bytes to the end of its current data file, say "/data/c", and inserts a row into its SQLite object_mapping table: object_id, filename /data/c, the starting offset, and size 4567.
  6. The primary replicates to two secondary data nodes and replies only after they succeed, choosing strong consistency over lower latency. A UUID is returned to the API service.
  7. The API service writes a metadata row: bucket_id, object_name script.txt, object_id (the UUID), plus other metadata. The client gets a success response.
  8. Later, GET /bucket-to-share/script.txt reverses the route: IAM checks read permission, the metadata store maps the name to the UUID, and the data store looks up filename and offset and streams back 4,567 bytes.

3 Purpose & Concept Beacons

Store huge volumes of immutable objects cheaply and durably by separating names from bytes, packing bytes efficiently on disk, and spreading redundancy across failure domains.

Mental picture

Picture a vast automated warehouse. At the front, a card catalogue maps each item's name to a barcode (metadata store: name to UUID), while the shelves out back only understand barcodes (data store). A dispatcher with a live floor plan decides which aisle a new box goes to (placement service with the virtual cluster map), and small parcels are packed into shipping crates with a packing list taped inside (WAL-style data files plus the object_mapping table). Every box is either photocopied onto shelves in three different buildings (replication) or split into puzzle pieces with spare pieces stored across aisles, so any few lost pieces can be rebuilt (8+4 erasure coding). A tamper seal on every crate reveals rot (checksums), and a night crew repacks crates to reclaim space (compaction).

4 Opportunistic Drilling

The data store internals and the durability math are where this design is won or lost; metadata sharding and multipart uploads are the most common follow-ups.

Inside the data store: routing, placement and nodes

The data store has three parts. The data routing service is stateless: it asks the placement service where to put or find data, then reads from or writes to data nodes. The placement service holds the virtual cluster map, a picture of the physical topology, and prunes nodes that stop sending heartbeats. Data nodes hold the bytes, and each runs a daemon that reports how many drives it manages and how full each one is.

Because placement is critical, it runs as a 5- or 7-node cluster synchronized by Paxos or Raft; 7 nodes survive 3 failures. Given an object's UUID, consistent hashing deterministically selects its replication group. The primary writes locally, replicates to two secondaries, and only then replies, so every successful write is already on three nodes at the price of higher latency.

Gains

Waiting for all replicas means any later read from any replica sees the object: strong consistency.

Costs

Write latency grows with the slowest replica.

How bytes are organized on disk

The naive approach, one file per object, collapses with many small objects. Each file consumes at least a whole disk block (typically 4 KB), wasting space on tiny objects, and millions of files mean millions of inodes, which operating systems handle poorly and cap at a maximum.

The fix is to append many objects into one big file, WAL style. Appends to a single file must be serialized, so cores would queue behind each other; confining each file to a specific core removes that contention. To find an object again, each node keeps an object_mapping table of object_id, filename, file_offset and object_size.

Where should that table live? A shared database cluster would need aggressive scaling and add a network hop to every read. Since each node only cares about its own objects, a lightweight relational DB, SQLite, runs inside each data node. Relational wins over RocksDB here because the access pattern is low write, high read.

Common trap: Proposing a central lookup database for object locations. The notes favour a local SQLite per node because data nodes only need their own mappings.

Durability: replication vs erasure coding

Hardware fails, and disasters take out whole racks or data centers at once. So copies must be spread across failure domains, not just across disks. With a typical HDD annual failure rate of 0.81%, three copies yield six nines of durability.

Erasure coding takes a different approach. Data is split into chunks and extra parity chunks are computed; if some chunks are lost, the rest can rebuild them. With 8+4, eight data chunks and four parity chunks are spread across failure domains, and up to four can be lost. Think of it as tearing a letter into eight strips and writing four clever summary strips, any eight of which rebuild the letter.

Whole-disk failures are obvious; partial corruption is not. So checksums (hashes of the contents) are stored for every file and every object, and verified on read. With 8+4 erasure coding, each of the 8 data pieces is fetched and its checksum verified separately.

Metadata: sharding, listing and versioning

The bucket table is small (users have a bucket limit) and fits one server, scaled for reads with replicas. The object table does not fit. Sharding by bucket_id creates hotspots because a single bucket can hold billions of objects. The chosen key is hash(bucket_name, object_name), since most queries look up an object by bucket and name.

That choice makes listing hard: "all objects under abc/ in bucket 123" is scattered across every shard. You could query every shard and merge, but pagination breaks because each shard returns different result counts and needs its own limit and offset. Since object stores are not optimized for listing anyway, the answer is a separate denormalized listing table sharded by bucket ID, so a listing hits one instance.

Versioning adds an object_version column of type TIMEUUID so versions sort by time, and each new version gets a new object_id. Deleting does not erase anything: it adds a new version with a special delete marker, and a GET for that name returns 404.

Multipart upload and garbage collection

Uploading a multi-gigabyte file in one request means one network hiccup restarts everything. Multipart upload splits the file into chunks that travel independently.

  1. Client initiates a multipart upload; the data store returns an upload ID.
  2. Client splits the file into parts and uploads each one with that upload ID.
  3. For each part, the data store returns an ETag, an MD5 checksum of that part.
  4. Client sends "complete multipart upload" with the upload ID, part numbers and all ETags.
  5. The data store reassembles the object, which can take a few minutes, then returns success.

Leftover parts become garbage, alongside lazily deleted objects and data that failed checksum verification. The garbage collector reclaims space by compaction: it copies live objects from an old file such as "data/b" into a new file "data/d", then updates the object_mapping table in one database transaction. Compaction runs only on files past a size threshold to avoid creating lots of small files, and deletions must reach every copy: primary and replicas, or all 12 nodes under 8+4 erasure coding.

Test yourself

Work each one out in the margin with your stylus, then reveal to check.

Why separate the metadata store from the data store?

Like a UNIX inode and its data blocks, names and locations are small and query-heavy while bytes are large and opaque. Splitting them lets each store be scaled and optimized independently.

What goes wrong if every object is stored as its own file?

Small objects waste most of a 4 KB block, and millions of files create millions of inodes, which operating systems handle poorly and cap. Packing objects into large append-only files fixes both.

Compare 3-copy replication with 8+4 erasure coding.

Replication costs 200% extra storage for 6 nines and gives fast, simple reads. Erasure coding costs 50% extra for 11 nines but needs more computation, is harder to build, and reads are slower because chunks come from many places.

What happens if a portion of a disk silently corrupts an object?

A whole-disk failure would be noticed, but partial corruption would not. Checksums stored per file and per object detect the mismatch on read, and the corrupted data becomes garbage to collect.

Why is listing objects by prefix slow, and how is it fixed?

The object table is sharded by hash(bucket_name, object_name), so one prefix's objects are scattered across shards and pagination across shards is awkward. A denormalized listing table sharded by bucket ID keeps a listing on one instance.

How does deleting a versioned object work?

A new version is added with a special object_id acting as a delete marker. Requests for the object then return 404, while older versions remain in the history.

Why does the placement service run on 5 or 7 nodes with Paxos or Raft?

It is critical: every write needs its cluster map. A consensus cluster keeps replicas in sync and survives failures; 7 nodes tolerate 3 failures.
