Picture this

It is peak season and a beachfront hotel has exactly one Deluxe King left for New Year's Eve. Two travelers, one in Tokyo and one in Toronto, press "Book" within the same heartbeat, while a third, impatient, double-taps the button on a laggy phone. Across a chain of 5,000 hotels and a million rooms, the system must sell each room once (well, up to 110% of once, because hotels deliberately overbook), charge each guest once, and never lose a paid reservation. Traffic is modest on average, just a few bookings per second, but the whole problem lives in those rare collisions where everyone reaches for the same room at the same instant.

1 Macro Structure & Dependency Map

This is a correctness-first system with low steady load. Read the map as: a data model that counts inventory, a set of guards that keep that count honest, and scaling and service boundaries built around the database.

  • Relational DB with ACID guarantees — the one thing that makes "never double-sell, never double-charge" achievable
    • Read-heavy, low-write workload (only a fraction of visitors book)
    • Clear, structured data that models naturally in tables
      • Read replicas across zones for high availability
  • room_type_inventory table — the ledger every booking reads and writes
    • One row per (hotel_id, room_type_id, date) with total_inventory and total_reserved
    • Overbooking check: total_reserved + n <= 110% * total_inventory
      • Rows pre-populated by a daily CRON job; ~73 mil rows for 2 years
    • Guests reserve a room type, not a specific room number
      • Original schema (reserve a roomID) fit Airbnb, not hotels
  • Concurrency control — the heart of the problem: preventing double booking
    • Same user clicks twice: idempotency key (reservationID) + unique constraint
    • Many users, same room: pessimistic lock, optimistic lock, or DB constraint
      • Client-side button disabling fails if JavaScript is off
  • Microservice architecture — separates concerns but raises the cross-service consistency question
    • Hotel, Rate, Reservation, Payment, Hotel Management services behind a public API gateway
    • Reservation + inventory kept in one service and one DB (hybrid)
      • 2PC and Saga if you must split them
      • gRPC for inter-service calls; CDN for static assets
  • Scaling for 1000x traffic — stateless services replicate easily; the DB is the bottleneck
    • Shard by hash(hotel_id) — every query filters on it
    • Redis inventory cache, kept in sync via CDC (Debezium)
      • TTL expires past dates; history can go to cold storage

The relational database is the root because every correctness guarantee in this design is borrowed from its transactions and constraints. The inventory table is what those transactions protect, the concurrency hub is how they protect it, and the microservice and scaling hubs are about not breaking that protection as the system grows.

2 Black-Box Cause & Effect Flow

A booking travels from browsing to a committed row in the inventory ledger. Each box below narrows the funnel and adds one layer of protection.

CDN + Hotel service

Input: Page views for hotel and room detail pages (the wide top of the funnel: ~300 detail views per 3 bookings).

Output: Static hotel and room info, images and JS bundles.

The glossy brochure rack in the lobby. The content rarely changes, so it is cached aggressively and costs almost nothing to hand out.

→ feeds into: Rate service and the reservation page

Rate service

Input: Hotel, room type and future dates.

Output: The price for each night, which changes daily and depends on how full the hotel is.

The price board that a clerk rewrites every morning, raising prices as the hotel fills.

→ feeds into: the reservation form

Reservation form (idempotency key)

Input: The guest starts filling in details.

Output: A globally unique reservationID generated up front and attached to the eventual POST.

A numbered claim ticket handed out before you order. However many times you wave it, the kitchen only cooks that ticket once.

→ feeds into: Reservation service

Reservation service + inventory DB

Input: POST /v1/reservations with hotelID, roomTypeID, roomCount, dates, reservationID.

Output: A new reservation row and incremented total_reserved for every night, or a rollback.

The front desk ledger. The clerk checks each night has space (allowing 10% overbooking), pencils in the guest, and a lock or constraint stops two clerks writing in the last slot at once.

→ feeds into: Payment service

Payment service

Input: A pending reservation and the guest's payment.

Output: Payment processed and the reservation status updated (state machine).

The cashier who stamps the ticket "paid" only after the money clears.

→ feeds into: reservation status, admin panel

CDC → Redis inventory cache

Input: Database change events (via Debezium).

Output: Keys like hotelID_roomTypeID_{date} holding available room counts.

A departures board that mirrors the ledger a moment later. It may briefly be stale, but the ledger itself still refuses invalid bookings.

→ feeds into: availability checks on future page loads

Follow one booking

  1. A guest views hotel 211's detail page, served from the CDN and the Hotel service's cache, and checks prices for room type 1001 from the Rate service.
  2. They open the reservation page. A reservation order is created with a unique reservationID, say 13422445.
  3. They request 3 rooms of type 1001 for 2021-06-01 to 2021-06-02 and press "Complete booking". The request hits the public API gateway (authentication, rate limiting).
  4. The Reservation service selects the inventory rows: 2021-06-01 shows 100 total / 80 reserved, 2021-06-02 shows 100 / 82.
  5. It checks each night: 80 + 3 = 83 and 82 + 3 = 85, both within 110% of 100 = 110. Allowed.
  6. In the same transaction it increments total_reserved to 83 and 85 and inserts the reservation row. With optimistic locking, the update succeeds only if the row's version has not changed since it was read.
  7. The laggy phone sends the same POST again with reservationID 13422445. The unique constraint on reservation_id rejects the duplicate; no second booking, no second charge.
  8. The Payment service charges the guest in full and updates the reservation's status.
  9. Debezium streams the inventory change to Redis, and the next visitor sees fewer rooms left for those nights.

3 Purpose & Concept Beacons

Sell each night of each room type no more than the allowed 110% of inventory, exactly once per booking, using the relational database as the single source of truth even under simultaneous clicks.

Mental picture

Think of an old grand hotel with a leather-bound reservations ledger at the front desk. Each page is one night for one room type, with two numbers written at the top: rooms we have and rooms promised (room_type_inventory). Every guest arrives holding a numbered claim ticket so the clerk never writes them in twice (reservationID idempotency key). When two clerks reach for the same page, either one physically holds the book while writing (pessimistic lock), or both write in pencil and the second erases if the page number changed while they were writing (optimistic lock with a version). A chalkboard in the lobby copies the ledger's free-room counts a moment later (Redis via CDC), and when the chain grows, the ledger is split into separate books per hotel (sharding by hotel_id).

4 Opportunistic Drilling

Nearly every follow-up question in this interview circles back to double booking and the database that prevents it. These drills cover the model, both flavors of double booking, and how to grow without breaking guarantees.

The inventory ledger: why reserve a room type

The first schema let guests reserve a specific roomID. That works for Airbnb, where each listing is unique, but hotel guests book "a Deluxe King", and a room number is picked later. So the API changes to roomTypeID plus roomCount, and a new table, room_type_inventory, tracks capacity per night.

Each row answers one question: for this hotel, this room type, this date, how many rooms exist (total_inventory, excluding rooms taken out of service) and how many are promised (total_reserved)? A stay of several nights touches several rows, and each must pass the check total_reserved + n <= 110% of total_inventory.

Double booking, part 1: the same user clicks twice

Disabling the button after one click helps, but a user with JavaScript turned off never sees it grey out. The robust fix is server-side: make the API idempotent so repeating it has no additional effect.

  1. Generate a globally unique reservation order ID while the guest fills in details.
  2. Submit the booking with that reservation_id.
  3. A second click resends the same reservation_id.
  4. The reservation_id column has a unique constraint, so the second insert fails and no duplicate is stored.

Double booking, part 2: many users, one last room

Assume the isolation level is not serializable. User 1's transaction reads 99 of 100 reserved: space! User 2's transaction reads the same 99: space! User 2 writes 100 and commits. User 1, still trusting its stale read, also writes and commits. Two guests, one room. The classic check-then-act race.

OptionHow it worksStrengthWeakness
Pessimistic lockSELECT ... FOR UPDATE locks rows until commitSerializes updates; good under heavy contentionDeadlocks; long transactions block everyone; not scalable (not recommended)
Optimistic lockRead version, write version + 1, reject if version changedNo DB lock; fast when conflicts are rareMany rollbacks when contention is high
DB constraintCHECK (total_inventory - total_reserved >= 0)Easy to implementPoor under high contention; hard to version-control; not all DBs support it

Version numbers are preferred over timestamps because server clocks can be inaccurate. Since booking QPS is low, conflicts are rare, which makes optimistic locking (or the constraint) the good fit here.

Common trap: Picking pessimistic locking because it "feels safest". The notes explicitly reject it for scalability: a lock held too long stalls every other transaction touching those rows.

Scaling to booking.com size: shard and cache

If the system is adopted by a huge travel site, QPS could be 1,000 times larger. The services are stateless, so you just add replicas. The database is stateful and is the real bottleneck. Shard it by hotel_id, since every query filters on it: at 30,000 QPS across 16 shards, each shard handles 1,875 QPS, comfortably within one MySQL cluster.

The cache key is hotelID_roomTypeID_{date} with the number of available rooms as the value, and TTLs expire past dates. Because sync is asynchronous, the cache can briefly show a room that is gone. That is acceptable: the database still rejects the invalid booking, and the user simply refreshes to see "no rooms left", which could happen anyway if they hesitated.

Gains

Lower DB load and in-memory speed for the read-heavy browsing path.

Costs

Keeping cache and DB consistent is hard; you must reason about how staleness affects the user.

Consistency across microservices

In a monolith, "reserve rooms, then record payment" can sit in one database transaction: all or nothing. In pure microservices, each service owns its own DB, so a failure halfway leaves inventory updated but payment not (or vice versa).

The design takes a pragmatic hybrid: reservation and inventory live in the same service and the same relational DB, so ACID still protects the critical update. If an interviewer insists on full separation, two tools exist. Two-phase commit gives atomic commit across nodes but blocks everything when one node lags. A Saga chains local transactions and runs compensating transactions on failure, trading atomicity for eventual consistency. Both add real complexity, so ask whether the purity is worth it.

Test yourself

Sketch your answer in the margin first, then open each one to check.

Why a relational database when average write load is only ~3 TPS?

The workload is read-heavy with few writes, the data is clearly structured, and above all ACID transactions prevent problems like double charges or negative inventory. NoSQL's write optimizations are not needed here.

What happens if two users read "99 of 100 reserved" at the same time without any locking?

Both see space, both increment, both commit, and the last room is sold twice. Optimistic locking, a DB constraint or pessimistic locking prevents this.

Compare optimistic and pessimistic locking for this system.

Pessimistic locking holds row locks until commit; it avoids conflicts but risks deadlocks and does not scale. Optimistic locking uses a version check and rolls back on conflict; it is faster when contention is low, which fits a low-QPS booking system.

How does the reservationID prevent a double click from creating two bookings?

It is generated once when the order is created and sent with every submission. A unique constraint on the reservation_id column rejects the second insert.

Why is it acceptable for the Redis inventory cache to be briefly stale?

The database remains the source of truth and rejects any invalid reservation. The worst case is a user seeing availability that is gone and getting a "no rooms left" message after refreshing.

Why shard by hotel_id rather than by reservation or date?

Every query filters on hotel_id, so each query lands on a single shard. With 16 shards, 30,000 QPS becomes 1,875 QPS per shard.

Why keep reservation and inventory in the same service?

So one relational transaction can update both atomically. Splitting them would require 2PC (blocking, slow) or a Saga (eventually consistent, complex).
