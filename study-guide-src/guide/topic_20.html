Picture this

It is 3 a.m. and a memory leak is slowly strangling a pool of web servers. No human is watching, yet five minutes after the first instance stops answering, an on-call engineer's phone buzzes through PagerDuty with one clear alert — not fifty duplicates. She opens a dashboard and sees the CPU and memory lines for that pool bending upward since midnight. Behind that calm moment is a system quietly ingesting about 10 million metrics from 100,000 machines, keeping them for a year, and continuously asking "is anything wrong?" The challenge is swallowing a relentless firehose of tiny numbers while still answering sudden, urgent questions in a flash.

1 Macro Structure & Dependency Map

The notes name five core components — collection, transmission, storage, alerting, visualization. Read them as a river: data flows in from the left, pools in the time-series database, and is drawn out on the right by alerts and dashboards.

  • Time-series data model — everything is (metric name, labels, timestamp, value); every component speaks this shape
    • Series identified by name + optional tags/labels, e.g. CPU.load host=webserver01,region=us-west
      • Line protocol format used by Prometheus, OpenTSDB
    • Access pattern: constant heavy writes, rare but bursty reads (during incidents)
    • Keep label cardinality low
      • InfluxDB builds an index per label
  • Collection: pull vs push — how 10M metrics leave 100,000 machines
    • Pull: collectors scrape /metrics endpoints found via service discovery (ZooKeeper / etcd)
      • Consistent hash ring so each server is scraped by exactly one collector
    • Push: agent on each host pushes (may pre-aggregate) to collectors behind a load balancer + autoscaling
      • Prometheus = pull; CloudWatch, Graphite = push
  • Transmission + storage: Kafka → time-series DB — the heart of the design; decouples ingest from storage and keeps data safe
    • Kafka buffer, partitioned by metric name (then labels); Flink / Spark / Storm consumers
      • Alternative: Gorilla-style ingestion to avoid Kafka's ops overhead
    • Purpose-built TSDB (InfluxDB, Prometheus), not a general-purpose DB
      • InfluxDB: 250k+ writes/s on 8 cores, 32GB RAM
    • Encoding (delta / double-delta), down-sampling, cold storage
      • ~85% of queries hit the last 26h (Facebook research)
  • Read side: query service, alerting, visualization — where data turns into decisions and pictures
    • Query service + cache in front of the TSDB (optional)
    • Alert manager: YAML rules, dedupe/merge, alert store, Kafka, alert consumers → email, SMS, PagerDuty, webhooks
    • Visualization: off-the-shelf Grafana
      • Alerting too is usually bought, not built

The data model is the root because it dictates the database choice, the Kafka partitioning, and the query language. Collection and transmission exist to feed the storage hub safely at scale; the read side exists only to interrogate it. If storage is chosen poorly, both dashboards and alerts become slow, which is why the notes call data storage "the heart of this design."

Follow one metric

  1. Instance i631 in the us-west web pool exposes CPU.load host=i631,region=us-west 1613707265 76 at its /metrics endpoint.
  2. A collector owns i631 on the consistent hash ring. It got the target, pull interval, timeout and retry settings from service discovery, and scrapes on schedule.
  3. The collector writes the point to Kafka, into the partition for metric name CPU.load.
  4. A Flink consumer reads the partition and writes the point to InfluxDB, which stores the timestamp as a small delta from the previous one rather than a full 10-digit number.
  5. Every interval, the alert manager runs its cached rules through the query service, e.g. "average CPU load across us-west web servers over the last 10 minutes."
  6. Separately, the rule instance_down: up == 0 for 5m fires for a neighbor host. The alert manager merges repeats into one alert event, records its state in the alert store, and publishes it to Kafka.
  7. An alert consumer pulls the event and pages the on-call engineer via PagerDuty; she opens Grafana, which queries the same service (hot results come from cache).
  8. Seven days later, this 10-second point is rolled into a 1-minute average; after 30 days, into a 1-hour average; eventually it can move to cheap cold storage.

3 Purpose & Concept Beacons

Reliably ingest a write-heavy firehose of infrastructure metrics, store it compactly for a year, and answer dashboard and alert queries with low latency so no critical alert is ever missed.

Mental picture

Imagine a national weather service. Thousands of weather stations are the metric sources, either waiting for inspectors to read them (pull) or radioing readings in (push). The central post room that queues incoming reports so nothing is lost when the archivists are overwhelmed is Kafka. The climate archive, which keeps hourly detail for recent days but only daily summaries for past years, is the time-series database with its down-sampling rules. The forecasters' desk that answers questions about the data is the query service, the storm-warning office that sounds sirens when thresholds are crossed — once, not fifty times — is the alert manager, and the big wall of weather maps is Grafana.

4 Opportunistic Drilling

Interviewers probe five areas: why a time-series DB, the push vs pull debate, the Kafka-buffered pipeline and where to aggregate, storage compression and down-sampling, and the alert manager's duties.

Why a purpose-built time-series database

A general-purpose relational database could be tuned to cope, but only with expert-level effort. A NoSQL store can work in theory, yet designing a scalable schema for time-series queries is hard. Purpose-built time-series databases — InfluxDB and Prometheus are the most popular — pair an in-memory cache with on-disk storage and ship query languages made for this data.

Consider the notes' example: an exponential moving average takes a nest of three sub-queries and window functions in SQL. In InfluxDB's Flux it is four short lines: pick the database, set a range of -1h, filter by measurement, apply exponentialMovingAverage. The shape of the language matches the shape of the data.

TSDBs also aggregate efficiently by label because they index labels. The flip side is cardinality: every distinct label value adds to the index, so labels like a unique request ID would blow it up.

Common trap: diving into TSDB internals. The notes say that is niche knowledge; for the interview, it is enough to know metrics are time-series data, to name InfluxDB/Prometheus, and to cite a number like 250k+ writes/s on an 8-core, 32GB box.

Pull vs push collection

In the pull model, collectors fetch from each service's /metrics endpoint. They learn what to scrape — IPs, intervals, timeouts, retries — from service discovery (ZooKeeper or etcd), either by subscribing to change notifications or by polling. Many collectors share the load via a consistent hash ring, so each server has exactly one owner. In the push model, an agent on each host sends metrics to collectors that sit behind a load balancer in an autoscaling group, since they may otherwise reject pushes under load.

There is no clear winner. Prometheus pulls; CloudWatch and Graphite push. A large organization probably needs both, especially where installing a push agent is not even possible.

The Kafka-buffered pipeline and where to aggregate

Collectors in autoscaling groups handle ingest spikes, but if the time-series database goes down, incoming data has nowhere to land. Placing Kafka between collectors and the database solves this: Kafka retains data until consumers (Storm, Flink, Spark) can write it, and it cleanly separates collection from processing.

Partition Kafka by metric name so consumers can aggregate per metric; for more scale, partition further by labels and prioritize important metrics. The main cost is operational overhead; a Gorilla-style ingestion system is an arguably equally scalable alternative.

Storage tricks: encoding, down-sampling, cold storage

Because about 85% of queries target the past 26 hours, the storage layer should be built around recent data being hot and old data being cheap. Three levers do this.

  1. Encoding and compression: store differences between neighboring timestamps instead of full values; good TSDBs do this built-in.
  2. Down-sampling: keep raw for 7 days, then 1-minute resolution to 30 days, then 1-hour to a year. In the notes' example, six 10-second CPU readings (10, 16, 20, 30, 20, 30) become two 30-second averages (19 and 25).
  3. Cold storage: move rarely used old data to much cheaper storage.
Gains

Dramatically less disk; queries over long ranges touch fewer points.

Costs

Old data loses fine detail forever; a spike lasting 20 seconds last month may vanish into a 1-hour average.

The alerting pipeline

Alert rules are written in YAML and loaded into a cache. The alert manager reads them, queries the query service at the configured interval, and creates an alert event when a rule is met — e.g. up == 0 held for: 5m with severity: page.

The alert manager's other duties matter as much as detection: filtering, merging and deduplicating (one instance firing repeatedly yields one event), access control over who can manage alerts, and retries so each alert is delivered at least once. The alert store (a key-value DB such as Cassandra) tracks every alert's state to back that guarantee, and Kafka decouples detection from the notification senders.

Common trap: proposing to build alerting and dashboards from scratch. The notes stress that off-the-shelf options (and Grafana for visualization) are hard to justify not using.

Test yourself

Jot your answer in the margin with your stylus, then tap to reveal.

Why put Kafka between the metrics collectors and the time-series database?

If the database goes down, collectors would otherwise lose data. Kafka retains the stream until consumers can write it, decouples collection from processing, and scales reliably. The trade-off is operational overhead.

Name two situations where push beats pull.

Short-lived batch jobs that end before a scrape, and firewalled or multi-data-center setups where collectors cannot reach every endpoint. With push, collectors behind a load balancer and autoscaling group can receive data from anywhere.

What goes wrong if two pull-based collectors scrape the same server?

Metrics are collected twice, wasting resources and duplicating data. A consistent hash ring assigns each server to exactly one collector, preventing overlap.

Compare aggregating in the ingestion pipeline vs at query time.

Ingestion-time aggregation (e.g. in Flink) shrinks write volume but discards raw data and precision. Query-time aggregation preserves everything but can make queries slow because of the sheer data processed.

Why keep label cardinality low?

Time-series databases like InfluxDB index each label. Many unique label values inflate those indexes, hurting memory and query performance.

A single instance triggers the same rule 30 times in 10 minutes. What should the on-call engineer receive?

One alert. The alert manager filters, merges and deduplicates alerts, while the alert store tracks state so the notification is sent at least once but not spammed.

How does the "85% of queries in the last 26h" finding shape storage?

It justifies optimizing for recent data: keep recent data at full resolution and fast, down-sample older data (1-minute, then 1-hour), and push old data to cheap cold storage.
