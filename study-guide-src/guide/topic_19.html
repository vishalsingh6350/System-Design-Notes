Picture this

It is a Friday-night flash sale. Checkout services are firing order events by the thousands per second, while the inventory system, the email sender, the fraud checker and the analytics pipeline all need to read those same events — each at its own pace. If checkout had to call every downstream service directly and wait, one slow email server would stall every purchase. So you drop a conveyor belt in the middle: producers place messages on it and walk away, and consumers pick them up when ready. Now make that belt survive disk failures, keep every message in order for two weeks, let many teams replay it independently, and let each team choose whether a lost or duplicated message is worse. That belt is a distributed message queue.

1 Macro Structure & Dependency Map

At the top sits one abstraction — the partitioned, append-only log — and everything else is about writing to it fast, reading from it in groups, keeping copies of it, and choosing guarantees on top. Read hubs first; the grey peripheral items are safe to skim.

  • Topics, partitions and brokers — the unit of scaling and ordering; every other decision is "per partition"
    • Partition = ordered FIFO log; position is the offset
      • Message located by (topic, partition, offset)
    • Partition key: hash(key) % numPartitions, e.g. user_id keeps one user's events ordered
      • Keys need not be unique, may even be missing; producer can override routing
    • Adding / removing partitions
      • New partitions take only new messages; decommissioned ones linger until retention expires
  • Storage: write-ahead log on disk + batching — how the system hits high throughput with two-week retention
    • Append-only WAL split into segments; only the newest segment is writable
      • Sequential access makes HDDs fast; OS disk cache does the rest
    • Immutable message schema shared by producer, broker, consumer (no extra copying)
      • Fields: key, value, topic, partition, offset, timestamp, size, CRC
    • Batching everywhere: throughput vs latency dial
  • Consumer groups and rebalancing — how many readers share work without breaking order
    • Each group keeps its own offset; one consumer per partition within a group
    • Pull model (consumer controls rate), long polling for idle periods
    • Coordinator broker (found by hashing group name) + group leader builds partition plan
      • Triggered by join, leave, missed heartbeats, partition changes
  • Replication, ISR and acks — durability and availability; the knob between speed and safety
    • One leader replica per partition; followers pull from it
    • In-sync replicas (ISR) defined by replica.lag.max.messages
    • ACK=0 / 1 / all
      • Broker failure: new leader elected, partitions redistributed; replicas across brokers (and ideally DCs)
  • Delivery semantics — the user-facing contract built from ack settings and offset-commit order
    • At-most-once, at-least-once, exactly-once
    • Advanced: tag-based filtering, delayed / scheduled messages, retry topics, archive to HDFS/S3

Partitions are the root: they are what brokers host, what gets replicated, what consumers are assigned, and the only scope in which order is guaranteed. Storage explains how a single partition is fast; consumer groups explain how many partitions are read; replication explains how partitions survive; and delivery semantics are simply the combination of replication acks on the write side and offset-commit timing on the read side. ZooKeeper sits beside all of them as the keeper of metadata, consumer state and leader election.

2 Black-Box Cause & Effect Flow

Follow the causal chain from producer to consumer; each box transforms something concrete and hands it to the next.

Producer (with embedded routing + buffer)

Input: Application events, the cached replica plan from metadata storage.

Output: Batches of messages sent directly to the leader broker of each target partition.

A mail sorter who bundles letters by destination before driving to the right post office, instead of dropping each letter at a central depot.

→ feeds into: Leader replica of the partition

Leader broker + WAL

Input: A batch for Topic-A Partition-1.

Output: Messages appended sequentially to the active segment, each assigned the next offset.

A ship's logbook written only at the last line in ink; old pages are never erased, just shelved.

→ feeds into: Follower replicas

Follower replicas (ISR)

Input: Fetch requests pulling new messages from the leader.

Output: Copies of the log; once all ISR members have a message, it is committed.

Apprentice scribes copying the master logbook; a page counts as official only when every up-to-date scribe has it.

→ feeds into: Acknowledgment to producer (per ACK setting); committed offset

Group coordinator

Input: Join / leave requests and heartbeats from a consumer group.

Output: A partition dispatch plan (built by the elected group leader) broadcast to members.

A shift manager who reassigns checkout lanes whenever a cashier arrives, leaves, or stops answering.

→ feeds into: Consumers' partition assignments

Consumer (pull)

Input: Its assigned partition and last committed offset from state storage.

Output: Processed messages and a newly committed offset.

A reader with a bookmark: open to the bookmark, read a chapter, move the bookmark. When you move it decides whether you might skip or re-read a page.

→ feeds into: State storage (ZooKeeper) — offsets

ZooKeeper (metadata + state + coordination)

Input: Topic configs, replica distribution plans, consumer offsets, broker liveness.

Output: Consistent answers to "who leads this partition?", "where did group 1 stop?", "which brokers are alive?"

The harbor master's office: it does not carry cargo, but every ship checks in there.

→ feeds into: Brokers, producers' routing cache, consumers

Follow one message

  1. Checkout emits order_placed for user 4821. The producer computes hash("4821") % 4 = partition 2 of topic orders, so all of this user's events stay in order.
  2. The message waits a few milliseconds in the producer's in-memory buffer until a batch forms, then is sent in one request to Broker-1, the leader for partition 2 per the cached replica plan.
  3. Broker-1 appends the batch to the active segment of partition 2's WAL; our message gets offset 15.
  4. Followers on Broker-2 and Broker-3 fetch it. Both are in the ISR, so once both have offset 15 it is committed.
  5. The producer used ACK=all, so only now does it receive its acknowledgment. Had it used ACK=1, it would have been acknowledged right after step 3.
  6. Consumer group "inventory" has three consumers; the coordinator assigned partition 2 to consumer C2. C2 pulls from its last committed offset, 13, and receives offsets 13–15 in one chunk.
  7. C2 decrements stock, then commits offset 16 to state storage. Processing before committing gives at-least-once delivery.
  8. Independently, group "analytics" reads the same message from the same partition with its own offset — possibly days later, since retention is two weeks.

3 Purpose & Concept Beacons

Decouple producers from consumers with a durable, ordered, replayable log that scales horizontally and lets each use case tune its own balance of throughput, latency and delivery guarantees.

Mental picture

Picture a railway freight yard. Each topic is a destination line, split into several parallel tracks — the partitions — so more trains can load at once. Cars are coupled only at the end of a track and never removed mid-line: that is the append-only WAL with offsets as car numbers. Station depots holding the tracks are brokers, and each track has one master depot (the leader) with backup depots mirroring it (followers, the ISR). Unloading crews are consumer groups: within one crew, each worker owns a whole track so cars come off in order, while a different crew can unload copies of the same cars on its own schedule. The yard office with the timetable, crew rosters and "last car unloaded" ledger is ZooKeeper.

4 Opportunistic Drilling

These five sections carry most interview weight: why a log on disk is fast, how consumer groups keep order, how replication and acks trade speed for safety, what each delivery guarantee really means, and why routing lives inside the producer.

Storage: the append-only log and why disks are not slow

Message traffic has a distinctive shape: heavy writes, heavy reads, no updates or deletes, and overwhelmingly sequential access. A general-purpose database handles that combination poorly. A write-ahead log — a file you can only append to — fits it perfectly.

The common belief that hard drives are slow is really about random access: moving the disk head around. When writes stream sequentially, HDDs deliver ample throughput, and the operating system aggressively caches disk data in memory, so recent messages are often served from RAM. Keeping messages immutable and using the same schema from producer to broker to consumer avoids re-copying bytes along the way.

Batching amplifies all of this. Grouping messages amortizes network round trips and turns many small writes into large sequential ones. The cost is latency: a message waits for its batch to fill.

Large batches

Higher throughput, fewer requests, better disk and cache efficiency — ideal for log aggregation.

Small batches

Lower latency for traditional queue use cases, but lower throughput; you may need more partitions per topic to compensate.

Consumer groups, pull, and rebalancing

A consumer group is a team sharing the work of reading a topic. Messages are delivered once per group, not once per consumer, and each group keeps its own offset. Reading in parallel boosts throughput but threatens order, so the rule is: within a group, a partition is read by only one consumer. Hence a group can never usefully have more consumers than there are partitions.

Consumers pull rather than being pushed to. Push gives lower latency but can overwhelm a slow consumer, since the broker sets the pace. Pull lets each consumer fetch as much as it can handle, which suits batch processing; the downside of empty polls is softened by long polling.

  1. A consumer joins, leaves, or misses heartbeats (or partitions change).
  2. The coordinator broker — chosen by hashing the group name — tells members to rebalance in its heartbeat responses.
  3. All members rejoin; the coordinator elects a group leader.
  4. The leader computes a new partition dispatch plan (round-robin, range, etc.) and sends it to the coordinator.
  5. The coordinator broadcasts the plan; consumers resume from the committed offsets in state storage.
Common trap: confusing the group coordinator (a broker) with the coordination service (ZooKeeper). The notes explicitly separate them: the coordinator manages consumer group membership; ZooKeeper handles broker discovery, metadata and leader election.

Replication, ISR and the ACK knob

Each partition is copied to several brokers. One copy is the leader: producers write to it and, in the simplest design, consumers read from it too. Followers pull new messages from the leader. The leader creates the replica distribution plan and stores it in ZooKeeper, and it tracks how far behind each follower is.

SettingProducer acknowledged whenSpeedDurability
ACK=0Never waitsFastestLowest
ACK=1Leader has the messageFastLow (lost if leader dies before followers copy)
ACK=allAll ISR replicas have itSlowestHighest

The ISR concept is itself a trade-off. Requiring every replica to sync guarantees nothing is lost, but one sluggish replica would stall the partition; letting laggards drop out of the ISR keeps writes flowing. When a broker fails, a new leader is elected and the failed broker's partitions are redistributed; new replicas act as followers until they catch up and join the ISR. When a broker is added, the system can temporarily run with extra replicas until the newcomer is caught up, then remove the surplus.

Common trap: placing all replicas of a partition on one broker. That wastes resources and protects nothing; replicas must sit on different brokers, and ideally in different data centers (at a latency cost, or via data mirroring).

Delivery semantics: where you place the commit

The three guarantees are not magic modes; they fall out of two choices: how the producer handles acknowledgments and retries, and whether the consumer commits its offset before or after processing.

GuaranteeProducerConsumerRisk
At-most-onceAsync send, no retryCommit offset immediately, then processLoss if crash before processing
At-least-onceack=1 or all, retries on failureProcess, then commitDuplicates if crash after processing, before commit
Exactly-onceFriendliest for users, extremely costly for the systemComplexity and cost

At-least-once is the requirement the notes insist on: nothing is left unprocessed, but duplicates can appear on both the producer-to-queue and queue-to-consumer hops. It fits use cases where duplication is acceptable or where consumers can deduplicate.

Common trap: assuming acks alone decide the guarantee. A producer on ACK=all still yields at-most-once behavior if the consumer commits its offset before processing.

Why routing moves inside the producer

A producer must send each message to the leader of its partition. A separate routing layer could look up the replica plan and forward messages, but that adds a network hop and prevents batching. Embedding routing and a buffer in the producer library fixes both.

Benefits: fewer hops mean lower latency, producers control which partition a message lands in, and the buffer enables larger batches for throughput. Around the edges, the notes add advanced features: tag-based filtering so consumers skip irrelevant messages without extra topics, delayed messages parked in temporary topics and released by delay queues or a hierarchical time wheel, retry topics, and archiving old data to HDFS or S3.

Test yourself

Answer in the margin with your stylus before revealing each one.

Why can a consumer group not benefit from more consumers than partitions?

To preserve order, each partition is read by only one consumer within a group. With more consumers than partitions, the extras have nothing assigned and sit idle. To scale further, add partitions.

Why is a WAL on HDD fast enough, despite HDDs' reputation?

HDD slowness comes from random access. Message queues write and read sequentially, which HDDs handle well, and the OS caches disk data in memory aggressively. Batching makes the writes even larger and more sequential.

What happens if a consumer crashes after processing a message but before committing its offset?

A replacement consumer resumes from the last committed offset and processes the message again, producing a duplicate. That is the at-least-once trade-off; downstream must tolerate or deduplicate.

Compare ACK=1 and ACK=all.

ACK=1 acknowledges once the leader has the message: fast, but a leader crash before followers copy it loses the message. ACK=all waits for every ISR replica: slower, but highest durability.

A follower replica falls far behind the leader. What happens?

If it lags more than replica.lag.max.messages, the leader removes it from the ISR, so commits no longer wait for it. It rejoins once it catches up. This prevents one slow replica from making the partition unavailable.

Why is decreasing partitions harder than adding them?

A decommissioned partition still holds unconsumed messages, so it cannot be deleted immediately. Producers stop writing to it while consumers keep reading until the retention period expires; only then is data truncated and consumers rebalanced.

Why do most message queues choose pull over push for consumers?

Pull lets each consumer control its rate, so slow consumers are not overwhelmed and can be scaled to catch up, and it allows aggressive large-batch fetching. The cost — latency and empty polls — is reduced by long polling.
