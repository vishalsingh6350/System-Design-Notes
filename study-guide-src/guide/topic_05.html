Picture this

It is 9 p.m. on a Friday and your cache cluster of four servers is humming along, each one holding a quarter of your hottest keys. Then server 1 quietly dies. With the classic formula hash(key) % N, N drops from 4 to 3, and in one instant almost every key on every surviving server now "belongs" somewhere else. The caches are still full of data, but nobody is looking in the right place: a storm of cache misses slams straight into your database. Consistent hashing exists so that losing (or adding) one server disturbs only the keys that server actually touched.

1 Macro Structure & Dependency Map

From 10,000 feet this chapter is one problem, one shape, one lookup rule and one fix. Read the map top-down: each hub is a load-bearing idea; the grey peripheral items are details you can reconstruct once the hub is solid.

  • The rehashing problem — the pain that motivates everything else
    • serverIndex = hash(key) % N works while N is fixed
      • Example: 4 servers, keys spread by hash % 4
    • Change N and most keys remap
      • Server 1 goes offline → hash % 3 → most keys land on a new server → cache misses
  • The hash ring — the shape that makes change local instead of global
    • Hash space 0 to 2^160 − 1 (e.g. SHA-1), ends joined into a circle
      • Same hash function f places both servers (by IP or name) and keys
    • Clockwise lookup rule: a key belongs to the first server found walking clockwise
  • Adding & removing servers — the payoff: only one arc of keys moves
    • Added server: keys between it and its anticlockwise predecessor move to it
    • Removed server: keys between its predecessor and it move to the next server clockwise
      • Worked examples: s4 added between s3 and s0; s1 removed, its keys go to s2
  • Virtual nodes — the fix that makes the ring fair
    • Problems with the basic ring: uneven partition sizes, non-uniform key distribution
    • Each server appears many times on the ring
      • More virtual nodes → smaller standard deviation → more balanced load

The rehashing problem is the "why"; the ring is the "how"; the add/remove behaviour is the proof that the ring works; virtual nodes patch the one weakness the plain ring still has. Each hub leans on the previous one, so if you can draw the ring and trace a key clockwise, the rest follows.

2 Black-Box Cause & Effect Flow

Treat each step as a sealed box: something goes in, something comes out, and the output of one is the input of the next. This is the causal chain from "a key arrives" to "the cluster changed and barely noticed".

Hash function f (e.g. SHA-1)

Input: a key string, or a server's IP/name.

Output: a number in the range 0 to 2^160 − 1.

A blender that turns any name into a seemingly random position number. The same input always lands in the same place, which is what makes lookups repeatable.

→ feeds into: placement on the ring

Ring placement

Input: hash values for every server and every key.

Output: points dotted around a circle (s0, s1, s2... and k0, k1, k2...).

Bend the number line until 2^160 − 1 touches 0, and you get a clock face. Servers and keys now share one geography.

→ feeds into: clockwise lookup

Clockwise lookup

Input: a key's position on the ring.

Output: the owning server — the first server met walking clockwise.

Each server "owns" the arc of ring just behind it (anticlockwise). A key simply walks forward until it bumps into an owner.

→ feeds into: routing the read/write to that server

Membership change (add or remove)

Input: a server joining or leaving the ring.

Output: one arc of keys changes owner; every other key stays put.

Adding a house on a circular street only changes the postman's route for the stretch just before the new house.

→ feeds into: minimal redistribution (the whole point)

Virtual nodes

Input: each physical server, replicated as many labelled points (s0_0, s0_1, s0_2...).

Output: many small, interleaved arcs per server instead of one big lopsided arc.

Instead of one big slice of pie per guest, everyone gets many thin slices scattered around the dish, so nobody ends up with half the pie by accident.

→ feeds into: balanced load, no hotspots

Follow one key

  1. A request arrives for key0. The system runs it through the same hash function f used for the servers.
  2. The resulting hash lands key0 near the top of the ring, just anticlockwise of server s0.
  3. Walking clockwise, the first server met is s0, so s0 stores and serves key0.
  4. Traffic grows and you add s4. Its hash places it on the ring between key0 and s0.
  5. Now the clockwise walk from key0 hits s4 first, so key0 moves to s4.
  6. Which keys moved? Only those between s4 and its anticlockwise predecessor s3. key1, key2 and key3 never notice.
  7. Later s1 fails. Only keys between s0 and s1 are affected, and they slide clockwise to s2. Everything else keeps hitting a warm cache.

3 Purpose & Concept Beacons

Consistent hashing lets you scale horizontally by guaranteeing that a change in server count remaps only a fraction of keys, while virtual nodes keep the data spread evenly enough to avoid hotspots.

Mental picture

Imagine a circular running track with lockers bolted at random spots around it — those lockers are your servers, placed by hashing their names. Every runner (a key) starts at a spot determined by their own hash and jogs clockwise until they reach the first locker, and that is where their bag lives. Bolt a new locker onto the track and only the runners who started in the short stretch just before it change lockers; everyone else jogs to the same place as before. Rip a locker out and only its runners jog a little further to the next one. Finally, to stop one locker from covering a huge empty stretch of track, each owner bolts many small lockers all around the loop — those are virtual nodes — so every owner covers a fair share of the distance.

4 Opportunistic Drilling

Three ideas carry nearly all the exam and interview weight: why modulo hashing breaks, exactly which keys move on the ring, and why virtual nodes are non-negotiable. Drill these; skim the rest.

Why modulo hashing collapses when N changes

With four servers, serverIndex = hash % 4 spreads keys neatly: key1 and key3 on server 0, key0 and key4 on server 1, and so on. The formula is perfectly fine as long as the pool never changes size.

Now server 1 goes offline. The formula becomes hash % 3, and because the divisor changed, the remainder changes for most keys — not just the ones that lived on server 1. Keys that were happily cached on servers 0, 2 and 3 are suddenly routed elsewhere. The data is still sitting in memory; clients are just knocking on the wrong door.

Common trap: saying "only the dead server's keys are lost". With modulo hashing the damage is global — most keys on healthy servers are remapped too, which is what causes the cache-miss storm.

Exactly which keys move on the ring

The rule to memorise: start at the server that changed and walk anticlockwise until you hit the next server. That arc is the affected range. Nothing outside it moves.

When a server is added, the keys in that arc used to walk past the gap and land on the next server clockwise; now the new server intercepts them. When a server is removed, the keys in its arc keep walking clockwise and land on its successor.

Common trap: mixing up directions. Lookup walks clockwise; finding the affected range walks anticlockwise. Say both out loud when you draw it.

Virtual nodes: turning a lumpy ring into a fair one

The plain ring has two flaws. Server positions are effectively random, so with only a handful of servers one might own a huge arc while another owns a sliver (uneven partition sizes). And keys themselves may bunch up, so one server receives far more than its share (non-uniform key distribution).

The fix is to place each server on the ring many times. Server 0 becomes s0_0, s0_1, s0_2; server 1 becomes s1_0, s1_1, s1_2. Each physical server now owns many short, interleaved arcs. Statistically, the more virtual nodes you add, the smaller the standard deviation of load, and the more balanced the data.

Gains

Much more even load; fewer hotspots; when a server leaves, its many small arcs are spread across many neighbours rather than dumped on one.

Costs

More positions to store and search on the ring — extra metadata in exchange for balance.

Why it matters: the three benefits

  1. Minimised redistribution — only a fraction of keys move when servers come and go.
  2. Horizontal scalability — you can add servers without a cluster-wide reshuffle.
  3. Hotspot mitigation — with virtual nodes, data is balanced so no single server is overloaded.

These are why Amazon DynamoDB, Apache Cassandra, Discord, Akamai's CDN and the Maglev load balancer all lean on consistent hashing. In the next chapter, the key-value store uses this exact ring for partitioning and replication.

Test yourself

Sketch a ring in the margin and answer with your stylus before tapping to reveal.

Why does hash(key) % N cause a cache-miss storm when one server dies?

Because N changes, the remainder changes for most keys, not just those on the dead server. Keys still cached on healthy servers are routed to different servers, so lookups miss even though the data exists.

How is the owning server of a key found on the hash ring?

Hash the key onto the ring with the same function used for servers, then walk clockwise from its position. The first server encountered owns the key.

What happens if server s1 is removed from the ring, with s0 before it and s2 after it?

Only keys between s0 and s1 are affected. They continue clockwise and are reassigned to s2. All other keys keep their servers.

You add s4 between s3 and s0. Which keys move and to where?

The keys in the arc from s3 up to s4 (walking anticlockwise from s4 until you hit s3). They used to go to s0; now they stop at s4.

What two problems does the basic ring have, and what fixes them?

Uneven partition sizes and non-uniform key distribution. Virtual nodes fix both by giving each server many ring positions, which shrinks the standard deviation of load.

Compare modulo hashing and consistent hashing when a server is added.

Modulo hashing reshuffles most keys across all servers because the divisor changes. Consistent hashing moves only the keys in one arc to the new server; everything else stays.

What would happen with too few virtual nodes per server?

Arc lengths would vary a lot, so load would be lopsided and some servers would become hotspots. More virtual nodes means lower standard deviation and more balanced data.
