Picture this

A game studio announces a free in-game reward, one per account. Within minutes a bot farm is hammering the claim endpoint thousands of times a second, creating throwaway accounts and draining the reward pool, while real players stare at spinning loaders because the servers are drowning. Your cloud bill climbs by the minute. What you need is a bouncer at the door who counts, remembers, and politely says "not yet" with an HTTP 429 when someone is coming in too fast. That bouncer is a rate limiter, and the hard part is making it fast, accurate and consistent when it is running on many servers at once.

1 Macro Structure & Dependency Map

The design splits into four questions: what must it do, where does it sit, how does it count, and how does it stay correct at scale. The algorithm hub is the heart; the others are the body built around it.

  • Requirements & purpose — they decide which algorithm and placement are acceptable
    • Why: prevent DoS/resource starvation, reduce cost, prevent overload
      • Real uses: limiting posts, account creations, reward claims
    • Must: accurate throttling, minimal latency, low memory, distributed, clear exceptions, high fault tolerance
      • Server-side API limiter, multiple throttle rules, inform users when throttled
  • Placement — determines whether the limiter can be trusted and how it fits the stack
    • Client-side: unreliable (can be tampered with)
    • Server-side: preferred for control
    • Middleware / API gateway: flexible, natural with microservices
      • Guidelines: match current tech stack, pick algorithm by business needs, buy commercial if resources are limited
  • Counting algorithms — the core decision; each trades accuracy, memory and burst behavior differently
    • Token bucket: refill at fixed rate, each request spends a token
      • Parameters: bucket size, refill rate
    • Leaking bucket: FIFO queue drained at a fixed rate
      • Example implementation: uber-go/ratelimit
    • Fixed window counter: one counter per time slot
      • Edge-burst flaw
    • Sliding window log: store timestamps; sliding window counter: weighted blend of windows
  • Architecture & distributed correctness — one limiter is easy; many limiter instances sharing counters is the real problem
    • Counters in in-memory cache (Redis); middleware checks, then forwards or rejects
    • Race conditions and sync: locks, Lua scripts, Redis sorted sets, centralized store
      • Multi-data center for latency, eventual consistency, monitoring and rule tuning

Requirements come first because "low memory" and "accurate" pull in opposite directions and force the algorithm choice. Placement decides where the counting happens; the algorithm decides how; and the Redis-backed architecture decides whether that counting still holds when dozens of servers are counting at once. The algorithms hub is where interviewers spend the most time.

2 Black-Box Cause & Effect Flow

Every request passes the same short gauntlet: identify, count, compare, decide. Each box is small and fast, because the limiter sits on the hot path of every call.

Client

Input: A user action, e.g. "claim reward".

Output: An HTTP request sent toward the API.

A guest walking up to the club door. You cannot trust the guest to count their own entries, which is why client-side limiting is unreliable.

→ feeds into: rate limiter middleware

Rate limiter middleware (API gateway)

Input: The request plus an identity to limit on (such as a user or IP) and the matching throttle rule.

Output: A lookup of the relevant counter or bucket in Redis.

The bouncer checking the guest list before letting anyone near the bar.

→ feeds into: Redis counter store

Redis counter store

Input: A key for this client and window/bucket.

Output: The current count or token level, updated atomically.

A shared tally board in memory that every bouncer at every door reads and writes, fast because it never touches disk.

→ feeds into: algorithm decision

Algorithm decision

Input: Current count/tokens and the rule's limit.

Output: Allow or throttle.

The rulebook: "no more than N entries per minute" or "one token per entry".

→ feeds into: API servers (allowed) or a throttled response (rejected)

API servers

Input: Only the requests that passed.

Output: Normal responses, with servers kept below overload.

The bar inside the club, never more crowded than it can serve.

→ feeds into: the client's response

Throttled response + monitoring

Input: Rejected requests and analytics about them.

Output: A clear error telling the user they are throttled (commonly HTTP 429 Too Many Requests), plus data used to tune rules.

The bouncer saying "come back in a minute", and the manager later reviewing the door log to decide if the rules are too strict or too loose.

→ feeds into: rule and algorithm adjustments

Follow one request

  1. A player taps "Claim reward". The app sends a request to the API gateway, not directly to the reward service.
  2. The middleware identifies the caller and finds the matching throttle rule, say a token bucket of size 4 refilled with 4 tokens per minute.
  3. It reads the player's bucket from Redis: 1 token left. Because Redis is in memory, the lookup adds only minimal latency.
  4. The request consumes the token (bucket now 0) and is forwarded to the API servers, which process the claim.
  5. A bot using the same account fires a second request 2 seconds later. The bucket is empty, so the middleware rejects it immediately and the API servers never see it.
  6. The client receives a clear throttled error (commonly HTTP 429) and knows to back off, rather than silently failing.
  7. The refiller adds tokens at the next interval; the player's legitimate next claim goes through.
  8. Meanwhile monitoring shows how many requests were dropped, so the team can adjust the bucket size or refill rate if real players are being blocked.

3 Purpose & Concept Beacons

A rate limiter controls how fast clients or services may send traffic, protecting servers from abuse, cost blowouts and overload. The design is a choice of placement and counting algorithm, backed by a fast shared counter store that stays correct under concurrency.

Mental picture

Picture a nightclub. The bouncer at the door is the rate limiter middleware: it stands in front of the club (the API servers) so the crowd inside never exceeds capacity. The clicker counter in the bouncer's hand is the Redis counter; when a club has several doors, all bouncers share one tally board, which is why the store must be centralized and updated atomically. The house rules ("four guests a minute", "one wristband per entry") are the algorithm and its parameters. A guest turned away is told why and when to return, which is the throttled response. And the manager reviewing the door logs each night is monitoring, tuning the rules so real customers are not left outside.

4 Opportunistic Drilling

Interviewers probe the algorithms hardest, especially token bucket and the fixed-window edge problem, then the distributed race condition. Placement is quick but must be justified.

Where the limiter lives

A client-side limiter is unreliable: a malicious client can simply remove or bypass it. Server-side limiting gives you control. A popular middle path is middleware, often an API gateway, sitting between clients and API servers so that throttled requests never reach your business logic.

  1. Evaluate your current tech stack and choose the option that fits it efficiently.
  2. Select the algorithm that matches business needs.
  3. If you already use microservices with an API gateway, put the limiter there.
  4. If engineering resources are limited, a commercial solution may be the better choice.

Token bucket: the default workhorse

Imagine a bucket that holds a fixed number of tokens. A refiller drops new tokens in at a steady rate; once the bucket is full, extra tokens overflow and are lost. Each incoming request must take one token. If a token is available, the request passes; if the bucket is empty, the request is dropped.

Because tokens accumulate while traffic is quiet, a short burst up to the bucket size can pass all at once. That makes it forgiving for real users, and it needs only a count and a timestamp per bucket, so it is memory-efficient.

Gains

Easy to implement, memory-efficient, and allows short bursts of traffic.

Costs

Two parameters, bucket size and refill rate, can be tricky to tune correctly.

Comparing the five algorithms

The leaking bucket is the token bucket's strict sibling: requests enter a FIFO queue and are processed at a fixed rate, like water dripping from a hole. The outflow is perfectly steady, but a burst fills the queue with old requests and newer ones wait or are dropped.

The window-based algorithms count requests in time. The fixed window counter uses one counter per interval and resets it at each boundary. The sliding window log stores every request's timestamp and counts only those inside the rolling window. The sliding window counter estimates the rolling count from the current window's count plus a weighted share of the previous window's.

The fixed-window edge problem

A fixed window counter looks airtight: "5 requests per minute, reset on the minute". But the counter only knows about its own slot. If a client sends 5 requests in the last seconds of one minute and 5 more in the first seconds of the next, both windows see a legal 5, yet 10 requests passed within a few seconds.

This is the classic weakness interviewers want you to spot, and it is exactly why the sliding window variants exist: they measure a rolling window, so a burst straddling the boundary is still counted together.

Common trap: saying the fixed window is "accurate" because each window respects its limit. Its failure is precisely at the edges, where a rolling view would reject the extra requests.

Distributed correctness with Redis

Counters live in Redis because in-memory operations are fast enough to sit on every request's path. The flow is simple: the client hits the middleware, the middleware checks and updates the counter in Redis, and the request is processed or rejected.

The danger appears with many limiter instances. If two instances read "count = 3" at the same moment, both increment to 4 and both allow, even though one should have been blocked. That is a race condition. Locks fix it but slow everything down; Lua scripts run the read-and-update as one atomic step inside Redis; sorted sets suit timestamp-based sliding windows. A centralized data store keeps every instance looking at the same numbers.

Test yourself

Sketch or write your answer in the margin with your stylus, then reveal.

Why is client-side rate limiting considered unreliable?

The client is under the user's control, so a malicious user can modify or bypass it. Server-side or middleware limiting keeps enforcement where you control it.

Compare token bucket and leaking bucket.

Token bucket refills tokens at a fixed rate and lets requests through as long as tokens remain, so it allows bursts up to the bucket size. Leaking bucket queues requests in FIFO order and processes them at a fixed rate, giving a stable outflow but delaying recent requests during bursts. Both are memory-efficient.

What happens with a fixed window counter if a burst lands at a window boundary?

Requests at the end of one window and the start of the next are counted separately, so each window stays under its limit while the combined burst exceeds the quota. Sliding window algorithms fix this by measuring a rolling window.

Why would you choose a sliding window counter over a sliding window log?

The log is accurate but stores a timestamp per request, which consumes a lot of memory. The counter approximates the rolling count from two window counters, so it is memory-efficient and still smooths spikes, at the cost of not being perfectly strict.

What race condition can occur in a distributed rate limiter, and how is it solved?

Two instances can read the same counter value simultaneously, both increment, and both allow a request that should have been blocked. Solutions include locks, Lua scripts that make the read-and-update atomic in Redis, and Redis sorted sets, with a centralized data store for synchronization.

Why store counters in Redis instead of a database on disk?

The limiter runs on every request, so it must add minimal latency. In-memory counters in Redis are fast to read and update, whereas disk access would slow down every call.

What are the two parameters of a token bucket and why do they matter?

Bucket size (how many tokens it can hold, which caps the burst) and refill rate (tokens added per unit time, which sets the sustained rate). Tuning them well is the main challenge of the algorithm.
