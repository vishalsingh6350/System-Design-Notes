Picture this

You fix one typo in a 40-page report on your laptop at 11 pm, close the lid, and the next morning your phone already shows the corrected version. Meanwhile a colleague edited the same file at the same moment, and instead of one of you silently losing work, the system shows both copies and lets them choose. Now multiply that by 10 million daily users, each storing up to 10 GB, adding up to 500 PB in total, with a flat rule that losing data is unacceptable. The challenge is to move as few bytes as possible, keep every device in agreement, and never drop a file even when servers, networks or whole regions fail.

1 Macro Structure & Dependency Map

The system is split into two planes: a data plane that moves file bytes as blocks, and a metadata plane that records what exists, which version is current, and who needs to hear about it. Almost every design choice follows from keeping those two planes separate.

  • Block Servers & Cloud Storage — the data plane; files become 4 MB blocks that are stored, synced and deduplicated independently
    • Split into blocks (max 4 MB), each with a unique hash
      • Compressed and encrypted before upload
    • Stored in cloud storage (e.g. S3) with cross-region replication
      • Cold storage (S3 Glacier) for inactive files
    • Delta sync: only changed blocks travel
  • Metadata DB & API Servers — the metadata plane; the source of truth for files, blocks and versions
    • Tables: User, File, Block, File Version
    • API servers handle auth, profiles and every non-upload workflow
      • Metadata cache for hot entries
      • Sharding and replication; promote a replica on failure
    • Upload status: pending → uploaded
  • Notification Service — tells every other device that something changed, so sync can begin
    • Publisher/subscriber over long polling
    • Offline backup queue holds changes for disconnected clients
      • Clients reconnect to another server if one fails
  • Sync & Conflict Resolution — the rules that keep multiple writers from destroying each other's work
    • First processed version wins
    • Losing version saved separately; user merges or overrides
    • Revision history
      • Limit saved revisions; prioritise recent versions

Blocks are the hub of the data plane: delta sync, deduplication, compression and reconstruction all depend on files being chunks with hashes. The metadata DB is the hub of the control plane: it knows which blocks form which version. The notification service links the two by telling clients when to go and fetch. Conflict resolution is what happens when two clients race through that loop at once.

Every file change travels the same loop: bytes go one way, metadata goes another, and a notification closes the loop for other devices.

Follow one file edit

  1. You edit a 40 MB presentation on your laptop. Split into 4 MB blocks, it is 10 blocks; your edit touched blocks 2 and 5.
  2. Your client sends the new file metadata to the API servers, which record the new version in the metadata DB with status pending.
  3. The notification service immediately tells your other devices that a change is underway.
  4. In parallel, the client sends the data to the block servers. Using block hashes, they detect that only blocks 2 and 5 changed. Those two are compressed, encrypted and uploaded to cloud storage; the other 8 are untouched (delta sync).
  5. Cloud storage fires a callback to the API servers, which flip the status to uploaded and record which blocks make up the new version.
  6. The notification service pushes "file updated" to your phone, which is holding an open long-poll connection.
  7. Your phone asks the API servers for the new metadata, sees it needs blocks 2 and 5, downloads just those from the block servers, and rebuilds the file.
  8. Your tablet was offline all day. The change waits in the offline backup queue; when the tablet reconnects it pulls the latest changes and runs the same download flow.

3 Purpose & Concept Beacons

Google Drive keeps many devices in agreement about a user's files by moving bytes as small, hashed blocks and coordinating everything through a strongly managed metadata record plus change notifications.

Mental picture

Picture a jigsaw library. Every document is a jigsaw cut into numbered pieces of at most 4 MB (blocks), each stamped with a fingerprint (hash) and sealed in a tamper-proof bag (compression and encryption). The pieces live in a vault with branches in several cities (S3 with cross-region replication), and old puzzles are moved to the cellar (cold storage). A head librarian keeps the master catalogue of which pieces make up which edition of which puzzle (metadata DB via API servers). When a puzzle changes, a messenger runs to every reading room (notification service over long polling), and leaves notes for readers who are out (offline backup queue). Readers then swap only the pieces whose fingerprints changed (delta sync).

4 Opportunistic Drilling

The marks concentrate on four ideas: the improved architecture, the block model with delta sync, the upload/download choreography, and conflict handling. Everything else (failure handling, storage savings) plugs into these.

From one server to the improved design

The starting point is almost comically simple: one web server, one metadata database, and a drive/ directory containing a namespace folder per user. A file is identified by namespace plus relative path. It works for a demo, but one disk fills up, one server is a single point of failure, and nothing is replicated.

The first fixes are familiar: shard storage by user_id, move files to Amazon S3 with cross-region replication, put a load balancer in front of multiple web servers, and shard and replicate the metadata database. The improved design then separates concerns into distinct services, shown below.

Common trap: sending file bytes through the API servers. API servers handle every workflow except uploading; bytes go through block servers.

Blocks, hashes and delta sync

Block servers cut every file into blocks of at most 4 MB, give each block a unique hash, compress it with an algorithm suited to the file type, encrypt it, and store it independently in cloud storage. The file itself is just an ordered list of block references in the metadata DB, and reconstruction means joining blocks in that order.

This single idea pays off three times. Delta sync: when you edit a file, only blocks whose hashes changed are transferred. Deduplication: identical blocks within an account are stored once. Reliability: a failed block upload can be retried on its own, and a failed block server simply has its pending tasks reassigned.

Gains

Far less bandwidth per edit, faster sync, storage savings from dedup, and fine-grained retries.

Costs

More metadata: a Block table and File Version table must track which blocks make up each version, and clients must reassemble files.

Upload and download choreography

Upload runs two tracks at once. On the metadata track, the client sends file metadata to the API servers, which store it with status pending and trigger a notification that a change is coming. On the data track, the client uploads to block servers, which push blocks to cloud storage. When storage finishes, it calls back the API servers, which set the status to uploaded and trigger a second notification.

Download is the mirror image, triggered by a change elsewhere. An online client hears about it via the notification service; an offline client finds changes waiting when it reconnects. Either way, it fetches metadata from the API servers first, then downloads only the needed blocks and rebuilds the file.

  1. Trigger: notification (online) or queued changes (on reconnect).
  2. Fetch updated metadata via API servers.
  3. Download the changed blocks from block servers.
  4. Reconstruct the file locally.
Common trap: thinking notifications carry the file. They only say "something changed"; the client then pulls metadata and blocks itself.

Sync conflicts and failure handling

When two users modify the same file at the same time, the version the system processes first wins. User 1's update goes through; user 2 gets a sync conflict. Nothing is thrown away: the system presents user 2 with both their local copy and the latest server version, and user 2 chooses to merge them or override one with the other.

Storage costs are controlled three ways: block-level dedup by hash, limiting the number of saved revisions while favouring recent ones for frequently edited files, and moving rarely accessed files to cold storage such as S3 Glacier.

Test yourself

Answer in the margin with your stylus before you reveal each one.

Why split files into 4 MB blocks instead of storing whole files?

Blocks with hashes enable delta sync (only changed blocks travel), deduplication (identical blocks stored once) and independent retries. Whole-file storage would force re-uploading an entire 10 GB file for a one-byte change.

What does the pending status protect against?

Metadata is written before the bytes have finished uploading. Marking it pending means the file is known but not yet complete; only the cloud storage callback moves it to uploaded, so no client treats a half-uploaded file as ready.

A laptop is offline for two days while files change. What happens when it reconnects?

Change information was kept in the offline backup queue. On reconnecting, the client pulls the latest changes, fetches updated metadata from the API servers, and downloads only the blocks it needs.

Two users save the same file at the same moment. Walk through the outcome.

Whichever update the system processes first wins and becomes the latest version. The other user gets a sync conflict and is shown both their local copy and the server version, then chooses to merge or override.

Compare the roles of block servers and API servers.

Block servers handle file bytes: splitting, hashing, compressing, encrypting and storing blocks. API servers handle everything else: authentication, profiles, and metadata updates in the metadata DB.

Why long polling for the notification service?

Clients hold a connection open so the server can respond as soon as a file is added, edited or deleted, giving near-instant change notification without constant repeated requests.

The primary metadata database dies. What happens?

A replica is promoted to master and traffic is redirected to the remaining replicas, so metadata stays available.
