Picture this

Monday, 8:59 a.m. A billion inboxes wake up at once. Every second, 100,000 new emails leave the building, some carrying 20 MB slide decks, while strangers' mail servers knock on your door with messages that must land in the right inbox, pass spam checks, appear on screen instantly, and be searchable the moment they arrive. Nothing can ever be lost, because a missing email might be a job offer or a contract. That is a distributed email service like Gmail: a planet-scale post office that never closes, never loses a letter, and remembers every word you have ever received.

1 Macro Structure & Dependency Map

At a distance the system is two conveyor belts (sending and receiving) feeding a set of specialized stores, all partitioned by user. Read each hub as a question the design must answer.

  • Protocols & the mail ecosystem — you must speak the outside world's language before you can build anything
    • SMTP between servers; HTTP/REST for our webmail clients
    • DNS MX records tell senders which server accepts mail for a domain
      • POP downloads and deletes; IMAP keeps mail on the server
      • Attachments base64-encoded, ~25 MB limit
  • Async send & receive pipelines — queues absorb 100k emails/sec and slow remote servers
    • Send: load balancer → web servers → outgoing queue → SMTP outgoing workers
    • Receive: SMTP load balancer → SMTP servers → incoming queue → mail processing workers
      • Error queue; exponential backoff when recipient server is down
    • Real-time servers push new mail via WebSockets
      • Long-polling fallback for older browsers
  • Metadata DB partitioned by user_id — almost every operation touches one user's mailbox only
    • Tables: folders, emails (timeuuid email_id), attachments
    • Denormalized read / unread email tables
      • Thread reconstruction via Message-Id, In-Reply-To, References headers
    • Consistency chosen over availability
      • Custom DB at Gmail scale (BigTable); multi-DC leader-follower failover
  • Supporting stores — each data shape gets a store suited to it
    • Attachment store: object storage (e.g. S3)
    • Distributed cache: recent emails in Redis
    • Search store: Elasticsearch partitioned by user_id, updated async via Kafka
      • Custom engine built on LSM trees as an alternative
  • Deliverability — sending is easy; landing in the inbox, not spam, is hard
    • Dedicated IPs, separate marketing mail, IP warm-up over 2-6 weeks
    • Ban spammers fast, ISP feedback loops, SPF / DKIM authentication

Protocols set the boundary with the outside world, and the pipelines are how mail crosses that boundary without overwhelming anything. Once mail is inside, the user_id partitioning of the metadata DB is the organizing idea that lets search, cache and storage scale by user. Deliverability is the one hub that depends on reputation rather than engineering alone.

2 Black-Box Cause & Effect Flow

Follow the boxes along the send path and then the receive path. Each takes a message in one state and hands it on in a safer or more useful state.

Load balancer + web servers

Input: POST /v1/messages from the webmail client (To, Cc, Bcc, body, attachment references).

Output: A validated email on the outgoing queue, or on the error queue if validation fails.

The post office counter: it rate-limits people mailing in bulk, weighs the parcel (size check), runs a spam check, and hand-delivers mail addressed to someone in the same domain without sending it out.

→ feeds into: outgoing message queue

Outgoing queue + SMTP outgoing workers

Input: Queued emails; attachments are references into the object store.

Output: Mail delivered via SMTP to the recipient's server (found through its MX record); a copy in the Sent folder.

Couriers who take parcels off the loading dock, scan them for viruses, and drive them to the right town. If the town's post office is closed, they come back later, waiting longer each time.

→ feeds into: the remote mail server (or our own receive path)

SMTP load balancer + SMTP servers

Input: Inbound SMTP connections from other mail servers.

Output: Accepted mail on the incoming queue; invalid mail discarded; large attachments placed in the object store.

The receiving dock with a bouncer: obviously bad deliveries are turned away at the gate before they take up any space inside.

→ feeds into: mail processing workers

Mail processing workers

Input: Accepted incoming mail.

Output: Mail written to the metadata DB, cache and object store, and handed to real-time servers.

Sorters who stamp each letter, file a copy in the right mailbox, put recent ones on the "just arrived" shelf, and ring the recipient's doorbell.

→ feeds into: storage layer and real-time servers

Storage layer (metadata DB, attachment store, cache, search)

Input: Email metadata, bodies, attachments and indexing events.

Output: Durable, user-partitioned mailboxes; fast recent reads; full-text search.

A filing room where each user's drawer lives on one cabinet (one shard), heavy parcels go to the warehouse (S3), and a card catalogue (Elasticsearch) indexes every word.

→ feeds into: GET /v1/folders, GET /v1/folders/{id}/messages, search

Real-time servers

Input: New-mail notifications for online users.

Output: Pushes over WebSockets (long-polling for old browsers); offline users fetch via HTTP later.

The doorbell. If you are home, it rings instantly; if you are away, the mail simply waits in your box.

→ feeds into: the user's open webmail tab

Follow one email

  1. Alice, a user of our service, writes to Carol at another provider, attaches a 2 MB PDF, and presses Send. The attachment is uploaded to the object store and the email references it.
  2. The load balancer checks Alice is not sending excessively and routes the request to a web server.
  3. The web server runs a spam check and basic validation (size well under the ~25 MB limit). Carol's domain differs from Alice's, so there is no internal short-circuit. The email goes onto the outgoing queue.
  4. An SMTP outgoing worker pulls it, runs spam and virus checks, looks up the MX record for Carol's domain in DNS, and delivers via SMTP. A copy is stored in Alice's Sent folder.
  5. Suppose Carol's server is down: the email stays queued and is retried with exponential backoff. A growing outgoing queue is a monitoring signal to investigate or add consumers.
  6. Carol replies. Her server resolves our MX record and connects to our SMTP load balancer; an SMTP server applies the acceptance policy and places the mail on the incoming queue.
  7. A mail processing worker checks it, then writes metadata to the emails and unread tables in Alice's partition (keyed by user_id, with a timeuuid email_id), caches it in Redis, and stores any large attachment in the object store.
  8. An indexing event is published to Kafka, and Elasticsearch updates Alice's index asynchronously.
  9. Alice has webmail open, so a real-time server pushes the reply over her WebSocket and it appears in her inbox, grouped into the thread via its In-Reply-To header.

3 Purpose & Concept Beacons

Reliably move and store email for a billion users, with no data loss, instant delivery and per-user search, by decoupling everything with queues and partitioning everything by user.

Mental picture

Imagine a national postal service for a country of a billion people. Counters in every town accept outgoing letters and weigh them (web servers with validation), then drop them on a loading dock (outgoing queue) where couriers drive them to other countries' post offices listed in a global directory (SMTP workers using DNS MX records). Incoming trucks arrive at a guarded receiving dock (SMTP servers with acceptance policy), and sorters file each letter into one private drawer per citizen (metadata DB partitioned by user_id), sending bulky parcels to a warehouse (S3 attachment store). A doorbell rings when you are home (WebSocket push), and each citizen has a personal card catalogue of every letter they have ever received (per-user Elasticsearch index).

4 Opportunistic Drilling

The pipelines and the metadata data model carry most of the interview weight; search and deliverability are where you show depth. Drill these four.

Why traditional mail servers break, and the queue-based pipelines that replace them

Classic mail servers stored each email as a separate file in a local directory per user. That is fine for one server and a few users, but at scale disk I/O becomes the bottleneck, and a single damaged disk or dead server loses mail, violating reliability and availability.

The distributed design puts a queue in the middle of both directions. On the send side, the web server only validates and enqueues, so a slow or unreachable recipient server never blocks the user's click. On the receive side, SMTP servers only accept or reject and enqueue, and mail processing workers do the heavy lifting of storing, caching and notifying.

Common trap: Forgetting to monitor the outgoing queue. If it grows, either the recipient server is unavailable (retry with exponential backoff) or you need more consumers.

The metadata database: partition by user, denormalize for queries

Email metadata has a telling shape: headers are small and read often, bodies can be large but are usually read once, nearly every operation is scoped to one user, recent mail is read far more than old mail, and loss is unacceptable. Relational DBs are tuned for small rows, object stores cannot efficiently support "mark as read" or search, and Gmail's BigTable is not open source. So the notes describe the characteristics of the ideal store instead: single-digit MB columns, strong consistency, low disk I/O, high availability and easy incremental backups.

The primary key has two halves. The partition key (user_id) decides which shard holds the data, so one user's mailbox lives in one place. The clustering key (such as a timeuuid email_id) decides the sort order inside that partition, so "newest first" is free.

The catch: in a Cassandra-style store you cannot filter on a column that is not part of the key, so "show unread emails" cannot be a simple WHERE is_read = false. Fetching all and filtering in memory does not scale. The answer is to denormalize into separate read and unread tables, and move a row between them when its state changes.

Gains

Every common query is a single-partition key lookup; users never contend with each other; strong consistency keeps mailbox state correct.

Costs

Sharing one email across multiple users is not supported; denormalized tables duplicate writes; during failover or partition, affected users briefly cannot sync.

Search: Elasticsearch or a custom LSM-based engine

Email search is not web search. Its scope is one mailbox, results are sorted by attributes like date rather than relevance, and indexing must be quick and accurate. It is also write-heavy: every arriving, moved or deleted email triggers reindexing, yet users rarely open the search box.

The off-the-shelf option is Elasticsearch partitioned by user_id so a user's documents sit on one node. Writes (reindexing) flow asynchronously through Kafka; searches are synchronous. The custom option builds the index on an LSM tree: writes accumulate in memory and, past a threshold, are merged into the next layer on disk, so the disk only sees fast sequential writes.

Gains

Elasticsearch is ready-made and handles full-text email search well. A custom engine can be tuned for email, scale further, and can be the datastore itself.

Costs

Elasticsearch is another cluster to run and keep in sync with the metadata store, and scales only so far. A custom engine needs significant engineering effort.

Deliverability and availability

Spinning up a server that sends mail is trivial; getting that mail into inboxes instead of spam folders is not. Recipient providers judge you by reputation. Use dedicated sending IPs, keep marketing mail on separate servers so it does not taint important mail, warm up new IPs gradually over 2 to 6 weeks, ban spammers quickly, process ISP feedback on complaint rates, and authenticate mail with SPF and DKIM.

For availability, most components scale independently because users rarely interact at the data level. A multi-data-center setup with leader-follower failover keeps the service alive when a whole DC fails.

Test yourself

Answer in the margin with your stylus before you peek.

Why does the send path put a queue between web servers and SMTP workers?

It decouples the user's request from delivery to remote servers, which may be slow or down. Users get a fast response, workers scale independently, and failed deliveries are retried with exponential backoff.

What happens if the outgoing queue keeps growing?

Either a recipient server is unavailable, so mail is waiting on retries, or there are not enough consumers. Investigate the remote server or scale out SMTP workers.

Why partition the metadata DB by user_id, and what does it cost?

Almost every operation touches only one user's mailbox, so each query hits one shard and users do not interfere. The cost is that an email cannot be shared across users in this model, which is not required here.

How do you fetch unread emails when the store cannot filter on is_read?

Denormalize into separate read and unread tables, keyed the same way, and move rows between them when the state changes. Filtering all emails in memory does not scale.

Compare email search with web search.

Email search covers one mailbox, sorts by attributes like date, and needs fast, accurate indexing. Web search covers the whole internet, sorts by relevance, and tolerates indexing delay. Email search is also write-heavy.

Why does an LSM tree suit a write-heavy search index?

It buffers writes in memory and flushes them to disk as sequential merges, avoiding slow random writes. The same idea powers Cassandra, BigTable and RocksDB.

Why might mail from a brand-new server land in spam, and how do you fix it?

Recipient providers do not trust unknown IPs. Use dedicated IPs, warm them up over 2 to 6 weeks, separate marketing mail, ban spammers fast, process ISP feedback, and authenticate with SPF and DKIM.
