Picture this

A shopper in Mumbai adds sneakers to a cart at the exact moment a fibre cable between two of your data centres is cut. One replica heard about the sneakers; two did not. Should the next get(cart) refuse to answer until the network heals, or answer now with possibly stale data? A single-server hash table never faces this question, but the moment you spread put and get across many machines, you are negotiating with the CAP theorem on every request. This chapter builds a store that stays up, scales out, and lets you tune how strict "consistent" needs to be.

1 Macro Structure & Dependency Map

The whole design is a stack of answers to one question: how do you keep small key-value pairs (under 10 KB) available and correct when they live on many fallible machines? Read the hubs in order — each exists because the previous one created a new problem.

  • CAP trade-off — sets the rules of the game before any component is chosen
    • Consistency, Availability, Partition tolerance: pick two
      • CA cannot exist in practice because network partitions are unavoidable
    • So the real choice during a partition: CP (block writes) or AP (serve possibly stale data)
      • CP example: banking systems
  • Partitioning & replication on the ring — where data lives and how many copies exist
    • Consistent hashing spreads keys; virtual nodes proportional to server capacity
      • Automatic scaling as servers join or leave
    • Replicate to the first N servers clockwise
      • Place replicas in distinct data centres
  • Quorum consistency & conflict resolution — the dial between speed and correctness
    • N, W, R and the rule W + R > N
      • Typical: N = 3, W = R = 2
    • Consistency models: strong, weak, eventual
    • Vector clocks detect concurrent (sibling) versions
      • Clients reconcile; clocks may need trimming
  • Failure handling — detect, survive, and heal
    • Detection: gossip protocol with heartbeat counters
    • Temporary failures: sloppy quorum + hinted handoff
    • Permanent failures: Merkle trees for anti-entropy sync
      • Data-centre outages: replicate across data centres
  • Storage engine: write & read paths — what one node does with a single request
    • Write: commit log → memory cache → flush to SSTable
    • Read: memory cache → Bloom filter → SSTable
      • Based on Cassandra's architecture

CAP decides the philosophy; the ring decides placement; quorums and vector clocks decide what "correct" means; failure handling keeps the promises when machines die; the storage engine is the local plumbing on each node. If you remember the order “choose, place, agree, heal, store”, you can rebuild the chapter.

2 Black-Box Cause & Effect Flow

Follow the machinery from the client's API call down to the disk and back out. Each box consumes what the previous box produced.

Client API + coordinator

Input: put(key, value) or get(key).

Output: the request forwarded to the right replicas, and a single response back to the client.

The coordinator is a concierge: any node can play it, it knows who holds what, and it hides the crowd of replicas behind one simple desk.

→ feeds into: ring lookup

Consistent-hash ring (partitioning + replication)

Input: the key.

Output: an ordered list of N replica nodes — the first N servers clockwise from the key.

Same ring as the previous chapter, but the walk does not stop at the first server; it collects N of them, ideally in different data centres.

→ feeds into: quorum

Quorum (N, W, R)

Input: the request fanned out to N replicas, plus the chosen W and R.

Output: success once W write-ACKs or R read replies arrive.

A vote: the coordinator does not wait for everyone, only for enough voters. W + R > N guarantees the read voters and write voters overlap on at least one up-to-date node.

→ feeds into: versioning (on reads) and the storage engine (on each replica)

Versioning with vector clocks

Input: multiple versions of the same key, each tagged with [server, counter] pairs.

Output: either "one version is the ancestor, keep the newer" or "siblings in conflict, let the client reconcile".

Each version carries a family tree. If one tree contains the other, there is no fight; if they branched, someone has to merge them.

→ feeds into: the value returned to the client

Failure machinery (gossip, sloppy quorum, hinted handoff, Merkle trees)

Input: heartbeat counters, down nodes, divergent replicas.

Output: an accurate membership view, uninterrupted writes, and replicas re-synchronised.

The immune system: gossip notices illness, sloppy quorum routes around it, hinted handoff returns borrowed data, and Merkle trees find exactly which cells need repair.

→ feeds into: the quorum having enough healthy voters

Node storage engine

Input: a write or read arriving at one replica.

Output: durable storage (commit log + SSTables) and fast reads (memory cache + Bloom filter).

Scribble the order in a ledger first so nothing is lost, keep a hot copy on the desk, and file it in sorted drawers when the desk fills up.

→ feeds into: the ACK or value returned to the coordinator

Follow one key

  1. The client calls put(key1, val1). It reaches node n6, which acts as coordinator.
  2. n6 hashes key1 onto the ring and walks clockwise, collecting N = 3 replicas: n0, n1 and n2.
  3. The coordinator sends put(key1, val1) to all three in parallel.
  4. On each replica the write is first appended to the commit log on disk, then stored in the memory cache.
  5. With W = 2, the coordinator replies "success" as soon as two ACKs arrive, without waiting for the slowest node.
  6. Suppose n2 is down. Gossip has already marked it offline, so a sloppy quorum uses the next healthy node on the ring instead; when n2 recovers, hinted handoff pushes the write back to it.
  7. Later, get(key1) arrives. With R = 2 the coordinator waits for two replies. Since W + R = 4 > 3, at least one reply carries the latest value.
  8. On the replica, the read checks the memory cache first; if the value was flushed, a Bloom filter points to the SSTables that might hold key1.
  9. If two replies carry sibling vector clocks, both versions go back to the client to reconcile.

3 Purpose & Concept Beacons

Build a decentralised, highly available key-value store where every node has the same responsibilities, data is partitioned and replicated on a hash ring, and the latency-versus-consistency trade-off is a dial (N, W, R) rather than a fixed decision.

Mental picture

Think of a chain of village libraries arranged around a lake (the hash ring). Every book (key) is shelved at the first three libraries you pass walking clockwise from its spot on the shore (N = 3 replicas). Any librarian can take your request and act as your concierge (the coordinator), and they only need two colleagues to confirm a new edition is shelved (W = 2) or two to report what they hold (R = 2). Librarians constantly pass notes about who is still open (gossip); if one library is closed, the next one keeps your book in a labelled box until it reopens (sloppy quorum and hinted handoff). Once in a while two libraries compare a one-line fingerprint of their whole catalogue, and only drill into shelves whose fingerprints differ (Merkle trees).

4 Opportunistic Drilling

Quorums, vector clocks and the failure toolkit are where interviewers probe and where the numbers live. The storage paths are a short, reliable win. Go deep here and treat the rest as recall.

CAP in one scenario: what happens when n3 is cut off

Three replicas, n1, n2 and n3. n3 drops off the network. Writes accepted by n1 and n2 cannot reach n3; anything written to n3 just before the cut has not reached n1 and n2 either. Somebody is now holding stale data.

A CP system responds by blocking writes to n1 and n2 so replicas cannot diverge — correct, but unavailable. An AP system keeps accepting reads (possibly stale) and writes on n1 and n2, and syncs to n3 when the partition heals — always up, but only eventually consistent.

Common trap: proposing a "CA" design. In a distributed system network failure is unavoidable, so partition tolerance is mandatory; CA cannot exist in real-world applications.

Quorum consensus: the latency vs consistency dial

The coordinator sends every write to all N replicas but declares success after W acknowledgements. Every read is sent to replicas and returns after R replies. Waiting for fewer nodes is faster; waiting for more is safer.

The magic inequality is W + R > N. If the write set and read set must be larger together than the total, they must share at least one node — and that node has the newest value. With N = 3, W = R = 2, any two readers overlap any two writers.

Vector clocks: spotting a real conflict

Each data item carries a list of [server, version] pairs. When a server writes the item, it bumps its own counter if it is already in the list, or adds itself with counter 1 if not.

To compare two versions X and Y: if every counter in X is less than or equal to its counterpart in Y, X is simply an ancestor and Y wins. If some counter in Y is smaller than in X (and vice versa), they are siblings — concurrent edits — and the system hands both to application logic or the client to reconcile.

Gains

Detects conflicts precisely instead of silently losing one of two concurrent writes.

Costs

Pushes merge logic onto clients, and the clock grows with every server that writes, so it may need trimming.

The failure toolkit: detect, bridge, repair

Detect. One node's accusation is not enough; you want at least two independent sources. In gossip, each node keeps a member list with heartbeat counters, increments its own counter, and periodically sends heartbeats to random nodes. If a member's counter has not increased for a predefined period, it is considered offline.

Bridge temporary failures. A strict quorum would stall if a designated replica is down. A sloppy quorum instead picks the first W healthy servers (for writes) and first R healthy servers (for reads) on the ring. The stand-in holds the data, and hinted handoff pushes it back when the original returns.

Repair permanent failures. Merkle trees make replica comparison cheap. Divide the key space into buckets, hash each key, hash each bucket, then hash pairs upward until one root hash remains. Two replicas compare roots: equal means in sync; different means descend into child hashes until the mismatched bucket is found, and sync only that data.

  1. Divide the key space into buckets.
  2. Hash each key in a bucket with a uniform hash.
  3. Create one hash per bucket.
  4. Combine bucket hashes upward to a single root; compare roots, then children, to find the divergent bucket.

For whole data-centre outages, the answer is simply replication across multiple data centres.

Inside one node: the write and read paths

Borrowed from Cassandra. A write is first persisted to the commit log on disk (so a crash cannot lose it), then saved in the memory cache. When the cache fills, it is flushed to an SSTable — a sorted string table on disk.

A read checks the memory cache first. If the key is not there, a Bloom filter quickly tells which SSTables might contain it, so the node reads only those, then returns the value.

Test yourself

Write your answer in the margin first, then tap to check yourself.

Why can't a real distributed key-value store be a CA system?

Network failure is unavoidable, so the system must tolerate partitions. That leaves a choice between consistency and availability only when a partition occurs.

With N = 3, why does W = R = 2 guarantee strong consistency but W = R = 1 does not?

2 + 2 = 4 > 3, so any read set overlaps any write set on at least one node holding the latest value. 1 + 1 = 2 ≤ 3, so a read might hit only replicas that missed the latest write.

What happens during a partition in a CP system versus an AP system?

CP blocks writes to the reachable nodes to avoid inconsistency, sacrificing availability. AP keeps accepting reads and writes, possibly returning stale data, and syncs when the partition heals.

Given D3([Sx,2],[Sy,1]) and D4([Sx,2],[Sz,1]), is there a conflict? Why?

Yes. D3 has Sy = 1 where D4 has 0, and D4 has Sz = 1 where D3 has 0, so neither dominates. They are siblings and must be reconciled by the client or application logic.

Compare sloppy quorum with hinted handoff.

Sloppy quorum keeps the system available by using the first W or R healthy servers on the ring instead of down ones. Hinted handoff is the follow-up: when the down server recovers, the stand-in pushes the changes back to restore consistency.

Why are Merkle trees efficient for syncing replicas after a permanent failure?

Replicas compare root hashes first and only descend into subtrees whose hashes differ, so they locate inconsistent buckets without scanning everything. Only the differing data is transferred.

Why does the write path append to a commit log before updating the memory cache?

The commit log on disk makes the write durable; if the node crashes, data only held in the memory cache would otherwise be lost. The cache is later flushed to SSTables when full.
