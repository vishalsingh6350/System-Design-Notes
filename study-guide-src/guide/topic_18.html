Picture this

You are in a rental car at an unfamiliar airport, phone on the dashboard, and you type "Disneyland." Within a second the screen fills with streets, a blue line snakes across the city, and a voice says "42 minutes." Behind that second, the app has turned your words into coordinates, stitched together a route across a road graph built from terabytes of raw data, asked a traffic model how long it will take, and streamed you only the few map squares you can actually see. Now multiply by a billion daily users, all of them also sending their GPS positions back in, and one accident on a freeway that should reroute thousands of drivers at once. That is the problem: a planet-sized map, served as if it were a local file.

1 Macro Structure & Dependency Map

The design stands on three services — location, navigation, map rendering — all resting on one idea: chop the world into tiles. Read the tree top-down; the tiling hub comes first because both rendering and routing borrow it.

  • Tiling the world (geohash, zoom levels) — the core trick that turns a petabyte-scale planet into small, cacheable, addressable squares
    • Map projection: 3D sphere to 2D plane (Google uses Web Mercator)
      • Every projection distorts geometry somewhat
    • Geohash: recursive quadrant subdivision encoded as a string
      • Latitude/longitude as the underlying positioning system
    • Zoom levels: level 0 = one 256x256 tile; each level quadruples tile count
  • Map rendering service — what the user sees; must be smooth and cheap on data and battery
    • Precomputed static tiles served from a CDN (closest POP)
      • World map estimated at ~70PB, after compressing near-identical tiles (e.g. desert)
    • Tile URL from geohash: client-computed or via a small URL API
    • Vector tiles (paths & polygons) rendered on the client
      • Substantial bandwidth savings vs raster images
  • Navigation service — turns "A to B" into an accurate route + ETA; the most algorithmically rich part
    • Geocoding service (address → lat/long), backed by Redis
    • Route planner → shortest-path (A* variant on routing tiles) + ETA (ML on traffic) + ranker (filters)
      • Updater services asynchronously refresh traffic and other DBs
    • Routing tiles: graph of intersections (nodes) and roads (edges), hierarchical levels of detail
      • Built by an offline pipeline, stored as binary adjacency lists in S3
    • Adaptive ETA and rerouting over WebSocket
  • Location service — the feedback loop: user GPS streams feed traffic, ETAs, and road-data improvements
    • Client batches GPS points; POST /v1/locations
    • Cassandra: partition key user_id, clustering key timestamp
    • Kafka streams updates to traffic, ML, routing-tile and analytics consumers
      • ~200k QPS, ~1M QPS at peak (1B DAU x 35 min/week)

Tiling is the root hub: rendering uses image tiles by zoom level, and navigation uses routing tiles with levels of detail — the same "divide into squares, load only what you need" strategy applied twice. The location service is the loop that keeps navigation honest: without live GPS data there is no traffic, and without traffic the ETA is a guess.

2 Black-Box Cause & Effect Flow

Three parallel flows share the same client: tiles flow down, locations flow up, and route requests go round-trip. Here they are as sealed boxes in causal order.

Client tile resolver

Input: Current viewport position and zoom level.

Output: A list of tile URLs (derived from geohash + zoom).

Like knowing a book's shelf number: once you know the geohash and zoom, you know exactly which file to fetch, no server thinking required.

→ feeds into: CDN

CDN with precomputed tiles

Input: Tile URL request.

Output: A static 256x256 tile (image or vector) from the nearest point of presence.

A chain of neighborhood newsstands that each carry the same printed pages, so nobody has to travel to the printing press.

→ feeds into: Client mosaic rendering

Location service

Input: Batched array of (lat, long, timestamp) tuples.

Output: Rows in Cassandra and events on Kafka.

A mail slot that accepts a bundle of postcards at once instead of one knock per postcard.

→ feeds into: Traffic update service, ML, routing-tile processing, analytics

Geocoding service

Input: Address text, e.g. "1600 Amphitheatre Parkway, Mountain View, CA".

Output: Coordinates (37.4224764, -122.0842499) and a place ID.

The translator between how humans name places and how machines locate them.

→ feeds into: Route planner

Shortest-path service

Input: Origin and destination lat/long.

Output: Candidate paths computed with an A* variant over routing tiles.

A hiker who only unfolds the map sections she needs, switching to a coarser regional map for long distances.

→ feeds into: ETA service, Ranker

ETA service + Ranker

Input: Candidate paths, live traffic data, user filters (avoid tolls, freeways).

Output: ML-predicted travel time per path and a ranked best route.

A seasoned taxi driver who knows rush-hour patterns, combined with your preference to skip toll booths.

→ feeds into: Navigation response to client

Adaptive rerouting

Input: A traffic incident on some routing tile + stored in-flight routes.

Output: Affected users identified and pushed new routes/ETAs over WebSocket.

A dispatcher who knows every driver's planned roads and radios the ones heading toward the crash.

→ feeds into: Client (live updates)

Follow one route request

  1. You type "Disneyland" while at 1355 Market Street, SF; the client sends GET /v1/nav?origin=1355+market+street,SF&destination=Disneyland.
  2. The navigation service calls the geocoding service, which looks up both addresses in the Redis-backed geocoding DB and returns lat/long pairs.
  3. The route planner hands the pairs to the shortest-path service, which derives geohashes and thus the origin and destination routing tiles.
  4. Because this trip is hundreds of miles, the algorithm quickly climbs from detailed local tiles to coarser, wide-area tiles, loading them from S3 (heavily cached) and traversing with A*.
  5. The ETA service scores each candidate path with an ML model fed by the traffic DB, which the update-traffic service keeps fresh from location data.
  6. The ranker applies your filters (say, "avoid tolls") and picks the top route; the response includes distance, duration, polyline, and turn-by-turn HTML instructions.
  7. Meanwhile, your phone fetches only the visible map tiles from the nearest CDN POP, and every few seconds uploads a batch of GPS points to the location service.
  8. Twenty minutes in, an accident blocks a tile on your path. The rerouting check sees your stored tile chain covers it and pushes a faster route over your WebSocket.

3 Purpose & Concept Beacons

Serve a planet-scale map and accurate, traffic-aware directions to a billion users while spending as little of each phone's data and battery as possible — by precomputing and tiling everything that does not change, and streaming only what does.

Mental picture

Think of the world as a giant atlas cut into numbered pages at many magnifications. The printed pages are the precomputed map tiles, and the newsstands on every corner that stock them are the CDN's points of presence. A second, hidden atlas shows only roads as dots and lines: those are the routing tiles, with a detailed city edition and a coarse highway edition, stored in the library basement (S3). A librarian who converts street addresses to page coordinates is the geocoding service, and the navigator who plans a trip by flipping between editions is the shortest-path service. Finally, millions of travelers mailing back postcards of where they are is the location service, and the analyst reading those postcards to mark jams in red is the traffic update pipeline feeding the ETA service.

4 Opportunistic Drilling

The payoff lies in four places: how routing scales with hierarchical tiles, how the navigation pipeline decomposes, why tiles are static on a CDN, and how adaptive rerouting avoids scanning every driver.

Routing tiles and hierarchy: making A* work on a planet

Pathfinding cost grows with the size of the graph, so running A* on the entire world's road network is hopeless. The fix mirrors map rendering: cut the road graph into routing tiles, each a small subgraph that holds references to its neighbors. The algorithm starts at the origin tile and pulls in adjacent tiles only as it explores, stitching together a bigger graph on the fly.

For a cross-country drive, even stitching small tiles is too slow and memory hungry. So there are tiles at several levels of detail, from fine-grained local streets up to coarse tiles that span wide areas. The algorithm uses the appropriately detailed tiles based on where you are headed.

These tiles are produced by a periodic offline pipeline that converts unstructured raw road data (TBs from many sources, improved by user location data) into graphs. They need no database features, so they live in S3 as compressed binary adjacency lists, cached aggressively.

Common trap: putting routing tiles in a relational or NoSQL database. Nothing queries inside them; the service just loads a whole tile by its geohash, which is exactly what object storage plus caching does best.

Rendering: static tiles, CDN, and the geohash URL

Generating tiles on demand for a billion users would put enormous load on servers and make caching nearly impossible, since every response would be unique. Instead, all tiles are precomputed for every zoom level, stored at an origin, and served from CDN points of presence closest to the user.

Client computes tile URL from geohash

No extra API hop; tiles fetched straight from the CDN.

But you are locked in

The tile-naming scheme lives in shipped app code; forcing clients to update is hard. A small server API that returns tile URLs keeps flexibility at the cost of one extra call.

New tiles are fetched when the user zooms or pans, or while navigating into a new tile. Sending vector data instead of raster images lets the client draw the map itself, which the notes call a substantial bandwidth saving — directly serving the data-and-battery requirement.

Adaptive ETA and rerouting without scanning everyone

To reroute drivers when an accident occurs, the system stores each navigating user's route as the list of routing tiles they will pass through. When a tile has an incident, find every user whose list contains it and recompute. The naive list, however, can be very long.

The clever compression: store only the origin tile and then its successively coarser "super" tiles until one contains the destination: user_1, r_1, super(r_1), super(super(r_1)), .... Now the question "is this user affected?" becomes "does the user's final, largest tile contain the accident tile?"

Updates are delivered over WebSocket: mobile push notifications have tiny payloads and do not work for web apps, long-polling costs more server compute, and SSE is one-way, while WebSocket's two-way channel also suits future features like last-mile delivery.

Test yourself

Sketch or jot your answer in the margin first, then tap to check.

Why are map tiles precomputed and served from a CDN rather than generated per request?

Dynamic generation would put a huge load on servers and make caching hard. Static tiles keyed by geohash and zoom can be cached at CDN points of presence near users, minimizing latency and server work.

How does the number of tiles change as you zoom in, and what does the lowest zoom level look like?

At the lowest zoom the whole world is one 256x256 tile. Each additional zoom level quadruples the number of tiles, which is why total storage reaches roughly 70PB even after compressing near-identical tiles.

What problem do hierarchical routing tiles solve?

For long routes, stitching together many small, detailed tiles is slow and memory hungry. Coarser tiles (e.g. highway level) let the algorithm cover long distances with far fewer nodes, using detailed tiles only near origin and destination.

Compare client-side tile URL calculation with a tile URL API.

Client-side calculation avoids an extra network call but locks the tiling scheme into app code that is hard to force-update. A URL API adds a hop but lets the server change the scheme freely.

Why Cassandra for user location data, and what are its keys?

The workload is extremely write-heavy and prefers availability over consistency, since locations go stale quickly anyway. user_id is the partition key to fetch all of a user's updates, and timestamp is the clustering key to keep them time-sorted.

What happens when an accident occurs on a routing tile?

The system checks stored in-flight routes; with the compressed representation, it tests whether each user's largest super-tile contains the accident tile. Affected users get a recalculated route and ETA pushed over WebSocket.

Why is Kafka placed after the location service?

Many consumers need the same location stream — traffic updates, ML, routing-tile improvements, analytics. Kafka decouples them so each can process the stream independently without adding load to the write path.
